### Engine limits to preserve and disclose

- 16 subscriptions per domain; paused live readers still occupy capacity. There is no subscription-close/delete tool: **revoking the owning grant is the only supported operator action to free a slot**. Engine admission transactionally retires revoked, expired or missing grant readers; automatic terminal expiry is not a manual capacity-management API. Disable, pause, token rotation or abandoning a client does not free a live slot; no eviction of live custody.
- Two snapshots per subscription, at most 96 observations and 16 MiB each; one-hour snapshot lifetime. Page limit 1–50 snapshot positions and 192 KiB **engine** serialized result. The final public/core framing must also be measured and bounded; adding provenance/schema fields cannot silently overrun that limit.
- 256 outstanding sparse refs, including sparse acknowledgments. Pending observations survive projection changes and snapshot expiry.
- 128 receipt slots shared by reservations and outcomes. Unused standalone reservations last 24 hours; committed outcomes last one hour after commit or the issuing snapshot's saved expiry, whichever is later. Identical retries do not extend committed receipts.
- Pull freezes a lowest ordered prefix. A limited snapshot has `complete:false`, retry `pull_after_ack`; null continuation finishes that snapshot only. Ack represented pages, then issue a new pull to obtain later eligible observations.
- Thread starts at the newest bounded tail window, ascending within a window; a terminal continuation requests an independently frozen older window. A limited window has `thread_continue`. Windows are not one history-wide simultaneous snapshot.
- Expired/forged/wrong-operation/anchor/visibility/manifest/generation continuations refuse; never silently restart. Reads issue refs but never implicitly ack. Oversized items refuse rather than disappear.
- These are materialization/custody bounds, not constant SQL work or a hard latency guarantee. Large one-row pages can exhaust receipt throughput at roughly 128 rows/hour with no other pressure; retained outcomes cannot be evicted to advertise unlimited catch-up.

### 3.2 Scoped v2 commands and MCP tools

All six raw tools require **`mail:read`**, not `fleet:read` and not `captain:presence`. There is no narrower existing mail-delivery scope; do not add a new scope or expand any grant implicitly. Coverage under `mail:read` uses only opaque visible source handles, not inventory. Optional inventory remains `fleet:read` and is not needed in this milestone.

| MCP tool | Core command | Arguments |
| --- | --- | --- |
| `desk_subscription_open` | `desk.subscription.open` | `{}`; domain comes exclusively from operator configuration. Opens or returns this door/grant's durable reader; no ack. |
| `desk_subscription_resume` | `desk.subscription.resume` | `{subscription}`; recovers state and durable snapshot start tokens, never accepts a cursor. |
| `desk_subscription_pull` | `desk.subscription.pull` | `{subscription, limit?, continuation?}`; default limit 50. Returns authorized eligible projection/pending observations under the recorded replay policy, potentially including outgoing captain conversations; never bulk older history under the recommended policy. |
| `desk_subscription_show` | `desk.subscription.show` | `{subscription, origin}`; exact retained authorized origin lookup, no implicit ack. |
| `desk_subscription_thread` | `desk.subscription.thread` | `{subscription, origin, limit?, continuation?}`; origin is an exact known retained thread anchor (for example from a previously served result), not a history-enumeration selector; authorize it independently, with engine window semantics. |
| `desk_subscription_ack` | `desk.subscription.ack` | `{subscription, ack_key, refs}`; all required. Server-issued batch key and actually carried raw refs only. |

`subscription` is an opaque UUID handle, not authority. `origin` is the closed `{core, mailbox, id}` identity already used by the engine: canonical UUIDs for core and mailbox, and the runtime's validated mail identifier. Never interpret core as an RPC destination. `limit` is an integer 1–50; continuation is a nonempty opaque string capped at 256 bytes. `ack_key` and each ref are nonempty opaque ASCII strings capped at 64 bytes; refs has 1–256 entries, with core sorting/deduplication before whole-batch validation. UUID handles have a 36-character canonical format. Mail IDs and operator door/domain identifiers use the existing core identifier rule: 1–160 ASCII letters, digits or `-_.:@`; mirror that length and character rule in the MCP schema.

Do **not** call the server-issued key `idempotency_key`: scoped admission currently strips that field into the generic write replay layer. The desk ledger already owns ack replay. No second receipt cache, client-generated key substitute, cross-generation translation or implicit ack retry. A page key binds one normalized batch: if selecting only part of a page, use a new server key from open/resume for a later distinct batch. Explain this in tool descriptions.

Successful public payloads use `schema:"desk.subscription.v1"`, `subscription`, `incarnation`, and `coverage`. Open/resume return `ack_key` and bounded `pending_snapshots:[{operation,anchor,continuation}]`. Page operations return `items:[{ref,origin,mail,state,delivery_class}]`, `continuation` (string or null) and `ack_key`. Every item explicitly renders its authoritative open/closed state, or `unknown` when no lifecycle state is proved; never infer closed from a raw ack. Add a core-authored `delivery_class:"history"|"since_switch_on"|"unknown"`: old open requests and any replayed older mail are labelled **history**, not “new” or “unread”. This is independent of request state and this reader's raw ack state. Ack returns `acknowledged` and `operation_complete:true`; input domain coverage is still separately dated/possibly incomplete. Core provenance is runtime-authored. The final serialized public payload, including that wrapper and provenance, must fit 192 KiB; reserve wrapper space before engine serving rather than reject an already committed page as oversized afterward. MCP transport framing has its own separately bounded overhead. Do not claim a raw ack closes a request, acknowledges the dashboard, or delivers any digest.

Each call, including open/resume/continuation/ack, resolves the actual bearer credential; the engine then verifies exact current local grant authority in its writer transaction. Recheck the credential, visibility revision and exposure binding before returning any protected result. No cached grant authority, unattended polling or SSE push. A revoke committed before engine admission prevents serving/ack changes; one committed after admission may hide the response but cannot undo committed served rows or acks. Release loss after an ack is `outcome_unknown`, not proof that nothing changed. Retry only the identical key/batch while retained.

### 3.3 Discovery, rendering and refusals

Extend scoped `capabilities` with a versioned, safe desk feature descriptor only for an enabled, admitted mail reader. Proposed shape: `desk_subscriptions:{schema:"desk.subscription-capability.v1",mode:"local_raw",operations:["open","resume","pull","show","thread","ack"],remote_owner:false,moves:false,waiting:false,presence:false,digests:false}`. It reveals no placement/domain or source inventory. A feature descriptor is not stored authority: every tool call repeats core admission. Tools/list filters by **both** `mail:read` and the descriptor. Hidden/non-enabled tools remain non-disclosing not-found on guessing; authentication failures retain normal OAuth challenges. Trusted v1 cannot acquire these commands by announcing v2.

Do not flip the legacy/global `subscriptions:false` diagnostic to an unqualified true. Keep selected-mailbox/local diagnostics scoped to their old surfaces; add the new qualified feature separately. Availability failures do not remove the operator's recorded opt-in or switch mail tools.

Preserve `coverage.v1` on every admitted new result, including failures, or use a closed non-disclosing refusal when coverage cannot safely be established. Snapshot coverage is frozen and dated, not recomputed as current on continuation. Render:

- `scope:"desk-domain"`, domain, visible opaque sources, source states/checkpoints, observation time, snapshot and allowed owner/revision fields exactly as admitted. Named-ship readers retain `complete:false`, null owner/revision and no hidden counts/topology.
- “As of last source contacts,” showing each available barrier mode, desk-measured `received_at`, `age_ms`, and the operator's `max_source_age_ms` (default 900000). Even collect/local barriers here are dated evidence; a pull creates no on-demand contact. Replay/import cannot refresh freshness.
- Omissions and history/unreadable/backpressure/unsupported gaps, and each retry action. Empty partial results say coverage is incomplete, never “nothing needs you.” Missing/malformed coverage stays incomplete; Python cannot manufacture proof.
- Continuation and `pull_after_ack`/`thread_continue` instructions separately from `coverage.complete`. A complete source vector does not mean drained inbox, exhausted history or completed work.

The bridge must normalize the internal engine's string-error envelope into a closed public error object **without losing coverage**. The current adapter's generic not-found collapse is insufficient. Proposed public error schema is `{code, message}` with optional allowlisted value-free `retry`/`hint`, alongside `coverage` when safe; no raw exception text. Preserve these outcomes:

### 3.5 Replay selection — captain choice B DECIDED (2026-10-31, `fb595ad0`, option a)

Opening from zero today freezes `(origin core, mailbox, source order, mail ID)`, not a fleet-wide newest-first feed. Up to roughly 10,000 retained history rows per source can sit before current mail; one source/mailbox's history can delay the next source. Pulling through that backlog can disclose **all retained captain conversations, including outgoing mail, to the hosted client/provider**. Independent progress is not informed consent to that bulk disclosure. Receipt throughput makes this a practical delay as well as a privacy choice.

**Approved policy: `open_and_new` — open requests plus mail from switch-on; older mail only by explicit bounded thread lookup, never bulk.** Here **open requests** means requests and decisions from ships **addressed to the captain**, awaiting the captain. The captain's own older outgoing requests are history, accessible only by explicit thread lookup, not by the old-open exception. The captain did not select `all_history` (bulk backlog/disclosure) or `new_only` (excluding older open requests). The operator records the approved policy; a grant cannot select or change it. Existing `fresh_replay` names independent reader creation, not a requirement to stream all history.

The recommended policy needs a small additive engine eligibility layer before exposure; an adapter-side filter is insufficient because it would consume refs/receipts and still send old bodies to the adapter:

- Persist a durable switch-on boundary/vector and replay policy with the exposure/reader state; do not use the dashboard cursor or client timestamps. Use source journal order and proved enrollment/barrier evidence, not remote wall clocks, to classify baseline/history versus subsequent mail. The switch-on vector is dated source evidence, not a simultaneous remote instant; disclose each source boundary. A source lacking a proved baseline is `switch_on_pending`, not evidence that late baseline rows are new. Preserve this conservative state across restart until its boundary is established via existing legal intake, without inventing a reverse contact.
- Filter automatic pull **inside** the engine/projection selector before snapshot/ref admission: carry old open requests (including decisions, addressed to and awaiting the captain) and eligible subsequent mail, retaining displaced pending versions and closure facts even if a request closes before the client acks it. Persist an eligibility pin for an offered old open request so a later closure is delivered rather than silently withdrawing custody. A closure/ack observation that gives old mail a newer `source_order` must not reclassify its original content as new; retain original-mail/baseline classification alongside mutable observation order where necessary. A proved late baseline is history; a late copy stays unknown unless separately proved history or upgraded by native proof. Arrival time is never a new-mail heuristic.
- Maintain eligibility-aware prefix compaction; intentional exclusion from **this** automatic stream is neither a raw ack nor deletion of historical facts. Exact older thread lookup uses an authorized anchor and existing bounded windows, labels every result history and never changes pull eligibility/progress implicitly. Under this policy, `show` is for already eligible/carried origins; it must not become an arbitrary bulk-old-mail enumeration escape hatch. There is no older-history list/pull endpoint. Scope restrictions still apply to lookup and coverage.
- Test old open/closed/outgoing mail, current mail behind a large baseline, late source enrollment, baseline/delta and closure races, lost page/ack, restart, restriction replay and historical thread windows. Policy resets or visibility changes cannot move switch-on forward and suppress pending facts, or label replay “new”. Report policy exclusion separately from missing-source coverage; it does not make historical retention or current coverage complete.

This changes delivery selection, not intake's required retained-history capture, origin identity, topology or request lifecycle. Precisely tracking original-mail versus later lifecycle observations may require a small additive ledger/projection field and schema fixture update; if that outgrows a small engine PR, report the split before implementing. No all-history replay is authorized by choice B.

**PR 4 split (engineering decision, 2026-10-31):** PR 4a is an additive evidence foundation only: `desk_intake_original` preserves an origin's first-applied source journal order atomically with its first projected content; legacy origins are deliberately not backfilled, even after lifecycle/ack updates. `desk_subscription_replay` copies the validated operator binding (including policy and dated switch-on vector) once at reader creation, independent of visibility incarnation. Missing legacy bindings remain unknown; disable, re-enable, restart and restriction replay never recapture the boundary. The internal classifier proves `history` only at/below an established source boundary. **First application above that boundary does not prove `since_switch_on`: late baseline/copy imports can append old content at newer journal orders. These observations, pending sources and legacy evidence remain `unknown`.** PR 4a does not filter pull, change show/thread/ack semantics, resolve pending boundaries or add public item labels. PR 4b must not activate `open_and_new` selection until a content-origin predicate is settled, then implements the remaining selector/pins/compaction/item-semantics contract. Deploying PR 4a bumps the door schema marker from v2 to v3; upgrade is additive and retains grants/readers/refs. Rollback to an older binary needs care: it does not maintain this evidence, so rows created or changed under that binary must not be assumed to have proved original-content age.

Read-only PR 4b design finding: existing `reconcile.rs::HomeProof` already carries opaque home, mailbox, enrollment nonce, `baseline_upper` and `delta_upper`; `home_proof` withholds readiness until frozen-baseline and delta imports are receipted. `proof.rs::Evidence` binds that census to an intake checkpoint; `completion.rs::snapshot` checks its validity before source coverage. This can support conservatively pending new/unproved homes and a later history boundary, without contact reversal. **As-is it is not a per-origin birth predicate**: the home uppers are not source journal sequence ranges, while `home.rs::import_one`/`resolved` flatten baseline and live observations (including same-source copies) into the same `Fact` appended by `append_in`. `Fact`/`Event` carry no baseline/live provenance. Merely using a later whole-source barrier cannot relabel earlier replay as new or safely distinguish a late copy into an already known mailbox. A no-Fact-wire-change approach would need a proved, durable mapping from home/nonce baseline completion to source journal ranges or exact origins, plus race/restart/copy tests and conservative unknown for missing evidence. A versioned optional proof-sidecar extension may carry that mapping without altering strict intake frames; it still needs protocol/old-peer review. Alternatively, source/home-authored per-origin baseline/live provenance would need persistence before append and explicit version negotiation because existing `Fact`/`Event` reject unknown fields. Neither approach is implemented or selected by PR 4a.

#### 3.5.1 PR 4b reviewed predicate contract — implementation staged

**Do not activate selection on the strength of baseline ranges alone.** A range proves where an observation was imported, not when its content originated. The proposed implementation uses an optional, independently versioned **replay-proof sidecar**, retaining the existing census/coverage sidecar unchanged. It combines a home/enrollment-to-journal mapping with a positive native-origin witness. No `Fact`, `Event`, `HomeFact` or strict intake page wire change is proposed. Linked-source assertions remain bookkeeping under the existing linked-operator trust, not cryptographic birth certificates.

Use these distinct orders; never compare one namespace with another:

- `J`: source registry journal order, including lifecycle and copy observations.
- `D`: a home's outbox order, scoped to its published enrollment nonce.
- `M`: a home's native `mail.seq` insertion order, scoped to its mailbox incarnation. The home's `mail` AUTOINCREMENT high-water, not its maximum surviving row, is the cut. Pruning must not lower it.

The source records an additive import ledger keyed by manifest binding, source, opaque home handle, mailbox and enrollment nonce. For each committed first-content native delta candidate it records its journal order, stable intent and immutable-content digest, whether it came from the frozen baseline or delta lane, and whether its provenance is **native** (`Provenance::Origin` exactly equal to this source/home mailbox/mail ID) or a copy/unresolved assertion. Baseline journal spans may be coalesced only across contiguous orders with identical binding/home/nonce/lane. They are not a single min/max interval that sweeps in interleaved imports. A native delta witness also carries the exact origin and its home insertion order `M`, read from the same consistent home snapshot as the pending intent and checked against pinned provenance/content. Read the mail high-water from `sqlite_sequence` for `mail`, never `MAX(mail.seq)`: require an AUTOINCREMENT table; a missing sequence row with surviving rows withholds positive proof. An empty never-written AUTOINCREMENT table has high-water zero. If the row is missing, mismatched, already an alias, or cannot be checked within budget, there is **no positive witness**. Never infer native provenance from the flattened `Fact.copy == None`: a same-source copy can flatten to that shape.

Baseline imports need only negative/history evidence. Positive witnesses are exact origin/source/order/digest records; do not claim every event outside baseline spans is native. `mail/source.rs` creates `Provenance::Origin` only for locally created mail; a received copy does not acquire native status by being imported locally. **New** means that exact content was created locally in its origin mailbox after the applicable cut, not first noticed, copied or re-imported after it. `D` and `M` are extra guards that only add caution; neither substitutes for native provenance. Re-creating a pruned ID must respect pinned identity/digest and retained original evidence; it cannot erase history or turn an unknown earlier incarnation into new content. Insertion before a cut followed by observation/import after it fails the `M` test.

The ledger/witness and journal append/registry receipt commit in the **same registry transaction**. A crash before the home records its receipt retries the same evidence; an already receipted legacy import cannot acquire a native-import witness retroactively. Keep original-content evidence independent of mutable lifecycle order and receipt/log reclamation: `desk_intake_original.first_order` is never reclaimed. Add the **supplying source** and **first-content kind** (`first_kind:"native"|"copy"`) beside `first_order` when first content is projected, atomically, without replacing any of them on later observations. Preserve explicit same-source/self-copy provenance in the existing optional `Fact.copy` identity (no new wire field); `copy` is recorded when that identity is present. The no-copy kind is not standalone native proof: a matching own-source native witness is still mandatory. These nullable columns and the source ledger live in the **registry** (`desk_intake.rs`), not the door database. Null permits a rolled-back 4a binary to keep inserting; legacy null is unknown and is never backfilled. Registry initialization must detect the missing column as well as missing tables, and a populated 4a registry upgrade must be tested. Do not guess a legacy supplying source from mutable projection state; missing source is unknown. In 1b, direct positive proof must require `first_kind == "native"` and match the witness's `(source, order)` to this saved first-content tuple, as well as matching origin/digest; otherwise it requires the explicit copy-first link, whose saved kind must be `"copy"` (never null). Orders are comparable only within their supplying source; in particular, never compare a copy's order with its origin source's cut.

**Source anchors are unnecessary (round-4 proof).** (1) Every native row present in any baseline has insertion `M <=` the AUTOINCREMENT high-water of the cut covering that baseline. Pruning cannot reduce that high-water or reuse `M`. Thus an unchanged row imported later cannot pass `M > cut.mail_high_water_M`, even if its lifecycle creates a later `D`/`J`. Re-enrollment or nonce/binding change requires a new cut, which again includes every existing row's `M`; an accepted restore also requires current-vector/lineage validation and a conservative cut, not reuse of incompatible proof. Undetectable identity-preserving clones remain outside the stated restore guarantee (§3.5.3). (2) A pruned/re-created ID can have a larger `M`, so its source witness is only provisional. Direct proof must match the desk's immutable `(source, first_order, first_kind == "native")` and digest: a later re-creation cannot replace that tuple or kind. A changed digest fails integrity admission. The explicit copy-first exception below is only for an original first seen as a copy; it cannot upgrade an already-native older incarnation or override history. Therefore neither baseline veto nor re-created-ID veto needs a source per-origin anchor. (3) To avoid lifecycle witness re-mints after source cleanup even against a cut **before** that row, keep a monotonic observed-`M` high-water per home. Seed it from a consistent live-home AUTOINCREMENT high-water snapshot once per published baseline before baseline/delta intake; this snapshot may be later than freeze, conservatively withholding intervening new rows, never admitting old ones. Advance it on **every observation carrying M, in every lane**, even without positive proof. Admit a native delta only when `M >` the previous `hw`, atomically advance `hw` before detail/witness admission, and retain it after cleanup. Rebuild uses the retained exact candidate, not a fresh import. A first-content import arriving at a lower `M` is withheld as unknown; out-of-order arrival cannot justify resetting the mark.

Implementation uses **one mark per `(domain, source, home)`**, carrying its maximum across binding, mailbox and nonce transitions instead of retaining one row per historical enrollment. This is stricter than per-(binding, home, nonce) marks: regressed/restored homes or a new mailbox may withhold positive evidence until they exceed the old mark, never become falsely new. Baseline/unknown lanes advance marks but allocate no per-origin replay storage. The baseline seed covers every pre-baseline row, so its first lifecycle import cannot mint an unprovable candidate or witness, even in rising-M order. No desk adoption receipt is needed to free vetoed witnesses: they are never allocated. Steady-state **additional source replay storage is O(homes ever observed), plus at most 10,000 outstanding candidate details, 2,000 witnesses and the bounded lasting omission ranges**, independent of retained/adopted origin history. No source anchor table, anchor budget or anchor cleanup remains. Existing ordinary mail/journal custody and the desk's permanent original-content rows are not duplicated in this source proof store.

**Copy-first upgrade is allowed (engineering decision).** An origin first seen as a copy may later become proved new when a native witness from the origin's **own source** proves the same immutable-content digest after that source/home's cut, and no accepted source evidence proves the content history. Preserve the first-content tuple; record an additive upgrade link from that exact tuple/digest to the own-source native witness's separate `(source, order)`. The link must match the saved first-content tuple exactly, including `first_kind == "copy"`; an already-native or null/unknown kind cannot use this exception, even for an identical-content re-created ID after journal reclamation; the native witness must match its own committed import-ledger tuple exactly. Do not pretend the original copy import was native, overwrite `first_order`, or compare the two sources' orders. A same-source copy-first case uses the same explicit link, not a later lifecycle order substituted for `first_order`. A copy without this witness remains unknown (unless independently proved history). PR 4b-2 revisits previously skipped origins on adoption of this proof. This does not add a new copy-to-projection path or relax existing integrity/alias admission. Both local-owner intake and remote intake use this same predicate.

#### 3.5.2 Immutable cuts and the positive test

Retain PR 4a's immutable exposure/reader binding and original-content order. Add companion cut records keyed by its binding hash, not by a visibility incarnation. A replay cut is an accepted, fully imported checkpoint plus the exact validated home vector: `(home, mailbox, nonce, baseline_upper_D, delta_upper_D, mail_high_water_M)` and the baseline journal spans it covers. A home read binds these fields in one snapshot. Source reconciliation rechecks the inventory, nonce/publication, delta head, loss state and registry import-ledger revision before issuance. The receiver checks the exact manifest/checkpoint, source membership, completed page custody, all orders/digests against retained authoritative origins, and sidecar bounds before adopting evidence. A later checkpoint with a different home vector cannot be substituted for the saved cut.

At enable, copy usable replay cuts atomically alongside the existing dated switch-on vector. **Enable-time freshness is mandatory:** the desk's own clock must prove the cut checkpoint's age is within the binding's `max_source_age_ms`, using the existing completed-contact clock/restore rules, not remote timestamps or sidecar arrival time. A missing/unusable clock age, stale checkpoint or replay of an old checkpoint is not a usable enable-time cut. Existing PR 4a `established` coverage evidence is **not** automatically an established replay cut: it lacks the new home/birth mapping. A source/home without a usable, fresh cut remains `switch_on_pending` for replay, even if a fully imported but stale cut is stored.

After enable, on an existing legal intake contact it may adopt its **first** usable, fully imported, fresh cut, once only. In particular a source stale at enable must take its first replay cut **after enable** when it reconnects, not adopt the cached stale pre-enable cut. This conservative delayed cut includes everything through its baseline and delta vector as pre-cut; it does not backdate newness to enable time or move an already established cut. Record and disclose each cut's checkpoint, desk-measured receipt time, `age_ms` (null when unprovable), age at adoption, freshness limit, delayed status and unproved interval separately from the original switch-on vector. Retain the adopted cut as a dated boundary when it later ages; source freshness remains a separate current-coverage check, never a reason to recapture the boundary. New content in the unproved interval may be withheld unless open; never silently claim complete from-switch-on delivery. A late home or new enrollment nonce likewise needs its own first cut. Reads themselves do not create contacts or re-enroll homes.

For an authorized observation of origin `o`, evaluate in this order:

1. **History/pre-cut:** the saved supplying-source/first-order tuple is at/below that **same source's** saved boundary; or accepted frozen-baseline evidence proves this exact original content. A validated delayed home cut can instead prove it pre-effective-cut: retain internal reason **`delayed_cut`**, counted separately from ordinary history in diagnostics, while rendering the conservative public class `unknown`. This is not proof it predates enable or a wall-clock creation time. History evidence from any accepted source vetoes a positive upgrade; lifecycle/copy order never overwrites it. Missing legacy supplying-source evidence cannot prove this order comparison.
2. **Since switch-on, direct:** require an established cut for the **same** binding/source/home/mailbox/nonce, saved `first_kind == "native"` and `(source, J0)` strictly above that source cut's journal upper, and a validated **native delta witness matching that exact saved tuple/content digest**, with `D > cut.delta_upper_D` and `M > cut.mail_high_water_M`. Here `D` is the retained outbox order found by stable intent, never the differently numbered `mail_source_import.seq`. **Copy-first upgrade:** alternatively require the exact additive link defined in §3.5.1, with the own-source native witness's journal order above its own source cut and the same `D`/`M` guards for its home. Do not compare the original supplying-source order to a different source's cut. Both paths require no accepted source proving history; no legacy first-order backfill, copy-only witness, source gap/loss, conflicting content or stale enrollment may supply positive proof.
3. **Unknown:** everything else. A later closure, raw ack, fresh contact, matching body or higher `J` alone cannot manufacture birth proof.

Why step 2 is positive evidence: all retained captain content and all deltas through the cut were receipted; the insertion high-water also covers old native rows subsequently pruned. An unchanged mailbox/nonce's native insertion beyond that high-water, observed beyond the cut's delta head, is not an old retained request receiving a new lifecycle observation. Copies alone have no native witness, irrespective of arrival lane or whether the origin was already projected; only a separately validated own-source witness can support the explicit copy-first upgrade. The conclusion is **after the disclosed per-home vector cut**, not a simultaneous remote wall-clock switch-on instant. That is the dated-vector contract above, with conservative delayed-cut omissions made explicit.

#### 3.5.3 Late arrivals, restart and restore

| Case | Required result |
| --- | --- |
| Late frozen home baseline above the source boundary | Its mapped baseline content is history, never live; home stays replay-pending until its full cut is accepted. Deltas before that delayed cut are not relabelled since-switch-on. |
| Late same-source copy of a known origin | Alias/lifecycle evidence cannot replace the saved first-content tuple or history classification. A copy-first unknown may upgrade only through the explicit own-source native-witness link with matching digest and no history veto. |
| Late copy of an unknown origin, including outside the manifest | Unknown unless separately proved history or later upgraded by the origin's own source under §3.5.1; never since-switch-on merely because it arrived in the delta lane or above `J0`. A copy with no native witness stays unknown. Preserve copy/integrity coverage obstacles. |
| Source stale at enable, later reconnects | Leave replay pending at enable; reject its cached stale cut. Adopt its first fresh post-enable cut on reconnect and separately report `delayed_cut` exclusions and the unproved interval. |
| Re-created pruned ID; insert before cut then observe after | Retained original tuple/digest/history wins; mismatched reuse is an integrity gap, absent proof is unknown. A higher replacement `M` cannot erase the old identity evidence. Insert-before-cut fails `M` even if `D`/`J` are later. Both races can only make classification more cautious. |
| Old request closes after the cut | Native home insertion order is at/below the cut even if its latest delta/journal order is higher. It stays history (or unknown without proof); offered-open custody separately requires its closure. |
| Home re-enrollment, mailbox move or nonce change | No reuse of old live ranges/cut. Establish a conservative cut for the new tuple; keep old classification/custody and reject conflicting reinterpretation. A returning old tuple cannot reset its cut. |
| Crash at any import/receipt/proof/cut commit boundary | Atomic registry evidence or no evidence; immutable intent retries. No boundary recapture on restart, disable/re-enable, token rotation or restriction replay. |
| Source/home changes during reconciliation or proof issuance | Revision/nonce/head revalidation fails; omit replay proof while normal pages/receipts retain custody. Do not publish a partly validated vector or use cached home counts as birth proof. |

| Registry/placement restore | Existing external owner fence remains mandatory. Restored cuts/progress cannot reopen service against a mismatched guard. No recovery, reset or placement action is added here. |

**Rollback/re-upgrade:** any work done under an older binary has no new witness and stays unknown absent independently retained history evidence; never synthesize native proof from its latest projection/order on re-upgrade. Before any kept cut or positive witness is reused after restart/re-upgrade, re-check its binding and enrollment tuple against the **current home vector**: unchanged mailbox/nonce/publication identity, non-regressed heads/insertion high-water, no loss and compatible import-ledger lineage/revision. Ordinary head advancement is allowed, not equality with the saved cut's old heads, and cannot replace that cut. A mismatch or unavailable validation withholds positive proof; it does not reset the immutable cut. This is in addition to the enable-time age check, not a way to refresh old checkpoint age.

This does **not** solve undetectable stale clones or arbitrary uncoordinated home restores that preserve every identity. Preserve [coverage §4's stopped-writer backup/restore prerequisites](door-mail-coverage.md#4-migration-and-local-only-compatibility); do not advertise the sidecar as a restore detector. Detected evidence loss or any missing witness is unknown, never a reason to reconstruct positive evidence from mutable projection rows. Persisted immutable evidence can retain a historical classification; absent *current* source proof cannot refresh source freshness or establish new witnesses.

#### 3.5.4 Compatibility and bounded transport

A/B1's outer sibling is `desk_intake_replay_v1`, whose presence is the support marker and whose closed version-1 object nests optional proof (exact checkpoint, census-vector digest, home cuts, baseline spans and bounded native witnesses) and bounded adoption receipts. Keep this closed object byte-shape compatible: both the A and B1 decoders reject **the entire replay sidecar** for an unknown field in the envelope or a receipt. B2's separately approved cut-return sibling below is the only exception; it must not add fields to A/B1 objects. This marker indicates implementation support, not completeness or authority: marker present/proof absent means omitted or pending proof; neither present means old/unsupported peer. Keep `desk_intake_proof` version 2 **byte-shape compatible** for existing coverage. Do not add a field to old `Evidence`, `reconcile::Proof`, `HomeProof`, `Frame`, `Fact` or `Event` on their existing wire: all relevant strict decoders use `deny_unknown_fields`. New private structs may be used after peeling off the sibling, just as the current coverage sidecar is peeled off before strict frame decoding.

**Compatibility is established by the current collect contract:** `fleet.collect` consumes a plain JSON object key by key, not an enclosing strict struct; an old peer ignores new outer siblings and still parses the unchanged strict intake/coverage shapes. There is no separate push intake: the two directions are the existing collect request/response plus local-owner intake. No optional-feature negotiation or new RPC is needed. A new receiver of old-peer pages has no replay witness and leaves that content unknown (or history if independently proved), even if ordinary source coverage is complete. Mixed-version real-subprocess tests must verify both request and response paths against the old binary, not merely deserialize a new struct with a version changed.

**The envelope limit is a hard mail-delivery limit.** `peers.rs::call` serializes the complete collect request (ID, command, args and `max_response_bytes`) and rejects it above **1,048,576 bytes** before the call: the entire collect, ordinary mail included, fails if a new sibling is not counted. In `transport::attach`, count the outer replay object (including its nested proof and bounded adoption receipts), unchanged coverage sibling, object keys/escaping/separators and existing ordinary body with the allocation-free saturating `json_size_bound`; preserve the conservative RPC-wrapper reserve (including the injected response-limit field). The final request must remain below that hard limit; response assembly uses the actual advertised `max_response_bytes` capped at 1 MiB. Test the complete serialized enclosing request/response against each limit, with escaped strings and near-limit ordinary mail, not just sidecar length. No `peers.rs` edit is proposed.

Set a separate 64-KiB replay-sidecar cap, at most 50 homes and bounded span/witness/receipt counts. Omit replay proof **first**, then optional coverage evidence, before reducing a viable legacy intake page; retain the small support marker in the reserved envelope budget. No truncation that turns partial spans/witnesses into an assertion of complete coverage. Sparse positive witnesses prove only the exact included origins. Pending proof work is bounded/resumable, with no network under a transaction, no history-sized contact scan and no ordinary mail failure because optional proof storage is full. Across contacts, reserve at least half the witness slots/bytes for unadopted witnesses, using a persistent rotating keyset cursor so new tail imports cannot starve old unadopted witnesses. This transport fairness is implemented in 4b-1b, not 1a.

**Adoption, retry and retention:** a source retains each witness until the desk explicitly confirms durable adoption, not merely page receipt, contact success or send attempt. Receipts identify the binding/source and exact proof batch/revision digest and partition its intents into adopted intents and rejected intents with typed reasons; emit them only after the desk's proof ledger commits, and resend them idempotently on legal contacts. Validate witnesses individually: one permanently invalid witness (including a pre-1a original with NULL `first_kind`) cannot prevent valid peers in its batch from being adopted. On a negative receipt, the source discloses the rejected journal order as a lasting per-reason omission, resolves that witness's custody, and releases it through the same bounded retry-window cleanup as adoption. The retained per-home M mark prevents it from being re-minted. Receipt replay never upgrades a rejected decision. Rotate small batch compositions as well as large queues. Source batch binding and indexed intent membership are stored separately from batch JSON, so retirement and cleanup require no JSON scans. Cache consistent per-home replay tuples matched exactly against the revalidated coverage vector. Quiet sources still send a cut-only proof with zero witnesses, using cached per-home tuples that exactly match the revalidated coverage vector. Refresh only missing or changed tuples within the remaining contact deadline, after ordinary page custody, including on quiet contacts; matching caches require no home opens. Keep the same 64-KiB/50-home caps and drop this optional proof before shrinking any viable ordinary page. Empty batches produce no adoption receipts. Multiple busy homes can advance together without perpetually withholding replay proof; matching cached tuples need no extra home opens. Measure ordinary frames and replay envelopes exactly with `serde_json::to_vec`; drop optional replay before it can shrink a viable ordinary page. Local replay preparation and receipt failures are best-effort and audited, just like remote contacts. CI must not download and execute workflow-run artifacts. The mixed-version subprocess test is an on-demand, required pre-deployment gate (§3.5.6); it asserts advancing ordinary intake custody and source receipts in both legal directions, not just optional key presence.

#### 3.5.5 Selection and item semantics in PR 4b-2

For an enabled `open_and_new` binding, automatic selection is **authorized AND (proved since-switch-on OR authoritative request/decision addressed to and awaiting the captain OR carried eligibility pin/pending version)**. Unknown closed/unclassified notices and outgoing mail, and known closed older history, are excluded before retained snapshot positions, serialized bodies, refs or receipts are allocated. The captain's older outgoing requests are excluded even if their lifecycle is open; only explicit thread lookup retrieves that history. Unknown **open incoming** requests/decisions awaiting the captain are intentionally included as the approved open-request exception, labelled unknown, not new. Unknown alone is never bulk-replay consent. A partial empty pull must name the replay-proof omission as well as any source-coverage omission.

Pins carry subsequent authoritative closure observations and displaced pending versions; closing before ack cannot withdraw them. Pins do not arise merely from scanning an open row, or from history lookup. Retire only when the relevant carried observations/closure are acknowledged under the ordinary bounded ledger, never on snapshot expiry alone. Newer evidence must not change the labels of an already frozen page. Items held back by a delayed cut have public `delivery_class:"unknown"`; `delayed_cut` is only the internal diagnostic reason. Item `state` comes from the authoritative origin lifecycle (`open`, `closed`, otherwise `unknown`); raw ack never closes it.

Compaction must distinguish **actually acknowledged eligible observations**, **intentional policy exclusion**, and **temporarily unproved eligibility**. Do not simply call the existing `source_order <= through_order` check after skipping unknown rows: delayed proof could make an earlier skipped origin eligible. Use bounded durable exclusion spans plus a proof-revision/revisit watermark, separate from raw acknowledgments. If exception capacity is exhausted, retain the revisit work and backpressure; never lose newly proved eligibility or fabricate an ack. Ineligible rows consume neither delivery refs nor receipt slots; acknowledged eligible refs may compact past them only while that revisit evidence remains durable. No unbounded per-history tombstone set. Tests must demonstrate that proof arriving after compaction cannot hide current mail, and that repeated proof cannot resurrect an actually acknowledged version. Exact `show` requires an independently authorized **eligible or already carried** origin; no arbitrary-old-origin enumeration through guessed IDs. `thread` still requires an independently authorized, exact retained anchor and bounded frozen windows, never a list/history selector. Thread pages are explicitly `delivery_class:"history"` (historical retrieval context), with independently proved lifecycle state; they do not relabel any automatic-stream evidence. History refs/receipts have a separate operation namespace in their own tables; automatic tables retain their v4 layout so even kind-unaware old readers cannot mistake history custody for automatic delivery. A history read **or its explicit ack** must not create automatic eligibility pins, advance its prefix, satisfy an automatic pending version or trigger its compaction; independently carried automatic refs retain their custody even for the same origin. History lookup remains permitted without a newness witness, within authorization and retention bounds.

Visibility changes retain the immutable binding/cuts but reauthorize all origins, pins, skipped-span diagnostics and responses. Existing continuation/ref incarnation fences still apply; no hidden body, origin, count or topology may escape through pending/policy diagnostics. A widened grant may replay newly visible eligible facts, never recapture switch-on or label history as new. Narrowing visibility must not silently acknowledge durable facts or erase origin evidence needed on a later authorized replay.

Diagnostics need a separate core-authored replay-selection object (policy, each effective cut's desk-measured age and adoption age/freshness limit, pending state, ordinary history exclusion, separately counted `delayed_cut` exclusion/unproved interval, unknown-proof withholding, peer-support versus omitted-proof marker state, bounded-work/backpressure and retry), not synthetic missing-source entries. Source `coverage.v1` continues to mean dated intake coverage: policy exclusion cannot make it complete, nor does intentional history exclusion make a fully covered source missing. Conversely, complete source coverage with missing replay proof is not a complete automatic stream. Freeze both diagnostics with the snapshot; sanitize by current visibility, withholding hidden counts just as coverage does. No client renderer or provider infers these labels.
