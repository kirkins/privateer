### Engine limits to preserve and disclose

- 16 subscriptions per domain; paused live readers still occupy capacity. There is no subscription-close/delete tool: **revoking the owning grant is the only supported operator action to free a slot**. Engine admission transactionally retires revoked, expired or missing grant readers; automatic terminal expiry is not a manual capacity-management API. Disable, pause, token rotation or abandoning a client does not free a live slot; no eviction of live custody.
- Two snapshots per subscription, at most 96 observations and 16 MiB each; one-hour snapshot lifetime. Page limit 1–50 snapshot positions and 192 KiB **engine** serialized result. The final public/core framing must also be measured and bounded; adding provenance/schema fields cannot silently overrun that limit.
- 256 outstanding sparse refs, including sparse acknowledgments. Pending observations survive projection changes and snapshot expiry.
- 128 receipt slots shared by reservations and outcomes. Unused standalone reservations last 24 hours; committed outcomes last one hour after commit or the issuing snapshot's saved expiry, whichever is later. Identical retries do not extend committed receipts.
- Pull freezes a lowest ordered prefix. A limited snapshot has `complete:false`, retry `pull_after_ack`; null continuation finishes that snapshot only. Ack represented pages, then issue a new pull to obtain later eligible observations.
- Thread starts at the newest bounded tail window, ascending within a window; a terminal continuation requests an independently frozen older window. A limited window has `thread_continue`. Windows are not one history-wide simultaneous snapshot.
- Expired/forged/wrong-operation/anchor/visibility/manifest/generation continuations refuse; never silently restart. Reads issue refs but never implicitly ack. Oversized items refuse rather than disappear.
- These are materialization/custody bounds, not constant SQL work or a hard latency guarantee. Large one-row pages can exhaust receipt throughput at roughly 128 rows/hour with no other pressure; retained outcomes cannot be evicted to advertise unlimited catch-up.

No inferred default domain; no placement, grant expansion, cursor import or intake repair. Identical enable is idempotent; conflicting binding refuses. ### 3.2 Scoped v2 commands and MCP tools

All six raw tools require **`mail:read`**, not `fleet:read` and not `captain:presence`. There is no narrower existing mail-delivery scope; do not add a new scope or expand any grant implicitly. Coverage under `mail:read` uses only opaque visible source handles, not inventory. Optional inventory remains `fleet:read` and is not needed in this milestone.

| MCP tool | Core command | Arguments |
| --- | --- | --- |
| `desk_subscription_open` | `desk.subscription.open` | `{}`; domain comes exclusively from operator configuration. Opens or returns this door/grant's durable reader; no ack. |
| `desk_subscription_resume` | `desk.subscription.resume` | `{subscription}`; recovers state and durable snapshot start tokens, never accepts a cursor. |
| `desk_subscription_pull` | `desk.subscription.pull` | `{subscription, limit?, continuation?}`; default limit 50. Returns authorized eligible projection/pending observations under the recorded replay policy, potentially including outgoing captain conversations; never bulk older history under the recommended policy. |
| `desk_subscription_show` | `desk.subscription.show` | `{subscription, origin}`; exact retained authorized origin lookup, no implicit ack. |
| `desk_subscription_thread` | `desk.subscription.thread` | `{subscription, origin, limit?, continuation?}`; origin is an exact known retained thread anchor (for example from a previously served result), not a history-enumeration selector; authorize it independently, with engine window semantics. |
| `desk_subscription_ack` | `desk.subscription.ack` | `{subscription, ack_key, refs}`; all required. Server-issued batch key and actually carried raw refs only. |

`subscription` is an opaque UUID handle, not authority. `origin` is the closed `{core, mailbox, id}` identity already used by the engine: canonical UUIDs for core and mailbox, and the runtime's validated mail identifier. Never interpret core as an RPC destination. `limit` is an integer 1–50; continuation is a nonempty opaque string capped at 256 bytes. `ack_key` and each ref are nonempty opaque ASCII strings capped at 64 bytes; refs has 1–256 entries, with core sorting/deduplication before whole-batch validation. UUID handles have a 36-character canonical format. Mail IDs and operator door/domain identifiers use the existing core identifier rule: 1–160 ASCII letters, digits or `-_.:@`; mirror that length and character rule in the MCP schema.

Do **not** call the server-issued key `idempotency_key`: scoped admission currently strips that field into the generic write replay layer. The desk ledger already owns ack replay. No second receipt cache, client-generated key substitute, cross-generation translation or implicit ack retry. A page key binds one normalized batch: if selecting only part of a page, use a new server key from open/resume for a later distinct batch. Explain this in tool descriptions.

Successful public payloads use `schema:"desk.subscription.v1"`, `subscription`, `incarnation`, and `coverage`. Open/resume return `ack_key` and bounded `pending_snapshots:[{operation,anchor,continuation}]`. Page operations return `items:[{ref,origin,mail,state,delivery_class}]`, `continuation` (string or null) and `ack_key`. Every item explicitly renders its authoritative open/closed state, or `unknown` when no lifecycle state is proved; never infer closed from a raw ack. Add a core-authored `delivery_class:"history"|"since_switch_on"|"unknown"`: old open requests and any replayed older mail are labelled **history**, not “new” or “unread”. This is independent of request state and this reader's raw ack state. Ack returns `acknowledged` and `operation_complete:true`; input domain coverage is still separately dated/possibly incomplete. Core provenance is runtime-authored. The final serialized public payload, including that wrapper and provenance, must fit 192 KiB; reserve wrapper space before engine serving rather than reject an already committed page as oversized afterward. MCP transport framing has its own separately bounded overhead. Do not claim a raw ack closes a request, acknowledges the dashboard, or delivers any digest.

Each call, including open/resume/continuation/ack, resolves the actual bearer credential; the engine then verifies exact current local grant authority in its writer transaction. Recheck the credential, visibility revision and exposure binding before returning any protected result. No cached grant authority, unattended polling or SSE push. A revoke committed before engine admission prevents serving/ack changes; one committed after admission may hide the response but cannot undo committed served rows or acks. Release loss after an ack is `outcome_unknown`, not proof that nothing changed. Retry only the identical key/batch while retained.

### 3.3 Discovery, rendering and refusals

Extend scoped `capabilities` with a versioned, safe desk feature descriptor only for an enabled, admitted mail reader. Proposed shape: `desk_subscriptions:{schema:"desk.subscription-capability.v1",mode:"local_raw",operations:["open","resume","pull","show","thread","ack"],remote_owner:false,moves:false,waiting:false,presence:false,digests:false}`. It reveals no placement/domain or source inventory. A feature descriptor is not stored authority: every tool call repeats core admission. Tools/list filters by **both** `mail:read` and the descriptor. Hidden/non-enabled tools remain non-disclosing not-found on guessing; authentication failures retain normal OAuth challenges. Trusted v1 cannot acquire these commands by announcing v2.

Do not flip the legacy/global `subscriptions:false` diagnostic to an unqualified true. Keep selected-mailbox/local diagnostics scoped to their old surfaces; add the new qualified feature separately. Availability failures do not remove the operator's recorded opt-in or switch mail tools.

Preserve `coverage.v1` on every admitted new result, including failures, or use a closed non-disclosing refusal when coverage cannot safely be established. Snapshot coverage is frozen and dated, not recomputed as current on continuation. Render:

- `scope:"desk-domain"`, domain, visible opaque sources, source states/checkpoints, observation time, snapshot and allowed owner/revision fields exactly as admitted. Named-ship readers retain `complete:false`, null owner/revision and no hidden counts/topology.
- “As of last source contacts,” showing each available barrier mode, desk-measured `received_at`, `age_ms`, and the operator's `max_source_age_ms` (default 900000). Even collect/local barriers here are dated evidence; a pull creates no on-demand contact. Replay/import cannot refresh freshness.
- Omissions and history/unreadable/backpressure/unsupported gaps, and each retry action. Empty partial results say coverage is incomplete, never “nothing needs you.” Missing/malformed coverage stays incomplete; Python cannot manufacture proof.
- Continuation and `pull_after_ack`/`thread_continue` instructions separately from `coverage.complete`. A complete source vector does not mean drained inbox, exhausted history or completed work.

The bridge must normalize the internal engine's string-error envelope into a closed public error object **without losing coverage**. The current adapter's generic not-found collapse is insufficient. Proposed public error schema is `{code, message}` with optional allowlisted value-free `retry`/`hint`, alongside `coverage` when safe; no raw exception text. Preserve these outcomes:

| Condition | Admitted client result | Operator detail / recovery boundary |
| --- | --- | --- |
| No active placement, pending acceptance or restore mismatch | `unavailable`, incomplete/unknown-domain coverage; no inferred mailbox | Preserve distinct typed internal `no_placement`, `placement_pending` and `restore_guard` outcomes, not string matching or a generic internal unavailable. Restore needs exact certified recovery, never re-bootstrap. Unknown and wholly hidden domains have the same client refusal. |
| Owner is remote, including callable remote owner | `unavailable` with fixed wording **“unsupported read direction / incomplete feature”** where safe; no local fallback | Distinct internal `remote_owner`; local-owner exposure only, remote-owner admission/transport remains missing. ### 3.5 Replay selection — captain choice B DECIDED (2026-10-31, `fb595ad0`, option a)

Opening from zero today freezes `(origin core, mailbox, source order, mail ID)`, not a fleet-wide newest-first feed. Up to roughly 10,000 retained history rows per source can sit before current mail; one source/mailbox's history can delay the next source. Pulling through that backlog can disclose **all retained captain conversations, including outgoing mail, to the hosted client/provider**. Independent progress is not informed consent to that bulk disclosure. Receipt throughput makes this a practical delay as well as a privacy choice.

**Approved policy: `open_and_new` — open requests plus mail from switch-on; older mail only by explicit bounded thread lookup, never bulk.** The captain did not select `all_history` (bulk backlog/disclosure) or `new_only` (excluding older open requests). The operator records the approved policy; a grant cannot select or change it. Existing `fresh_replay` names independent reader creation, not a requirement to stream all history.

The recommended policy needs a small additive engine eligibility layer before exposure; an adapter-side filter is insufficient because it would consume refs/receipts and still send old bodies to the adapter:

- Persist a durable switch-on boundary/vector and replay policy with the exposure/reader state; do not use the dashboard cursor or client timestamps. Use source journal order and proved enrollment/barrier evidence, not remote wall clocks, to classify baseline/history versus subsequent mail. The switch-on vector is dated source evidence, not a simultaneous remote instant; disclose each source boundary. A source lacking a proved baseline is `switch_on_pending`, not evidence that late baseline rows are new. Preserve this conservative state across restart until its boundary is established via existing legal intake, without inventing a reverse contact.
- Filter automatic pull **inside** the engine/projection selector before snapshot/ref admission: carry old open requests (including decisions) and eligible subsequent mail, retaining displaced pending versions and closure facts even if a request closes before the client acks it. Persist an eligibility pin for an offered old open request so a later closure is delivered rather than silently withdrawing custody. A closure/ack observation that gives old mail a newer `source_order` must not reclassify its original content as new; retain original-mail/baseline classification alongside mutable observation order where necessary. Late baseline/copy arrival is history, never a new-mail heuristic based on arrival time.
- Maintain eligibility-aware prefix compaction; intentional exclusion from **this** automatic stream is neither a raw ack nor deletion of historical facts. Exact older thread lookup uses an authorized anchor and existing bounded windows, labels every result history and never changes pull eligibility/progress implicitly. Under this policy, `show` is for already eligible/carried origins; it must not become an arbitrary bulk-old-mail enumeration escape hatch. There is no older-history list/pull endpoint. Scope restrictions still apply to lookup and coverage.
- Test old open/closed/outgoing mail, current mail behind a large baseline, late source enrollment, baseline/delta and closure races, lost page/ack, restart, restriction replay and historical thread windows. Policy resets or visibility changes cannot move switch-on forward and suppress pending facts, or label replay “new”. Report policy exclusion separately from missing-source coverage; it does not make historical retention or current coverage complete.

This changes delivery selection, not intake's required retained-history capture, origin identity, topology or request lifecycle. Precisely tracking original-mail versus later lifecycle observations may require a small additive ledger/projection field and schema fixture update; if that outgrows a small engine PR, report the split before implementing. No all-history replay is authorized by choice B.

**PR 4 split (engineering decision, 2026-10-31):** PR 4a is an additive evidence foundation only: `desk_intake_original` preserves an origin's first-applied source journal order atomically with its first projected content; legacy origins are deliberately not backfilled, even after lifecycle/ack updates. `desk_subscription_replay` copies the validated operator binding (including policy and dated switch-on vector) once at reader creation, independent of visibility incarnation. Missing legacy bindings remain unknown; disable, re-enable, restart and restriction replay never recapture the boundary. The internal classifier proves `history` only at/below an established source boundary. **First application above that boundary does not prove `since_switch_on`: late baseline/copy imports can append old content at newer journal orders. These observations, pending sources and legacy evidence remain `unknown`.** PR 4a does not filter pull, change show/thread/ack semantics, resolve pending boundaries or add public item labels. PR 4b must not activate `open_and_new` selection until a content-origin predicate is settled, then implements the remaining selector/pins/compaction/item-semantics contract. Deploying PR 4a bumps the door schema marker from v2 to v3; upgrade is additive and retains grants/readers/refs. Rollback to an older binary needs care: it does not maintain this evidence, so rows created or changed under that binary must not be assumed to have proved original-content age.

Read-only PR 4b design finding: existing `reconcile.rs::HomeProof` already carries opaque home, mailbox, enrollment nonce, `baseline_upper` and `delta_upper`; `home_proof` withholds readiness until frozen-baseline and delta imports are receipted. `proof.rs::Evidence` binds that census to an intake checkpoint; `completion.rs::snapshot` checks its validity before source coverage. This can support conservatively pending new/unproved homes and a later history boundary, without contact reversal. **As-is it is not a per-origin birth predicate**: the home uppers are not source journal sequence ranges, while `home.rs::import_one`/`resolved` flatten baseline and live observations (including same-source copies) into the same `Fact` appended by `append_in`. `Fact`/`Event` carry no baseline/live provenance. Merely using a later whole-source barrier cannot relabel earlier replay as new or safely distinguish a late copy into an already known mailbox. A no-Fact-wire-change approach would need a proved, durable mapping from home/nonce baseline completion to source journal ranges or exact origins, plus race/restart/copy tests and conservative unknown for missing evidence. A versioned optional proof-sidecar extension may carry that mapping without altering strict intake frames; it still needs protocol/old-peer review. Alternatively, source/home-authored per-origin baseline/live provenance would need persistence before append and explicit version negotiation because existing `Fact`/`Event` reject unknown fields. Neither approach is implemented or selected by PR 4a.

#### 3.5.1 PR 4b predicate proposal — DESIGN ONLY, awaiting engineering review

**Do not activate selection on the strength of baseline ranges alone.** A range proves where an observation was imported, not when its content originated. The proposed implementation uses an optional, independently versioned **replay-proof sidecar**, retaining the existing census/coverage sidecar unchanged. It combines a home/enrollment-to-journal mapping with a positive native-origin witness. No `Fact`, `Event`, `HomeFact` or strict intake page wire change is proposed. Linked-source assertions remain bookkeeping under the existing linked-operator trust, not cryptographic birth certificates.

Use these distinct orders; never compare one namespace with another:

- `J`: source registry journal order, including lifecycle and copy observations.
- `D`: a home's outbox order, scoped to its published enrollment nonce.
- `M`: a home's native `mail.seq` insertion order, scoped to its mailbox incarnation. The home's `mail` AUTOINCREMENT high-water, not its maximum surviving row, is the cut. Pruning must not lower it.

The source records an additive import ledger keyed by manifest binding, source, opaque home handle, mailbox and enrollment nonce. For each committed import it records its journal order, stable intent and immutable-content digest, whether it came from the frozen baseline or delta lane, and whether its provenance is **native** (`Provenance::Origin` exactly equal to this source/home mailbox/mail ID) or a copy/unresolved assertion. Baseline journal spans may be coalesced only across contiguous orders with identical binding/home/nonce/lane. They are not a single min/max interval that sweeps in interleaved imports. A native delta witness also carries the exact origin and its home insertion order `M`, read from the same consistent home snapshot as the pending intent and checked against pinned provenance/content. If the row is missing, mismatched, already an alias, or cannot be checked within budget, there is **no positive witness**. Never infer native provenance from the flattened `Fact.copy == None`: a same-source copy can flatten to that shape.

Baseline imports need only negative/history evidence. Positive witnesses are exact origin/order/digest records; do not claim every event outside baseline spans is native. The ledger/witness and journal append/registry receipt commit in the **same registry transaction**. A crash before the home records its receipt retries the same evidence; an already receipted legacy import cannot acquire a positive witness retroactively. Keep original-content evidence independent of mutable lifecycle order and receipt/log reclamation. Both local-owner intake and remote intake use this same predicate.

#### 3.5.2 Immutable cuts and the positive test

Retain PR 4a's immutable exposure/reader binding and original-content order. Add companion cut records keyed by its binding hash, not by a visibility incarnation. A replay cut is an accepted, fully imported checkpoint plus the exact validated home vector: `(home, mailbox, nonce, baseline_upper_D, delta_upper_D, mail_high_water_M)` and the baseline journal spans it covers. A home read binds these fields in one snapshot. Source reconciliation rechecks the inventory, nonce/publication, delta head, loss state and registry import-ledger revision before issuance. The receiver checks the exact manifest/checkpoint, source membership, completed page custody, all orders/digests against retained authoritative origins, and sidecar bounds before adopting evidence. A later checkpoint with a different home vector cannot be substituted for the saved cut.

At enable, copy usable replay cuts atomically alongside the existing dated switch-on vector. Existing PR 4a `established` coverage evidence is **not** automatically an established replay cut: it lacks the new home/birth mapping. A source/home without a usable cut remains `switch_on_pending` for replay. On an existing legal intake contact it may adopt its **first** usable, fully imported cut, once only. This conservative delayed cut includes everything through its baseline and delta vector as pre-cut history; it does not backdate newness to enable time or move an already established cut. Record and disclose the delayed cut and the unproved interval separately from the original switch-on vector. New content in that interval may be withheld unless open; never silently claim complete from-switch-on delivery. A late home or new enrollment nonce likewise needs its own first cut. Reads themselves do not create contacts or re-enroll homes.

For an authorized observation of origin `o`, evaluate in this order:

1. **History:** PR 4a already proves original content at/below the saved source boundary; or accepted frozen-baseline evidence proves this exact original content; or a validated delayed home cut proves it pre-cut. Lifecycle/copy order never overwrites that content-age result. Delayed-cut history means pre-effective-cut, not proof of a wall-clock creation time.
2. **Since switch-on:** require an established cut for the **same** binding/home/mailbox/nonce, PR 4a first-applied order `J0` strictly above that cut's source journal upper, and a validated **native delta witness for that exact first-applied content/order**, with `D > cut.delta_upper_D` and `M > cut.mail_high_water_M`. Here `D` is the retained outbox order found by stable intent, never the differently numbered `mail_source_import.seq`. No legacy first-order backfill, copy-only witness, source gap/loss, conflicting content or stale enrollment may supply this proof.
3. **Unknown:** everything else. A later closure, raw ack, fresh contact, matching body or higher `J` cannot manufacture birth proof.

Why step 2 is positive evidence: all retained captain content and all deltas through the cut were receipted; the insertion high-water also covers old native rows subsequently pruned. An unchanged mailbox/nonce's native insertion beyond that high-water, observed beyond the cut's delta head, is not an old retained request receiving a new lifecycle observation. Copies have no native witness, irrespective of arrival lane or whether the origin was already projected. The conclusion is **after the disclosed per-home vector cut**, not a simultaneous remote wall-clock switch-on instant. That is the dated-vector contract above, with conservative delayed-cut omissions made explicit.

#### 3.5.3 Late arrivals, restart and restore

| Case | Required result |
| --- | --- |
| Late frozen home baseline above the source boundary | Its mapped baseline content is history, never live; home stays replay-pending until its full cut is accepted. Deltas before that delayed cut are not relabelled since-switch-on. |
| Late same-source copy of a known origin | Alias/lifecycle evidence cannot replace the origin's original-content classification. Native witness must belong to the first authoritative content, not this copy. |
| Late copy of an unknown origin, including outside the manifest | Unknown unless separately proved history; never since-switch-on merely because it arrived in the delta lane or above `J0`. Preserve copy/integrity coverage obstacles. |
| Old request closes after the cut | Native home insertion order is at/below the cut even if its latest delta/journal order is higher. It stays history (or unknown without proof); offered-open custody separately requires its closure. |
| Home re-enrollment, mailbox move or nonce change | No reuse of old live ranges/cut. Establish a conservative cut for the new tuple; keep old classification/custody and reject conflicting reinterpretation. A returning old tuple cannot reset its cut. |
| Crash at any import/receipt/proof/cut commit boundary | Atomic registry evidence or no evidence; immutable intent retries. No boundary recapture on restart, disable/re-enable, token rotation or restriction replay. |
| Source/home changes during reconciliation or proof issuance | Revision/nonce/head revalidation fails; omit replay proof while normal pages/receipts retain custody. Do not publish a partly validated vector or use cached home counts as birth proof. |
| Home restore, stale sidecar, regressed heads or conflicting reused intent | Fail closed for affected positive proof; report pending/integrity/restore detail. Old insertion orders cannot become new merely through journal reappend. A changed nonce needs a new cut, not old ranges. |
| Registry/placement restore | Existing external owner fence remains mandatory. Restored cuts/progress cannot reopen service against a mismatched guard. No recovery, reset or placement action is added here. |

This does **not** solve undetectable stale clones or arbitrary uncoordinated home restores that preserve every identity. Preserve [coverage §4's stopped-writer backup/restore prerequisites](door-mail-coverage.md#4-migration-and-local-only-compatibility); do not advertise the sidecar as a restore detector. Detected evidence loss or any missing witness is unknown, never a reason to reconstruct positive evidence from mutable projection rows. Persisted immutable evidence can retain a historical classification; absent *current* source proof cannot refresh source freshness or establish new witnesses.

#### 3.5.5 Selection and item semantics in PR 4b-2

For an enabled `open_and_new` binding, automatic selection is **authorized AND (proved since-switch-on OR authoritative open OR carried eligibility pin/pending version)**. Unknown closed/unclassified notices and outgoing mail, and known closed older history, are excluded before retained snapshot positions, serialized bodies, refs or receipts are allocated. Unknown **open** requests are intentionally included as the approved open-request exception, labelled unknown, not new. Unknown alone is never bulk-replay consent. A partial empty pull must name the replay-proof omission as well as any source-coverage omission.

Offering an old/unknown open origin pins that origin and its original classification in the same transaction as durable snapshot custody, even if output is lost. Pins carry subsequent authoritative closure observations and displaced pending versions; closing before ack cannot withdraw them. Pins do not arise merely from scanning an open row, or from history lookup. Retire only when the relevant carried observations/closure are acknowledged under the ordinary bounded ledger, never on snapshot expiry alone. Newer evidence must not change the labels of an already frozen page. Item `state` comes from the authoritative origin lifecycle (`open`, `closed`, otherwise `unknown`); raw ack never closes it.

Compaction must distinguish **actually acknowledged eligible observations**, **intentional policy exclusion**, and **temporarily unproved eligibility**. Do not simply call the existing `source_order <= through_order` check after skipping unknown rows: delayed proof could make an earlier skipped origin eligible. Use bounded durable exclusion spans plus a proof-revision/revisit watermark, separate from raw acknowledgments. Before committing a proof revision as consumed, revisit affected skipped spans and pin newly eligible origins as exceptions to the compacted prefix, transactionally. If exception capacity is exhausted, retain the revisit work and backpressure; never lose newly proved eligibility or fabricate an ack. Ineligible rows consume neither delivery refs nor receipt slots; acknowledged eligible refs may compact past them only while that revisit evidence remains durable. No unbounded per-history tombstone set. Tests must demonstrate that proof arriving after compaction cannot hide current mail, and that repeated proof cannot resurrect an actually acknowledged version. If a bounded representation cannot maintain these invariants, stop and revise the design rather than drop unknown content behind an irreversible prefix.

Exact `show` requires an independently authorized **eligible or already carried** origin; no arbitrary-old-origin enumeration through guessed IDs. `thread` still requires an independently authorized, exact retained anchor and bounded frozen windows, never a list/history selector. Thread pages are explicitly `delivery_class:"history"` (historical retrieval context), with independently proved lifecycle state; they do not relabel any automatic-stream evidence. History refs/receipts have an explicit operation kind. A history read **or its explicit ack** must not create automatic eligibility pins, advance its prefix, satisfy an automatic pending version or trigger its compaction; independently carried automatic refs retain their custody even for the same origin. History lookup remains permitted without a newness witness, within authorization and retention bounds.

Visibility changes retain the immutable binding/cuts but reauthorize all origins, pins, skipped-span diagnostics and responses. Existing continuation/ref incarnation fences still apply; no hidden body, origin, count or topology may escape through pending/policy diagnostics. A widened grant may replay newly visible eligible facts, never recapture switch-on or label history as new. Narrowing visibility must not silently acknowledge durable facts or erase origin evidence needed on a later authorized replay.

Diagnostics need a separate core-authored replay-selection object (policy, effective dated cuts/pending state, history exclusion, unknown-proof withholding, bounded-work/backpressure and retry), not synthetic missing-source entries. Source `coverage.v1` continues to mean dated intake coverage: policy exclusion cannot make it complete, nor does intentional history exclusion make a fully covered source missing. Conversely, complete source coverage with missing replay proof is not a complete automatic stream. Freeze both diagnostics with the snapshot; sanitize by current visibility, withholding hidden counts just as coverage does. No client renderer or provider infers these labels.
