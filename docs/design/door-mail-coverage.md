# Door mail coverage and desk-generation handoff

## Status and recommendation

Design for [#452 phase 2.4](mcp-front-door.md#9-phased-delivery-plan-prs-and-evidence), part C. **Implementation status: PR 1 (coverage/identity), PR 2a (initial placement) and PR 2b-i (dormant journal, #507) are implemented. PR 2b-ii hardens that journal but leaves it dormant. PR 2b-iii adds source-home capture and writable-startup schema installation. PR 2b-iv(a) activates bounded optional intake frames on legal collect/push contacts, with conservative `complete:false`; PR 2b-iv(b1) adds conservative acknowledged-log/import-proof retention, periodic empty push barriers and transport corrections; PR 2b-iv(b2a) moves baseline enrollment to bounded off-contact idle work; PR 2b-iv(b2b-i) adds bounded retained-home reconciliation evidence and optional explicit copy-provenance transport; PR 2b-iv(b2b-ii-a) adds optional barrier-bound vector evidence and conservative revalidation; PR 2b-iv(b2b-ii-b) derives source-only completion from that proof plus fenced placement, availability and desk-clock freshness, with a real-subprocess source matrix. No aggregate fleet subscription is complete or exposed.** The design extends the required subscription contract in [MCP front door §5](mcp-front-door.md#5-cross-machine-mail-away-routing-and-duplicate-policy); the older “current behavior after #454” subsection is not the complete v2 implementation baseline.

Recommend **desk-owned subscriptions**, served by the desk core to a configured, operator-trusted door-host core. Keep selected-mailbox reads as a separate surface. Add explicit source coverage and a fenced, generation-changing desk handoff. Do not move the desk when starting a door, infer reachability from a ship directory, or turn a failed remote read into a successful local read. In this phase reverse-only selected-mailbox readers report `complete:false`, `state:"unavailable"`, `retry:"reverse_only"` and a closed, value-free `coverage.hint`; there is no reverse-reader spool. The hint explains that this machine cannot read the other machine's mailbox directly, sends still deliver on collection, and the supported alternatives are an already-held local copy or a door on a machine with a callable link to the holder and a valid grant. Retrying here is not a remedy. Neither alternative creates a new read route or proves fleet completeness. The captain's decisions on the open points are recorded in §7.

Examples use machines `alpha`, `beta` and `gamma`, and ships `survey` and `relay`; these are fictional. “Fleet” below means an explicit configured coverage domain, filtered by the admitted grant, not discovery of arbitrary machines. “Owner” means the core authorized to mutate the desk stream, not an adapter, grant or ship.

## 1. Today's model: storage, direction and visible gaps

### Mail and links

- A ship's captain request and its open/closed state originate in that ship's home. Copies can exist in a local captain home and on another machine; a copy's mailbox sequence is not the original's sequence. `captain::waiting_visible()` enumerates local active homes and filters both holding home and sender under delegated visibility. See [captain.rs](../../src/captain.rs), `fleet`, `waiting_visible`, `held_here`, and `with_local_asks`.
- A configured link is **one-way callable**: `alpha -> beta` means `alpha` records role `collects` and can call `beta`'s gateway; `beta` records `collected` and cannot initiate a call back. The request and response both carry data, but that does not create a reverse connection. The directory is cached inventory, not a callable route. See [machine-link architecture](../architecture.md#linked-machines), and [machines.rs](../../src/machines.rs), `Machine`, `collect`, gateway `fleet.collect`/`fleet.collected`.
- `alpha` periodically collects pending ship mail and eligible captain mail from `beta`, delivers by stable mail ID, then acknowledges accepted/refused deliveries. A crash before acknowledgment can repeat a copy. Captain mail normally starts at link creation; older captain history is not automatically copied. `captain_destination()` puts a correlated answer in a local home holding its ask, otherwise in `captain_home()` (liaison, else first ship). Unknown destinations can wait and eventually produce a visible refusal.
- By default the linking machine collects captain mail from the reached machine. `machine captain beta` on `alpha` instead records a local `captain_desk(machine,set_ms)` choice. `collect()` requests `captain:false`, withholding general captain mail but still receiving `answering_origin` replies and notices correlated to captain requests sent from `alpha`. The gateway also withholds general captain mail if its own explicit placement names a different desk, even when the collector requests it (`fleet.collect`, `wants_captain`/`answering_origin`). `push_captain()` sends captain mail since that choice **plus still-open older requests/decisions**, then closures, using `fleet.captain`. Accepted/refused records prevent repeated transfer; unreadable homes are skipped and retried. Closed older asks and older notices are not a complete history handoff. See `set_desk`, `push_captain`, `push_messages`, `push_closures`, and `mail::awaiting_captain` in [mail.rs](../../src/mail.rs).
- There is no general captain-mail relay through a third machine. A source must be linked and placed toward its desk itself. `holds_desk()` also infers a desk from a `collected` link when no explicit placement exists; several such links can be ambiguous. A local placement command is not agreement by both machines: setting `beta` on `alpha` can leave `beta` inferring that `alpha` owns its desk. `desk_here()` and scoped `desk.v1` then refuse execution. No durable shared generation or transfer certificate resolves this today.

### CLI and door reads are different

[Captain dispatch](../../src/captain.rs), `dispatch`, routes the operator's `captain.waiting` and `captain.feed` to an explicitly remote desk; waiting adds local-only asks. Replies/dismissals stay local when `held_here()` finds the item. As changed for #481, `captain.send` to a locally hosted ship stays in that ship's home even when the desk is elsewhere (the desk may not reach back). Other sends use the desk's routes. Consequently the remote desk feed is **not** a record of every local outgoing send. Gateway captain operations execute against their own homes, never recursively forward. See also the captain-desk paragraph in [architecture.md](../architecture.md).

[Trusted v1 doors](../../src/door.rs) poll local homes, including copies already collected there. `cursor()` persists a per-door/per-home `door_cursor`, initialized from the captain's acknowledged position; `Session::carried` bounds session acknowledgments. Digest acknowledgments require an emitted digest. Door acknowledgments neither acknowledge the dashboard nor another door. `Session::waiting()` calls the local helper, not the desk-routing CLI wrapper. `door_mail_delivery()` in [machines.rs](../../src/machines.rs) only reports topology; it contacts nobody and cannot collect or repair coverage.

The newer scoped v2 baseline is more capable, but not a fleet subscription:

| Surface | Actual coverage and state |
| --- | --- |
| `inbox`, `show`, `thread`, mailbox `ack` | [reader_link.rs](../../src/door/reader_link.rs) selects one local or directory-routed linked mailbox. [machines/reader.rs](../../src/machines/reader.rs) calls `fleet.reader.v1` only through a `collects` link. Reverse-only, unsupported and failed peers return incomplete selected-mailbox coverage; there is no reverse reader queue. |
| Local reader state | [reader.rs](../../src/door/reader.rs) persists machine identity, mailbox incarnation UUID, per-client/resource/mailbox generation and contiguous cursor, sparse served refs, and snapshot-bound continuation tokens. Transactions validate a whole ack batch before changes. Only actually served refs can advance an authorized contiguous prefix. |
| Copy suppression | `copies`, `copy_known` and `compact` prove copies from allowed active **local** homes and their reader cursors/served rows. This is not cross-machine reader deduplication. Grant/client identity on a peer is namespaced by the originating core UUID via `reader_context()`. |
| `waiting`, `status` | [delegated.rs](../../src/door/delegated.rs) reads visible local homes and returns conservative `mail_delivery` wording, hiding operator-only topology. No remote waiting aggregation. |
| Scoped away, held, digest and digest ack | [desk.rs](../../src/door/desk.rs) uses `delegated_desk_call()` and `fleet.delegated.v1` / `desk.v1`. It refuses ambiguous, reverse-only or failed desk routes instead of mutating local fallback state. A receiving gateway verifies `desk_here()` and executes locally only. |
| Digest inputs | [digest.rs](../../src/digest.rs), `collect_visible`/`build_visible`/`delegated`, uses the desk's local stores and registry; already collected copies can participate. It does not query uncollected remote homes. A successful desk operation or digest ack is not evidence those inputs cover the fleet. |

Current reader bounds include a 256-record sparse window, 32 continuation records per client/resource, 24-hour continuation expiry and a 512 KiB page-body budget; tool limits cap pages at 50 items. These are existing implementation facts, not proposed unbounded history retention.

[plugins/mcp/tools.py](../../plugins/mcp/tools.py), `MAIL_COVERAGE`, `mail_inbox` and `fleet_waiting`, explicitly says selected-mailbox coverage is not fleet coverage and waiting is not a fleet-wide all-clear (#476). Preserve that wording until stronger behavior actually ships. The diagnostic `subscriptions:false` does not mean linked selected-mailbox reads are impossible.

### Replying to carried asks

A selected-mailbox thread may show a carried captain ask from another ship.
The MCP `reply` tool still sends to the door's normal recipient; it has no `to`
argument. Native authenticated reply binds the exact stored ask to its sender
and recipient. A copy does not transfer that ownership. When a visible open
captain ask fails native sending because this mailbox's recipient differs from
the ask's sender, a grant with `mail:read` receives `reply_wrong_mailbox` and a
fixed action: use a door whose normal recipient is the ship that sent the original
ask, with a grant allowing it. No reply is sent or ask closed. Unknown, hidden,
stale and typed authorization/approval failures keep their existing refusals;
there is no search for an owner, automatic reroute or copy answering for it.

### Concrete non-desk cases

For `alpha -> beta`, a door on `beta` while the desk is `alpha` sees captain mail held on `beta`, but cannot pull `alpha`'s desk or collect from `alpha`. A scoped send may queue for reverse collection; that is not a reader transport. A door on `alpha` with an agreed desk on `beta` can read a selected `beta` mailbox and route scoped presence there, but still lacks an aggregate subscription to all desk-held and source-held mail. In either direction it can miss uncollected remote notices, older history left behind at a placement change, and local-only outgoing sends on another machine. Neither inventory nor successful sends closes these gaps.

## 2. Options

| | (a) Desk-owned subscriptions | (b) Door-side collection |
| --- | --- | --- |
| Correctness | One owner for reader delivery, held classification, digests and catch-up. Complete only if source coverage is proved; desk location alone is insufficient. | Can inspect reachable sources that the desk has not collected. Must merge copies, closures, cursor namespaces and concurrent placement changes itself. Merely pulling the desk's current homes has the same input gaps as (a). |
| Failure modes | Desk outage blocks fresh subscription data/presence. Source outages leave explicit gaps. Lost responses replay durable refs. Handoff must fence the old owner. | Door can show partial reachable mail during desk outage, but cannot invent authoritative away/digest state. Different doors can silently disagree unless each reports an identical coverage model. Restart needs a durable merge journal per host. |
| Complexity | Shared desk journal, source checkpoints, per-door/grant readers, delegated RPC, handoff and coverage accounting. Reuses a single presence owner. | Distributed per-host merge/deduplication and source cursors, plus desk routing anyway for presence. More copies of sensitive mail and more recovery states. A full solution converges toward a desk service plus host caches. |
| Link needs | Door host must reach desk for synchronous pull; sources must reach desk or desk reach sources for ingestion. | Host must reach every source it claims to cover, or receive a separately designed reverse transport. Reaching only one peer never proves a whole domain. |

**Reverse-only impossibility:** if only `alpha -> beta` exists, `beta` cannot synchronously read `alpha`, whether `alpha` is desk or source. It may receive data in the response/request of `alpha`'s next poll, but only if a new protocol explicitly carries it. Configuring a route, tunnel, desk move or operator fallback is not a reader's authority.

A future bounded reverse request/reply spool could let `alpha` poll requests queued on `beta`, execute at `alpha`, and return results on another contact. That is asynchronous, needs fresh grant admission before each protected page, durable correlation/expiry/cancel semantics and separate tests. Existing reverse-send collection cannot be repurposed as proof of these properties. **This phase builds no such transport** (decision 1, §7): a reverse-only reader reports `reverse_only` partial or unavailable coverage with retry/remediation, while already received data can be displayed as dated partial data. In the usual setup, with the door on reached `beta` and the desk on `alpha`, that means unavailable; full coverage there needs an agreed desk on `beta` (§3.2). If `alpha` does not poll, neither option can promise fresh data on `beta`.

## 3. Recommended protocol

### 3.1 Authority and identities

Implement a versioned core-to-core `fleet.door-mail.v1` envelope, negotiated independently of `fleet.reader.v1` and `desk.v1`. Names below are proposed operations, not today's API. The plugin supplies only its normal permitted request arguments; it cannot supply peers, owner identities, raw SQL, paths, grants or provenance.

**Trust boundary (decision 3, §7):** linked machines share operator trust. This design adds no per-origin authentication. The callable transport authenticates access to the remote operator gateway; its `machine` argument and reader `origin` UUID are self-asserted. A linked caller can already invoke operator `captain.reply`/`captain.dismiss`. A second collector with gateway access can impersonate another origin's reader, obtain or forge its acks, forge a placement acceptance and fabricate coverage; random refs and delegated scopes do not defend against that operator-trusted peer. This design does not isolate mutually untrusted linked machines. Per-link origin credentials and gateway confinement would need their own design.

A protected envelope binds protocol version, initiating core ID, request/idempotency ID, destination desk ID and expected generation/incarnation, registered door identity/resource, reader identity, operation, arguments and core-resolved delegated context. Under the shared-trust assumption the receiver checks configured participant/placement records and context consistency, but a caller-supplied UUID is still not authenticated origin proof. No gateway follows an arbitrary forwarded route. A generation mismatch yields a checked owner hint, never an automatic operator retry.

A v2 reader key is `(origin_core, registered_door, resource, grant_id)`; tokens of the same grant share it. Different grants and doors remain independent even for one application. Trusted v1 readers use their registered trust record and door identity, not a forged v2 grant or external Full Captain assertion. Keep authoritative provenance separate from internal namespaced storage keys, as [DelegatedContext](../../src/door/scoped.rs) does today.

| Operation | Authority and bounds |
| --- | --- |
| `coverage` / `open` / `resume` | `mail:read`; derives subscription/reader identity from admitted context. Returns only allowed coverage, creates or resumes bounded reader state, never acknowledges mail or changes placement. Fleet inventory/waiting metadata requires `fleet:read`; if it includes mail bodies, also require `mail:read`. |
| `pull` / `show` / `thread` | `mail:read`; filter both conversation participants and source visibility under the current ship restriction, including desk copies. No arbitrary-address mailbox access. Returns opaque refs and continuation, not implicit acknowledgment. |
| `ack` | `mail:read`; only refs carried to this reader, owner generation and subscription incarnation. No dashboard ack, request closure or presence change. |
| `held`, `digest`, `digest_ack`, `presence` | Preserve existing command scope table: held and digest ack require `mail:read`; explicit digest generation requires `mail:read` plus `captain:presence`; away status requires `fleet:read`; start/back requires `captain:presence` and existing target checks. All execute only at the recorded desk owner. |
| `source.page` / `source.commit` / `source.status` | Internal configured, operator-trusted linked-core replication, not exposed to grants or adapters. Only the linked source's own captain conversations, closures and source checkpoints for the configured desk domain; no operator command dispatch. Core replication is distinct from permission to reveal replicated content to a door. |
| `desk.placement.propose` / `desk.placement.accept` / `desk.placement.commit` / `desk.placement.status` | Operator-gateway-only initial placement agreement for an unowned domain; binds proposal ID, manifest hash, owner core, generation 1 and incarnation. `desk.placement.accept` delivers the captain's approval of that exact proposal to a participant, which then runs its own acceptance checks (§3.2); polling status is not acceptance. Delegated door calls and grants can never reach these verbs or create ownership. |
| `desk.placement.stage` / `desk.placement.install` | Internal operator-authorized source placement change bound to the handoff certificate, manifest and expected old/new owner tuple (§3.5). Not a subscription or grant operation. |
| `handoff.prepare` / `handoff.page` / `handoff.seal` / `handoff.activate` / `handoff.status` | Operator-authorized placement transfer bound to old/new core IDs, domain, expected generation and transfer ID. Only configured participants may stage/activate it; never implicitly authorized by `mail:read`, subscription startup or delegated presence. A future scoped placement API needs explicit `fleet:admin` mapping and existing owner policy, not access to these internal verbs. |

The grant-owning host rechecks the current grant on **every** protected request, including resume, continuation, ack and delivery to the adapter. Remote admission uses a bounded, request-bound delegated snapshot, not a stored subscription's initial scopes. A grant restriction invalidates visibility/continuation state and prevents old unread refs from being newly exposed. Never send bearer credentials over the machine link. The desk checks operation scopes/ships again and records admitted provenance.

Define admission ordering explicitly: revocation committed before host admission denies that request; revocation during an already admitted remote operation cannot retract data/side effects admitted there. Recheck at host release can discard an arriving page after revocation, but cannot undo its served rows. Do not prefetch further pages or run unattended subscriptions using cached grant authority. A future reverse transport must renew this admission, not replay expired snapshots indefinitely.

Requiring `mail:read` for bodies in **new aggregate waiting** is an intentional tightening, not parity (decision 4, §7): today's scoped `waiting` returns full records with `fleet:read` alone ([scoped.rs](../../src/door/scoped.rs), `command_scopes`; [delegated.rs](../../src/door/delegated.rs), `Command::Waiting`). Keep the legacy operation unchanged; a door opts in to the aggregate operation, and the opt-in carries a migration notice that bodies now need `mail:read`. Metadata stays under `fleet:read`: the metadata-only variant omits body/payload and sensitive derived text.

### 3.2 Initial placement agreement and owner bootstrap

This is a prerequisite to serving any new desk subscription, **not** a side effect of its first pull or the later transfer protocol. In today's `alpha -> beta` setup, `machine captain beta` changes only `alpha`; `beta` still infers `alpha` as its desk from the `collected` row. The [desk fixture](../../tests/fixtures/door_desk_linked.rs) deletes that row to make `desk_here()` succeed. Implementation must keep the row and fix placement, not reproduce that workaround.

Persist an explicit agreement on **both** cores (and each additional domain source): `(proposal_id, domain, manifest_revision/hash, owner_core, generation=1, incarnation, local_role, intake_direction, state)`. The owner gets explicit `here`, overriding collector inference; sources record the same owner tuple and a legal `push` (source calls owner) or `collect` (owner calls source) direction; the owner's own homes use `local` intake. Keep the local `captain_desk` routing row consistent with this record, with explicit-here representation rather than deleting a row and falling back to inference. `desk_here()`/`holds_desk()`, `fleet.captain` and `fleet.collect` must consult the agreement for enrolled domains; preserve ordinary correlated-answer return paths. Pending/conflicting agreement is not an active desk. Preserve legacy behavior only for installations not enrolled in this protocol.

**Naming.** The agreement uses its own `desk.placement.*` namespace. [placement.rs](../../src/placement.rs) already owns `placement` for ship moves: the `placement` frame on `fleet.collect`, the `placement.proposed`/`placement.approved` audit events and `placement.lock`. Desk agreement uses a separate `desk_placement` collect frame, `desk.placement.*` audit events and its own lock beside the registry. It reuses that module's pattern: a target the proposer calls answers through the gateway, otherwise on its next collect pass; one captain decision is written; the operator's own reply records an approval in the registry where it was written (mail never does), and the exchange carries it on.

**Participants and contact.** Participants are the proposed owner and every manifest source. A legal contact between two machines is a configured link in either direction: a gateway call one way, the `desk_placement` frame on the other's collect pass the other way. The proposer coordinates when it has a legal contact with every participant. Otherwise the proposal runs at the owner: the proposer hands it to the owner over their contact, and the owner coordinates. Every source needs a legal intake direction to the owner anyway, so a source linked only to the owner takes part through it: the owner carries the proposal, approval and certificate to that source (by gateway call, or in the frame on the source's collect pass) and carries the source's acceptance back to the proposer. This relays agreement records bound to proposal ID and manifest hash, never mail; it is not a general captain-mail relay (§1). If neither the proposer nor the owner has a legal contact with every participant, or the proposer cannot reach the owner, `desk.placement.propose` is rejected before anything is staged with `no_legal_contact`, naming the participants that cannot be reached and the link direction that would fix it.

Proposed wire/operator sequence (command names illustrative, no new reverse connection):

1. **Propose, from either machine.** The operator runs `machine.desk.propose {domain, owner:beta, sources:[alpha,beta]}` on any participant: callable `alpha` or reached `beta`. The coordinator allocates a proposal ID/incarnation, pins every core ID and the manifest hash, stages the generation-1 record under its desk placement lock and audits `desk.placement.proposed`. Participants it calls receive `desk.placement.propose`; the others stage it from the `desk_placement` frame on their next collect pass. A proposal made on reached `beta` therefore reaches `alpha` on `alpha`'s next collect, as ship-move proposals do today. Every participant durably stages the identical record; no new subscription serves. Reject an existing owner/certificate, a concurrent conflicting proposal or an illegal source direction. Inventory alone is not agreement.
2. **The captain confirms by decision card.** The coordinator writes one captain decision (accept or reject) showing domain, owner, sources, each intake direction and the manifest hash, routed by today's captain-mail rules. No terminal is needed on the machine that cannot call out. The operator's own reply, in the process where it is written (as `answered` does for ship moves), records a `desk.placement.approved` approval bound to proposal ID and manifest hash; a reply that arrives as mail never records one. The exchange carries the approval to the coordinator and every participant: by `desk.placement.accept` where the carrier calls the participant, otherwise in the frame on the participant's next collect pass. An operator at a participant's terminal may instead run `machine.desk.accept {proposal_id, manifest_hash}`, which records the same approval there.
3. **Each participant accepts.** Whether the approval arrives locally or remotely, the participant runs the same local step: its staged record and hash match, its legacy writers are fenced, its intake direction is legal and no rival proposal holds the domain. It then audits `desk.placement.accepted`, which returns to the coordinator on the reply or the next frame. A remote accept (a gateway call to `desk.placement.accept`, or an approval in a frame) only delivers the captain's confirmation; the receiving participant still runs its own checks and can refuse. It is not consent by the calling machine. This is a confirmation step, not a security boundary: under shared operator trust (§3.1) a linked peer could forge an approval, as it can already reply for the captain at that gateway. Delegated door calls and grants never reach this path.
4. **Commit.** After every participant accepts, the coordinator commits the immutable bootstrap certificate naming **one** owner tuple, then delivers it with `desk.placement.commit` or the frame over the same legal contacts (through the owner for owner-only sources). Each participant installs its agreed routing/placement atomically. `beta` activates generation 1 only from that certificate and its own matching acceptance; `alpha` stays a source. Lost replies resume by proposal ID and `desk.placement.status`; no timeout selects a different owner. Partial install reports pending coverage until all source placements reconcile.

Before certificate commit, lock/fence participating legacy desk/presence/cursor writers being enrolled and reconcile any conflicting away/digest ownership explicitly. Unresolved imports or a participant that has not confirmed its fence block commit. Pending bootstrap can abort before certification, including by a reject answer on the card; afterward only recovery of the exact certified owner is allowed. One coordinator serializes bootstrap under its desk placement lock; each participant reserves the domain to that proposal and rejects rival proposals, including a second proposer. A single-machine domain records the same tuple locally without RPC. Restores and attempts to re-bootstrap an owned domain fail closed; changing an established owner uses §3.5, never another generation-1 agreement.

### 3.3 Source journal and coverage barriers

A desk subscription needs more than reading whichever copies happen to be local. Maintain a durable desk intake journal referencing stable **origin** `(core UUID, mailbox incarnation, mail ID)` and source order, with local aliases for collection/desk copies. Preserve correlation, open/closed state and source checkpoint evidence. Existing mail IDs remain externally useful; never use a home path, ship rename or a copied `seq` as global identity. Copy provenance must be carried by new ingestion, not guessed from equal sequences or identical bodies. Conflicting origins/content for one purported copy produce an integrity gap, not silent suppression.

Source pages have bounded bytes/items, an immutable upper checkpoint and ordered events for mail and closures. Commit source intake and its checkpoint together before reporting acceptance; a failed receipt is safe to replay. Local mail remains the source of truth for its request lifecycle. The journal is a projection, not permission to answer an ask or manufacture approval evidence. Use idempotent import intents when source home and registry cannot commit atomically; never claim a distributed SQL transaction.

Initialize each source with a bounded snapshot of retained captain history, including **all unread mail and open requests regardless of age**, then replay changes from a recorded barrier. Include local-only outgoing captain sends and closures so #481's routing stays unchanged while its observational gap can close. A source that cannot supply required retained facts reports `history_gap`/`unreadable`; a legacy desk push's timestamp cutoff is not a sufficient baseline. Do not reroute or re-offer ship mail merely to rebuild reader coverage.

A door's first aggregate subscription names its domain explicitly; the operator selects and confirms it when enabling the door (decision 5, §7). No default domain is inferred from the door's machine, its links or the directory. Record the configured domain/source manifest revision, membership and checkpoint vector. Retired or unreachable sources with unread/open facts cannot disappear just because a new directory omits them. Bootstrap from all authorized local homes and known linked sources; transitive or unregistered fleet members remain explicitly outside the domain, never silently claimed observed. Topology conflicts and unknown membership prevent a fleet-wide completeness claim.

A fresh aggregate read reports a **vector snapshot**, not a globally simultaneous instant. For callable sources, request a new barrier and fetch through it. For **push-only sources the desk cannot call**, choose explicitly: “fresh” means the latest fully committed source barrier received on a completed push contact, within the domain's `max_source_age_ms`, **not** a barrier taken on demand after the read began. The bound defaults to 15 minutes (900000 ms) and the operator sets it per domain (decision 5, §7); no door, grant or adapter can widen it. The source must enumerate all required homes and send checkpoint evidence, including empty-contact barriers; an ordinary legacy push receipt is insufficient. A result can be `complete:true` under this bounded-contact-age policy, but must say “as of last source contacts” and expose each source's mode and age, never imply a current on-demand fleet observation.

Measure `received_at` and `age_ms` on the desk's clock; they measure contact age, not mail creation time or remote event age. Only a new completed contact with a new barrier refreshes it, not a replayed page/checkpoint or handoff import. Persist evidence; after restart, clock discontinuity or handoff, conservatively mark it cached until new contact unless elapsed-age continuity is proved. Coverage carries `barrier_mode` (`on_demand` or `last_received_push`), `received_at`, `age_ms`, and `max_source_age_ms`. An expired, absent or incomplete push barrier is cached/partial; no waiting timeout upgrades it. Source ingestion can ride either legal collect/push direction, including a source that only reaches the desk, but cannot create a reverse reader route.

### 3.4 Durable delivery, acks and duplicates

At the desk persist subscriptions, reader identity, generation/incarnation, source checkpoint vector, contiguous per-origin acknowledged prefixes, bounded sparse served/acked refs, paging snapshots and independent digest/catch-up baselines. Persist the host's subscription identity and last known owner; host caches are not cursor authority. Reserve served refs transactionally **before** releasing a page. Restart resumes these records; lost output leaves harmless refs that are re-carried, not acknowledged. Resume never trusts a client-provided high-water mark.

Ack behavior:

- Bind random opaque refs to reader, owner generation, subscription incarnation, origin/mail identity and kind (raw mail versus digest). Validate the entire batch, including visibility and generation, before any mutation. Client sequences cannot advance a cursor.
- An ack lost before commit changes nothing. An ack committed with its response lost may be retried with the same bounded idempotency key and identical ref batch, returning its recorded outcome. After receipt retention expires, return `stale_or_unknown`, not fabricated success. Existing selected-mailbox ack behavior need not be silently changed.
- A forged, future, wrong-reader, wrong-origin or wrong-kind ref fails closed. Sparse acknowledgments compact only a proved contiguous prefix of eligible mail; no unseen gap can be skipped by `show` or thread reads. Concurrent acks have one transactional outcome.
- A read never closes an open request. Dashboard acknowledgment, raw delivery acknowledgment and digest delivery are distinct facts. A digest cannot globally acknowledge its input mail or suppress another reader.

At-least-once delivery is intentional. Deduplicate repeated origin/copy identities within one reader, retaining aliases and closure facts; never deduplicate by rendered text. Two doors or two grants can each receive the same mail. Bounded sparse records and cursor/checkpoint proofs replace an unbounded delivered-ID set. If retention removes a proof needed to suppress a copy, safe redelivery or an explicit coverage gap is preferable to treating unseen mail as read. Do not prune unread, open or pinned pending delivery facts to free a queue; stop intake/page admission and report backpressure.

### 3.5 Desk moves: fenced generation handoff

The current `captain_desk.set_ms` is not an ownership generation. Start with the agreed domain ID, owner core ID, generation 1 and unguessable incarnation from §3.2; add a durable transfer record. Every reader/ref is bound to that owner generation/incarnation from its first issuance, before moves are implemented. Incrementing a local integer on two disconnected machines is **not** election. No automatic takeover on timeout, registry restore or link failure.

Use a cooperative transfer from old owner `alpha` at generation `g` to `beta` at `g+1`:

1. **Prepare.** An operator submits `(transfer_id, domain, expected_owner=alpha, expected_generation=g, target=beta)`. The old owner serializes transfers, allocates the successor incarnation, and verifies target capacity and the transfer's legal contact direction. Freeze the source manifest revision and require **every source**, including old owner `alpha` and target `beta`'s own homes, to have an agreed legal intake direction to `beta`: source-to-target push, target-to-source collect, or local intake for `beta`'s own homes, not third-party relay. A missing link/direction blocks prepare; only a separately authorized operator action can configure one. Via current legal contacts, each source durably accepts `desk.placement.stage` binding its old tuple, successor tuple, local `captain_desk` routing change and intake direction to this transfer. A source that cannot stage blocks sealing. Target records `staging`, never serves it; staged placement does not yet switch traffic.
2. **Copy.** Page a manifest and snapshot to the target over the configured operator-trusted transport: source journal/aliases, unread/open/closure facts, source barriers, reader cursors, pending deliveries, away period and routing counters, digest/catch-up rows and baselines. Hash and count chunks; repeat by transfer ID. No target grant/token duplication is required: reader keys still refer to their grant-owning host. Live intake can continue with a bounded delta log; apply backpressure if it fills.
3. **Seal and fence.** After target confirms durable staging, old owner takes its owner-write lock, drains admitted owner mutations, fences all reader acks/pulls/presence/digest builds, and records the final delta/barriers and sealed manifest. Imports from multiple stores need replayable intents; seal cannot succeed while any required intent is unresolved. The final ownership transaction records an **irrevocable successor certificate** binding domain, `g`, `g+1`, both incarnations/core IDs, transfer ID and sealed manifest. The old owner is now permanently fenced for desk mutations at `g`; retired desk operations serve only transfer status and a verified redirect. Its own source journal/replication continues without desk authority. It cannot unilaterally roll back this certificate.
4. **Activate and install source placement.** Target verifies the certificate through the configured operator-trusted relationship, durably installs the final state, and atomically changes `staging` to active owner `g+1`. It cannot become active from a prepare message or elapsed timeout. The source certificate designates the successor even during the availability gap before activation: there is one recorded successor and possibly no serving owner, never two serving owners. Both records reference one transfer, not rival elections. Carry `desk.placement.install` and the certificate to each staged source over its legal contact direction (a push-only source may retrieve it when next contacting the old owner). Each installs the new owner tuple and local `captain_desk` routing row/direction in one transaction. New `fleet.captain` pushes name the successor/generation; generation-aware `fleet.collect` serves general captain intake only to that owner, preserving correlated-answer exceptions. An explicit remote placement must support a desk that collects from the source; it must not require that source to call out as today's `set_desk()` does.
5. **Resume and reconcile.** Door hosts verify the new owner through configured links/status; they must have a callable route to resume. A source waits for verified target activation before committing intake there, retains mail/closures until successor acceptance, and reconciles through a new barrier. Old placement-driven pushes reaching fenced `alpha` receive `stale_generation` plus the certificate/hint, **not** intake acceptance or recursive forwarding; the durable source retries toward `beta` after installing placement. `alpha` is now an ordinary source: its own ships, local outgoing sends and post-seal changes enter `beta` by its staged legal intake direction. Late pushes from other sources remain those sources' custody and go directly to `beta`; imported pre-seal copies retain their original provenance. Until every required source installs placement and reconciles, coverage stays partial. Old pending deliveries are reissued with **new refs** at `g+1`; already acknowledged prefixes and request state are preserved, not reset to the dashboard cursor.

Every owner mutation checks the active generation inside the same transaction as its cursor/presence change. An ack committed before sealing is included in the final delta. An ack racing after fencing is refused without mutation. **Never translate an old ref into a new-generation ack**, even if it names the same mail and reader. Pending mail/digests can therefore repeat after a move; they cannot disappear because an old ack arrived at either desk. Any retained receipt for an ack committed before sealing is explicitly a historical `g` outcome, not admission or acknowledgment at `g+1`. Intake arriving after the sealed barrier stays unacknowledged at its source until the successor durably accepts it; the old owner must not report acceptance and discard it.

Recovery: restart before certification resumes staging or allows an explicit abort under the old owner's lock; after certification only forward recovery/activation of that exact successor is allowed. A target receipt lost on the wire is recovered by `handoff.status`. A target crash after activation cannot make the old owner serve again. Simultaneous moves, moves back and delayed old activation messages compare expected generation/transfer ID and fail stale. A second transfer starts only from the active successor.

Handoff is cooperative only, with no automatic failover (decision 6, §7). This protocol sacrifices availability during a partition. It cannot safely force a move if the old owner is permanently lost: forced recovery needs verifiable fencing of that installation and its own design and authorization later. Restoring an unfenced old registry backup must not reactivate it; bootstrap/restore needs current ownership validation, otherwise it stays read-only/unavailable. A local certificate file is not protection against an operator deliberately running a stale clone. Do not claim consensus or partition-tolerant failover.

### 3.6 Away, digest and paging

Only the active desk classifies held mail and mutates authoritative away state, breakthrough budgets, digest builds and catch-up decisions for these subscriptions. Adapter hosts relay; failed routes cannot create local away forks. Scoped sends preserve today's rule that they do not end away, including failed sends; presence changes remain explicit. Trusted local v1 behavior stays unchanged until a deliberate migration.

Digest inputs come from the intake projection and carry its coverage vector. If a source is missing, a useful partial digest may still be delivered with visible omissions, but its baseline advances **only** through represented source checkpoints. Preserve counts, IDs/correlation, deadlines, open requests, closures and omitted-source facts when combining notifications. Pending summaries are transferred intact across desk moves, with new-generation ack refs; no second builder runs at the old owner. Request content remains filtered for each grant, including old pending summaries after restriction. Returning from away updates that owner's subscription catch-ups once; it must not consume independent MCP raw inbox cursors as if they were trusted v1 push cursors.

Use stable keyset paging with per-source upper checkpoints and a bounded merge snapshot. Continuations bind reader, visibility revision, owner generation, operation/thread anchor, domain manifest revision and snapshot; expire them explicitly. Limit items, serialized response bytes (including metadata), scanned rows, source fan-out, in-flight refs, pending snapshots, retry/idempotency receipts and transfer chunks. Empty pages may have continuations when work limits are hit. Reject an oversized item with a structured gap/handle policy, never silently drop it. Window pressure stops new serving without discarding pending unread facts. Avoid holding a registry transaction over network calls.

All new mail, waiting, presence/digest, ack, resume and handoff responses, including empty and failed ones, carry typed coverage or a non-disclosing refusal envelope. Keep `coverage.complete` separate from `continuation`/`more`, side-effect outcome and transport success. A complete page is not a drained inbox; an accepted send is not completed work.

Required semantics:

- Scope distinguishes `selected-mailbox`, `desk-domain`, `local` and `operation-only`. Selected-mailbox `complete:true` never means fleet-wide. Ack/presence success may have operation-only completeness while input coverage remains partial; include those separately rather than upgrading the whole result.
- `complete:true` for desk-domain data means every required **authorized** source in the fixed manifest has installed the owner placement and is reconciled through the advertised fresh barrier under §3.3's explicit on-demand/bounded-contact-age policy, no required home/page failed, and no unresolved ownership, retention or integrity gap exists. It is only complete as of that vector. No claim about later mail or unknown machines. Only a validated manifest of the whole configured fleet permits the additional user-facing “fleet-wide as of snapshot” wording.
- Distinguish `covered`, `cached`, `unavailable`, `reverse_only`, `unsupported`, `history_gap`, `unreadable`, `backpressure`, `handoff_pending`, `stale_generation` and `ambiguous_owner`. Report barrier mode, desk-measured contact age/last successful contact, configured maximum age, observation time and retry action; push-only completeness is dated last-contact evidence, not proof of an on-demand read. Do not compare remote clocks as proof of freshness. Network failures after a write can be `outcome_unknown`; coverage cannot imply that write failed or succeeded.
- The local `mail_delivery.summary/warning` diagnostic remains topology information, not live proof. Tool rendering must display omissions, not summarize a partial empty waiting result as “nothing needs you.”
- Ship restrictions apply to coverage too: hidden topology, counts, home paths and source names must not leak. Use opaque allowed source handles and an unexplained incomplete/unknown-domain marker where necessary. If the host cannot establish authorized completeness without hidden metadata, return `complete:false`, not an invented all-clear. Precise operator diagnostics stay in bounded internal audit.

## 4. Migration and local-only compatibility

**b2a upgrade defense in depth — stop old writers.** Before enabling off-path enrollment, stop **every pre-b2a resident process** that can open an enrolled home (including old serve workers and hosted agents), verify its payload has actually exited, and replace every CLI/gateway launcher that could invoke an older binary. Do not rely on stopping a wrapper. Keep ordinary mail on the compatible binary; no route change is required. Do not downgrade while tracking/publication is active. A backup restore or in-place home recreation must likewise be done with all writers stopped.

**Mail-compatible #514 fence (b2a round 3):** activation atomically inserts a placeholder `mail_source_snapshot` row with binding `enrolling:<nonce>` and upper/copy pointer `-1`. #514's writer hook tests that row's existence inside the mail transaction, so it records deltas even though it ignores the enrollment table. Its contact reads that impossible binding and stops with `stale_generation` before inline capture, staging or reclaim, without failing ordinary mail. New code treats negative uppers as unpublished (except the intentionally active writer predicate). Publication replaces only the matching nonce's placeholder; abandoning/deactivating removes it. This fences #514's known predicates, not arbitrary historical binaries or malicious writers, and does not supply compatible old intake after publication: stop-old-writers remains upgrade defense in depth. No failing mail trigger, route change or open-time-only schema-version check is used.

The nonce binds home activation, home publication and sidecar. At the start of another idle unit an unpublished activation with no matching frozen sidecar is deactivated **before** retry backoff, and a later attempt gets a fresh nonce. Thus a backup made in the activation-before-freeze crash window cannot match the next unit's sidecar and reclaim reused post-restore sequences. A genuinely committed matching sidecar still resumes across restart. This is not a claim to detect every arbitrary mid-attempt backup/clone or deliberate stale restore; coordinated stopped-writer backups/restores remain required. Pre-nonce **published** off-path enrollments fail closed for intake and require explicit recovery/reconciliation; the upgrade does not invent a nonce for already imported facts. Legacy inline baselines without an enrollment row are unaffected. Ordinary mail still opens and flows.

1. Add schema/version negotiation without deleting or rewriting existing `door_cursor`, `door_reader_*`, away or digest rows. Old peers remain explicit `unsupported`/partial. Existing selected-mailbox v2 operations keep their coverage scope and acknowledgment contract.
2. Bootstrap an owner/domain through §3.2's explicit placement agreement and generation-1 certificate, including explicit `here` on a reached owner without deleting its `collected` link. Preserve existing registry machine UUIDs, mailbox incarnation UUIDs and grant IDs; source identity migration adds aliases rather than renumbering stored mail. No automatic desk movement on upgrade. Gate aggregate waiting's new body scope check behind opt-in and notify clients that bodies now need `mail:read`; do not silently broaden existing `fleet:read` grants.
3. Opt a door into the new subscription at a recorded local/source barrier, with its domain explicitly selected by the operator (§3.3). Import its proved per-home acknowledged prefixes and outstanding unread/open facts transactionally via replayable migration state. Never translate a sequence from one mailbox into another's. A remote selected-mailbox cursor migrates only with holder evidence obtained over the configured operator-trusted link, not the adapter's claimed position. If old copy provenance cannot be proved, replay retained unread/open facts conservatively and report any history gap.
4. Keep a v2 grant's existing reader progress independent from v1 and dashboard progress. Do not initialize it from the dashboard on upgrade. Local v1 cursors retain their existing first-registration rule. Fence the migrated door's old push writer before new subscription serving; use a new subscription incarnation and reissue outstanding refs. After migration, late old-session acks cannot write either migrated cursor.
5. Import one authoritative away period, routing counters, pending digests and per-reader baselines from the agreed owner. Conflicting active local periods require operator reconciliation, never timestamp-winner merging. Do not mark pending digest rows delivered merely because the import completed.
6. A single-machine installation needs no link, transfer or remote grant store. Existing non-opted-in v1 doors, scoped selected-mailbox reads, local sends, dashboard unread state and grant lifecycle stay unchanged. New local desk-domain subscriptions run the same bounded serving/ack logic without RPC; migration replay is permitted, mail loss is not. Downgrade cannot safely reactivate migrated old cursor writers: retain the fence and require explicit compatible recovery.

Unused reservations expire after **24 hours**; committed outcomes expire **1 hour after commit**, or at the issuing snapshot's saved expiry if that is later (including a backwards clock adjustment). They never expire while that snapshot can still reissue the key. Identical retries remain immutable inside that receipt lifetime, even after early snapshot reclamation. After expiry the result is honestly `stale_or_unknown`. An expired page key cannot be reserved anew: its snapshot and secret have expired too; new snapshots and standalone keys use fresh random identities. Older already-committed 24-hour receipts retain their saved expiry. Reserving a key consumes a receipt slot; acking with that key commits its outcome without consuming another slot. In particular, each distinct visited page offset reserves its deterministic page key, whether or not the client acks it. The cap can still backpressure a client reserving roughly 128 keys within an hour (fewer with other retained reservations or outcomes), but no longer imposes a day-long lockout on new commits. The pull snapshot cap above lets one maximum-size snapshot drain with per-page acks and room for a fresh pull when starting without other receipt pressure. Open/resume reuse an unused standalone key and extend its reservation expiry when handing it out again, without changing committed receipts; unused page reservations are reclaimed after their snapshot is gone, including keys for later page offsets. Reservation metadata uses the existing outcome field only while batch is NULL, and is atomically replaced by the committed outcome. The entire sorted/deduplicated batch is checked before mutation. Identical committed retries return the recorded operation outcome; unknown/expired keys refuse honestly. Sparse refs compact against all eligible projected and pending observations above the proved prefix, not the subset seen by show/thread, streaming bodies and retaining only unseen boundaries and bounded sparse ack orders. Visibility changes start a new subscription incarnation and conservative progress; no old ref translation is provided. Revoked/expired/missing local grants and their subscription state are retired in the writer transaction before admission, using the operation's injected `now`; paused grants retain their slots. An expired grant that has been retired and is later re-extended opens a new subscription from zero, replaying retained authorized history; extending before a retirement sweep preserves its state. A fenced Open against a newly certified local owner tuple retires that reader's stale-owner row and starts a new identity with no refs, receipts, snapshots or progress carried over; stale resume/ack requests still refuse. This is conservative replay, not placement, handoff or intake reconciliation. Genuine live subscription/unexpired-committed-receipt capacity still stops admission rather than evicting custody.

   Coverage stores the filtered, dated source vector with each immutable snapshot, including its observation time, opaque source handles and contact-age policy. A read creates no on-demand barrier. Restricted grants omit owner/revision and never claim whole-domain completeness. Precise source diagnostics, home paths and hidden counts are not forwarded. Normal writable startup installs additive ledger tables; read accessors do not migrate. This stage adds no public command/tool or delegated wire. PR 3b must implement fresh host admission/release, remote reader provenance and callable-owner routing; v1 trust/migration and adapter exposure remain later stages. This is not a production ChatGPT fix or a topology change.
4. **Generation-changing handoff:** operator-only prepare/stage/seal/certificate/activate/status, source placement installation and intake-direction reconciliation, owner fencing and registry-restore guard. Builds on PR 2a's starting owner, not a new bootstrap mechanism. Tests: every crash boundary, conflicting/return transfers, illegal source directions, late pushes/old-owner sources, link loss, unread/open preservation and mail/digest stale refs at both desks. Seed digest-shaped state without enabling a second digest builder.

Tests: partial inputs, restart, return/move races and independent reader baselines. Preserve v1 policy until opt-in.
6. **Cursor/state migration:** explicit cursor import/fence, subscription incarnation change, away/digest reconciliation and local-only compatibility. Tests: seeded v1/v2 progress, interrupted/repeated migration, unsafe downgrade refusal and real supervisor restart. No new aggregate tool exposure yet.

## 7. Decisions (captain, 2026-10-25)

The captain accepted all six recommendations. The body above is written to match.

1. **Reverse-only readers:** report partial or unavailable coverage in this phase; no reverse-reader spool. In the usual `alpha -> beta` setup with the door on reached `beta` and the desk on `alpha`, that means unavailable. Full coverage there needs an agreed desk on `beta` (PR 2a), source barriers and bounded push-contact freshness; the door cannot move the desk or create a route.
2. **Placement agreement:** either machine can propose. A proposal from the reached machine is carried on the next collect pass, as ship-move placement works today. The captain confirms through a captain decision card, so the machine that cannot call out needs no terminal. Local acceptance is a confirmation step, not a security boundary, under shared operator trust (§3.2).
3. **Linked-machine trust:** linked machines share operator trust. A linked peer can impersonate reader origins, acks, placement acceptances and coverage; this design does not claim otherwise (§3.1).
4. **Aggregate waiting bodies:** new aggregate waiting bodies need `mail:read`; metadata stays under `fleet:read`. The tightening ships behind an opt-in with a migration notice (§3.1, §4).
5. **Coverage domain and freshness:** a door's first aggregate subscription selects its domain explicitly. Push-only sources count as fresh within `max_source_age_ms`, which defaults to 15 minutes and is set by the operator (§3.3).
6. **Unrecoverable owner:** cooperative handoff only, with no automatic failover. Forced recovery needs its own design and authorization later (§3.5).
