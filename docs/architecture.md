# Architecture

Privateer's flat structure distributes routine decisions while preserving explicit responsibility. A navigator is a conversational role, not the scheduler's exclusive control plane. A department may contact another department directly. Tasks retain an owner, a charter, status, and bounded delegation depth. A handoff requires the current owner's request and the recipient's acceptance.

## Runtime boundary

The Rust runtime handles durable state, process supervision, resource admission, and transport. SQLite stores charter/task state, facts, pending issues, approvals, and audits. A job runs under a recorded task and an admitted resource reservation. A detached supervisor manages its payload process group and records completion after the invoking CLI exits. Some programs leave that group: `xcodebuild`, for one, starts a session of its own. While the job runs, the supervisor records every descendant of the payload outside its group, with its start identity, so it can find them after their parent exits; it skips independently supervised Privateer processes (other jobs' supervisors, dispatchers, doors) and everything under them, since a job started from inside another job belongs to its own supervisor. A timeout or cancellation signals those descendants as well as the group, and a job whose leader exits while one of them still runs keeps its reservation as `orphaned` (or, with `cleanup_descendants`, ends them first), exactly as for a surviving group member; `job.cancel` and reconciliation treat them alike. A descendant that leaves the group and loses its parent within half a second of starting can still be missed.

Schema upgrades, including activation's wake/session columns, check and change the schema under an immediate write transaction. Concurrent opens serialize those checks and retain existing wake history.

Multiple homes on one host share a configured resource ledger, and admission decisions are made under its lock against the same readings, so independent departments cannot each assume the machine is free.

Every job checks the host-wide free-disk floor (`min_free_disk_bytes`, default 2 GiB) and its charter's `min_free_bytes` floor against live free space before launch, measured on the filesystem the job will use. The stricter floor wins; `resource.status` reports the total and free bytes of the home's filesystem and whether the host floor is met. Jobs that do not fit can use `wait_for_capacity:true` to join the same host-wide FIFO queue; queued jobs are visible to `runtime.needs` after a minute, with disk-floor waits typed as `disk_floor_wait`. Workspaces check both floors on the filesystem where their worktree pool lives; a workspace needs only disk, so it is allocated at once when the floors are met, whatever jobs wait for CPU or memory; below a floor, `workspace.acquire` accepts the same `wait_for_capacity` and `max_wait_secs` options and waits behind earlier workspaces waiting for disk, holding its queue position across lease creation. Light jobs without estimates are exempt from CPU, memory and disk demand admission but still obey disk floors. Jobs declare disk as well as CPU and memory (`estimate`, or the heavy defaults); see [setting a machine's resource floor](resources.md).

Heavy jobs, and any job that passes an `estimate` (`cpus`, `memory_bytes`, `disk_bytes`), are admitted from live readings rather than a fixed slot count: the load average, CPU count and available memory, plus the estimates of jobs admitted within the last `ramp_secs` (default 60), whose use does not show in those readings yet. The reverse is credited too: a heavy or estimated job that just ended still shows in the one-minute load average for minutes, so admission subtracts what is left of it (its CPU estimate, at most the load when it ended, fading with the average's one-minute time constant, and together never more than that load), and the next job is not held back by a build that has already finished. `resource.status` shows the credit (`released_load`) and how many jobs it comes from (`recently_ended`). A job is admitted while load plus recent estimates stays below `max_load_per_cpu` (default 1.0) per CPU, and while available memory minus recent estimates and its own stays above `min_available_memory_bytes` (default 1 GiB). A job's own estimate counts only while another estimated job holds a reservation: one running alone needs just that floor, so a small machine whose person is using most of its memory still runs its builds one at a time instead of queueing them forever. Heavy jobs without an estimate count as every CPU and 2 GiB of memory, and a job started with `heavy: true` also counts 4 GiB of disk (`heavy_estimate`), so two big builds cannot start together, while a later one is admitted once the first turns out to be light. A job's declared disk is counted above the floors together with the disk that live reservations on the same filesystem still have to write: each one's declared `disk_bytes` less the drop in free space since it was admitted, since a reading already shows what it wrote, with the total credit capped at the drop since the oldest of them. Unlike load and memory, a build's bytes stay on the filesystem until something removes them, so a reservation holds its declared disk for as long as it lives. The resolved demand and the filesystem's key and admitted free space are recorded with the reservation, so another home's admission and `resource.status` both see them; a reservation written before jobs declared disk is read as demanding none. `max_heavy_jobs` adds an optional host-wide slot cap and a charter's `max_heavy_jobs` an optional per-charter share. `resource.configure` changes these host-wide settings for every home, and is open to agents so they can tune the machine to their person's wishes, from using all of it to leaving room for the person's own work; `resource.status` shows the settings beside the live readings. Light jobs without estimates are exempt from CPU and memory admission but still obey disk floors. Model providers are regulated separately. A harness job launched by `agent.start` records its route (`harness/provider/model`); after it ends, the dispatcher reads how its last reply ended, and a run that failed on a provider throttle (429, 503 or 529, rate limit, overloaded, upstream unavailable, quota, timed out) backs the route off in the host's ledger, for 30 seconds doubling to 15 minutes, while a later success on the route clears it and other failures leave it alone. A throttle that states when it reopens holds its route until then, wherever the statement appears: an HTTP `retry-after`, an ISO deadline, or a `resets in N hours` window. That stated reset only ever raises the floor of the doubling, never lowers it, so it can lengthen a backoff but never shorten one. A rate limit or quota on a route the captain marks `cost: free` is that route's allowance spent, however the provider words it, while an outage on it stays on the short doubling; without a stated reset it waits for the daily reset the captain records on the route (`allowance_resets_utc`), and knowing neither, or throttled within 15 minutes after that time, it is probed again after an hour, then two, doubling to a day, so the allowance is used again soon after it returns. A free allowance a provider names as one but gives no reset for is probed the same way. A reset read out of free text can be misread, so it is capped at two days rather than trusted further; a `retry-after` marker reads only the number that directly follows it, with `_ms` or `-ms` meaning milliseconds. A structured reset from Claude is trusted up to eight days. A headless OpenCode V1 run waits silently after a provider error instead of failing, so it runs under a watch (`opencode_watch.py`) that reads OpenCode's log: when a model stream fails and neither an event nor a retry of that stream follows within five minutes, the watch stops OpenCode and ends the run with that error as its final `error` event. OpenCode sleeps out a provider's `retry-after` without a log line, so a run told to wait longer than that is ended too and its route backs off. Native adapters end a run in their own shapes, which are read too: Gemini reports a failed turn as a `type:"error"` event whose text sits in a top-level `message` (a `severity` of `warning` did not end the run) or as a terminal `type:"result"` carrying a `status` and an `error`, neither of which is a throttle when the run succeeded. Claude Code reports its plan windows in a `rate_limit_event`; a `rejected` window backs the route off until its stated `resetsAt` (at most eight days), and the five-hour and weekly windows, which cover the whole account, back off every Claude model at once (`claude/-/*`). A Claude run that ends on an error result fails even when Claude exits 0. While a route is backed off, `agent.start` refuses new crew and errands on it with the time left, headless wakes on it wait, and `resource.status` (`model_routes`) and the bearings show it. Live hosted sessions retry inside their harness.
The captain chooses which routes crew, errands and first mates may use. `privateer routes set FILE.json` (or `routes.set`, operator only) writes one fleet-wide file beside the fleet registry: named `routes`, each a manifest, options and a `cost` of `free`, `plan` or `credits` with an optional `note` and, for an allowance known to renew daily, `allowance_resets_utc` (`HH:MM`); ordered `crew`, `errand` and `first_mate` lists; and optional per-ship lists under `ships.<name>`, which replace the fleet's list of that kind for that ship. `agent.start` without a manifest takes the first route in the ship's crew list that is not backing off, or the one named with `route`; when every listed route is backing off it is refused with each one's reason. An agent that passes its own manifest and options is refused unless they match a listed route's harness, provider and model, so ships cannot widen their own spending; the operator may launch anything. Settings such as `effort` may be added to a chosen route, but its provider and model stay. `errand.start` uses the errand list the same way, also accepting `route`; tool bundles and plugin config apply only when an errand runs on the ship's own route, and an errand on another harness starts a fresh session. First-mate wakes use the ship's own manifest and options unless that route is backing off; then they use the first available route in the ship's `first_mate` list, falling back to the fleet list when the ship has no override. The fallback route's options replace the first mate's options, so settings such as `permission_mode` carry over only when the selected fallback sets them. A charter with a `provider_plugin` pin does not fall back. With no available fallback, the wake waits as before. While the own route is backing off, a hosted first mate is not relaunched; due mail can instead start a headless wake on the fallback route. When the own route clears, first mates return to their configured route and normal hosting. Without a routes file, crew keep their first mate's route as before. The bearings list each ship's routes in order with their cost and note, and mark those backing off. A failed run is not relaunched on the next route: its throttle backs the route off, and the next launch moves down the list.

A job started with `wait_for_capacity: true` joins a host-wide, first-come-first-served queue in the ledger instead of being refused. Its detached supervisor waits there, re-checking cancellation and authority about once a second, and starts the payload once the job reaches the head of the queue and fits; `max_wait_secs` (default 3600) bounds the wait. Requests subject to admission cannot bypass a non-empty queue, and entries whose supervisor has gone are dropped. Nothing runs while a job is queued, so cancelling it, or losing its supervisor, simply ends it.

Admission governs work started through `job.start`. A harness started by `agent.start` is light by default, since it mostly waits on its model; its brief asks it to run builds and test suites that load the machine as heavy jobs with `wait_for_capacity`, so those are spaced out and queued. Work a harness runs directly in its own shell is outside admission. Process identity and surviving payloads matter more than a supervisor's liveness; uncertain ownership is preserved for explicit recovery. When a job's leader exits, its supervisor stops whatever the leader left in its process group (TERM, then KILL), unless the job was started with `cleanup_descendants: false`. A job whose supervisor and recorded process group are both provably gone settles automatically: to its leader's recorded result when descendants outlived the leader, otherwise to `failed`. `resource.recover` explicitly releases a reservation no job can settle, such as one left by a crash between the ledger and home commits. It never releases a live supervisor or process group, and a reservation with no recorded payload identity requires `force: true`.

Events are facts. Pending notifications are a projection: repeated facts concerning the same task and issue update one pending item. An acknowledgment names the sequence actually observed, so a later fact cannot be silently discarded. Messages name a recipient and a task rather than broadcasting to the whole fleet.

History is kept until an operator prunes it. `history.prune` (`older_than_days` or `before_ms`, optionally `dry_run`) removes event facts older than the cutoff that no longer back a pending notification, audit rows older than the cutoff, and finished jobs whose reservations are released, together with their log directories. Pending notifications, including unread messages, and live or still-reserved jobs are kept. Pruned event and job ids may be reused afterwards. Nothing is deleted automatically; run it by hand or from cron.

## Ships and mailboxes

A ship is an identity with its own mailbox, first mate and crew; a home hosts one or more ships, and the directory (`ship.put`, `ship.list`, `ship.show`) records each ship's plain-language scope, location and the request kinds it accepts. `captain` is the reserved address of the person. Directory administration through `ship.put` is an operator command.

`mail.send` writes typed, durable messages: a `request` or a `decision` (addressed to the captain) stays open until its single `reply` from the recipient or an explicit runtime closure, and the runtime tracks it rather than any agent's memory; a `notice` states a fact. Message ids are idempotency keys, a request can carry a reply deadline after which it reads as overdue, and typed request kinds are checked against what the recipient accepts. `mail.inbox` returns unacknowledged mail, `mail.ack` acknowledges through a sequence actually present in that mailbox and never moves back, and `mail.requests` lists incoming or outgoing requests by state. Agents send and read mail only as their own ship; only the operator speaks as, or reads mail for, the captain. `history.prune` removes acknowledged mail past its cutoff but never unread mail or a request still owed its reply. A sender withdraws a request it no longer needs answered with `mail.withdraw` (state `withdrawn`), using a transactional durable closure notice; updated peers apply it through the existing outbox. The compatibility `remote` result reports `withdrawn` only with matching application evidence, never from transport success alone (older peers are `unknown`). `captain.waiting` lists every open request and decision addressed to the captain across the fleet's homes, the list the front door's `/waiting` shows; the operator and the verified liaison, from its own home, may read it. Each entry carries `asked_ms` and the derived `age_ms` against the list's `now_ms`, so a reader says when a request was asked instead of restating its body as current fact. A request the sender marks `payload.needs_hands` with a bounded `step` (a request to the captain only) also appears in `hands_on` with that step, and the front door lists those first; the mark is read from the record, never inferred from the text. This raw list is distinct from the bounded read-only, operator-only typed `runtime.needs` observation ([contract](runtime-needs.md)); desk permission does not grant bridge observation or action rights. The liaison records an answer the captain gave it with `captain.relay {request, source, body}`: `source` must be the captain's own message to the liaison from the last day, the reply is written as the captain's in the asking ship's home with `relayed_by` and the captain's words in its payload, and production approvals are never relayed. The operator answers or closes one captain item without knowing which home holds it: `captain.reply {id, body?, payload?}` finds the open request or decision in any fleet home on this machine and sends the captain's reply there (a ship behind a machine link is answered through that link, and a typed decision's `payload.answer` is checked as `mail.send` checks it; production approvals are answered with `approval.grant` or `approval.deny` instead). `captain.dismiss {id, note?}` ends an open request, decision or `needs_hands` ask as `dismissed` with the note as its `end_reason` (at most 2000 bytes), and the asking ship gets one notice from the captain, correlated to the request and carrying `request_end` state `dismissed`, saying it was closed without an answer; a notice to the captain is instead marked `acknowledged` and leaves the captain's unread `mail.inbox`. A dismissal drops the item from `captain.waiting` and `runtime.needs`, crosses a machine link like a reply, and a desk copy closes through the same closures as answered and withdrawn asks. Both take the full id or a unique prefix (such as the eight characters `/waiting` shows): an exact id always wins, an ambiguous prefix is refused listing its matches, and an unknown id is refused by name. Both are operator commands; `privateer reply ID TEXT` (as the captain) and `privateer dismiss ID [REASON]` call them, and the Telegram door offers `/dismiss ID [reason]`. The operator reads the captain's whole mail history, a page at a time, with `captain.feed {after?, before?, limit?, ship?, include_ship_mail?, states?, open_only?}`: every message to and from the captain in every fleet home on this machine, in time order, as `{entries, more, next}`. Each entry carries `id`, `ship` (the ship the captain is talking with), `home`, `from`, `to`, `kind`, `request_kind`, `urgency`, `created_ms`, `body` and `payload` as stored, `correlation`, `task_id`, `state` (`open`, `answered`, `dismissed`, `withdrawn`, `acknowledged`, `approved`, `denied`, `task_done`, `task_cancelled`, or null for a reply or an unacknowledged notice), `end_reason`, `answered_by`, `answered_ms`, `ended_by`, `ended_ms`, `deadline_ms` and its own `cursor`. A cursor is the opaque composite (created_ms, home, seq), so the order is the same across homes; `next` passed back as `after` continues forward, `before` alone pages backward (each page still oldest first, `next` passed back as `before`), and either bound may also be a time in milliseconds (`before: now` reads the newest page). `limit` defaults to 50 and is capped at 200; each home is asked only for the page past the cursor, and a page ends where the slowest home stopped reading, so no entry is skipped or repeated. A message held in two homes (a delivered copy, a desk copy) is one entry: an open copy if any, the original among equals. `ship` keeps one ship's mail with the captain; `include_ship_mail` adds the other mail in those homes (ship to ship, crew and runtime notices), of that ship when `ship` is set. `states` (or `open_only: true` for `["open"]`) filters by stored state over the whole history, not only the pages read. Mail another machine's ships write to the captain appears through the desk home that collected it, named by its asking ship; this machine's captain mail held on a desk elsewhere, and other machines' homes, are not read: the feed adds no machine-link traffic. The operator reads one ship's configuration, read-only, with `ship.profile {ship}`, so the captain's portal never reads ship folders. It returns `{ship, machine, hosted, sleep: {policy, idle_minutes}, first_mate: {harness, options}, routes: {first_mate|crew|errand: {list, names}}, charter: {actions, active}, permissions: {fleet_mode, fleet_rules, ship_rules}, tool_bundles: {bounded, selected, error}, skills: [{name, description}], plugins: [{name, description}], mcp_servers: [{name, url, description, credentials}]}`. `machine` is this machine's name as its links know it (else the host name). `hosted` is a Herdr-hosted first mate; `sleep.policy` is `after_idle` with `idle_minutes` from `first_mate.sleep_after_secs`, `never` when that is 0, or `not_hosted` (woken per turn, nothing to sleep), with `idle_minutes` null in the last two. `first_mate.options` are the record's options with every value under a secret-looking name (key, token, secret, pass, auth, cred, cookie, session, at any depth) shown as `"<set>"`. Each route kind names the list that applies, `ship` (the ship's own, which replaces the fleet's), `fleet`, or `none` (no list: crew keep the first mate's route, errands the ship's own), and its route names in launch order. `permissions` are the fleet's mode (`standard` or `yolo`) and `claude_allow` rules; ships have no rules of their own, so `ship_rules` is always empty. `skills` and `mcp_servers` are what the first mate's bounded tool bundle plan selects, computed as its launch computes it: skill descriptions come from each selected `SKILL.md`, MCP URLs lose their query and fragment, and `credentials` are the names the server reads, never a ref or value. Without a `tool_bundles` selection (`bounded: false`) the native harness loads its ambient resources, which are not listed; a plan the adapter refuses leaves both lists empty and its public refusal in `tool_bundles.error`. `plugins` are the attended plugins `privateer start` loads for the harness: Claude's `privateer-mail` plugin directory, or Pi's mail, captain and (not OMP) calm extensions. No environment value is read. An unknown ship is refused by name; a ship on a linked machine is refused with `ship <name> is on machine <m>; ask there`, since the gateway serves no profile call; agents are refused. A ship can live behind a peer (`location: {"peer": name}`): mail to it is recorded first as an outgoing copy, then delivered through `peer.call` to the other home's `mail.deliver`, which accepts it only from a ship it knows to live behind a peer and only for a ship it hosts. A failed attempt leaves the copy pending, counted in `status`, until `mail.flush` delivers it; redelivery is idempotent. Each home keeps its own copy of a request, and the reply closes both. Task ids and captain mailbox storage stay local to their home; see the [dashboard](dashboard.md) for the captain's fleet view. The older `message.send`/`message.inbox` commands remain for now. See the [conversation and activation design](design/conversation-and-activation.md) for where mailboxes lead.

`mail.send` accepts at most 64 KiB of serialized JSON arguments. New outgoing mail must also fit that bound after normalization into the receiving home's envelope, including generated ids, defaults, timestamps and reply deadlines. Rejection rolls back the outgoing record and leaves a correlated request open. Transport correlation ids are separate from the durable message id, which is preserved across delivery and replies.

Outgoing delivery keeps sequence order within each peer and selects the peer attempted least recently, so one unavailable destination cannot hide other peers behind its backlog. A new remote send makes at most one network attempt for that peer, which may deliver an older queued message; the returned record shows whether the new message remains pending. Failures preserve the mail and record a durable retry delay, starting at one second and doubling to at most 60 seconds; automatic sends and dispatcher passes honor that delay across restarts. An agent cannot deliver another sender's mail or bypass it in the peer's queue. Explicit `mail.flush` bypasses the delay, uses configured peer timeouts, and attempts a failed peer only once per invocation. Its `limit` bounds network attempts; each invocation examines at most `limit + 50` records, including local classifications. Immediate sends examine at most 51 records under their one-attempt budget. Large invalid backlogs may require several passes. The flush result reports `delivered`, `attempted`, active `pending` mail and total `quarantined` mail visible to the caller.

An older binary could accept outgoing arguments that fit 64 KiB but whose normalized receiving envelope exceeds it. When such a record reaches an eligible queue head, delivery records `delivery: "quarantined"`, a bounded `delivery_error`, and a `mail.quarantined` audit in one transaction. This classification uses the local envelope bytes, never an error string from a peer. It sends nothing, consumes no network attempt, and changes no peer retry state. The original message id, sender, body, payload and request state remain unchanged; the quarantined row stops blocking the active FIFO and is excluded from `history.prune`. Transport errors and remote refusals remain pending with normal backoff. `status.undelivered_mail` includes pending and quarantined mail; `status.quarantined_mail` reports the quarantined subset.

Inspect outgoing delivery with `mail.outbox {"delivery":"quarantined","limit":40}`. The optional `delivery` filter accepts `pending`, `quarantined` or `delivered`; omitting it lists all three states for cross-home outgoing copies, excluding local-only mail. It returns headers, request state, correlation, attempts and errors without loading bodies or payloads; follow `next_after_seq` with `after_seq` until it is null. The default page is 40 records, capped at 100. Operators may filter by `from`; agents see only their own outgoing mail even when they omit that filter. Error display is capped at 1,024 characters without changing the stored diagnostic. `mail.show {"id":"..."}` reads the full original record and delivery metadata; quarantined records remain readable after restart or `history.prune`.

Quarantine recovers queue progress and visibility; it does not rewrite conversations. Replaying the original id returns the unchanged quarantined record, and changed content under that id is refused. A corrected notice or request needs a new id and may refer to the retained original; an original open request stays open. A legacy oversized reply may already have closed its sender-local request while the remote request remains open. A second reply to that locally answered request is still refused: coordinate explicitly in a new thread, retaining the original reply and correlation for investigation. No automatic request closure, reopening, in-place repair or retry of an unchanged oversized envelope is implied.

## Waking first mates

A ship hosted here can have a first-mate profile (`ship.put` with `first_mate`): the harness plugin manifest and options to launch, a duty task owned by the ship whose charter its first mate works under, and activation settings. `privateer serve` is the dispatcher, meant to run as a background service; `serve` with `{"once": true}` performs a single pass. Each pass reconciles unsupervised jobs and repairs completed jobs whose reservation release was interrupted, records finished wakes, and wakes due first mates before attempting outgoing delivery. Job status, list, and retry decisions use durable records without reconciling them. On Linux, a process record carries the PID namespace its recorder saw the PID in, and each pass records the dispatcher's own. `job.start` and workspace allocation refuse a caller in another PID namespace, such as a PID sandbox, because work recorded there could not be settled from outside it. A reader in another namespace treats recorded processes as alive rather than taking a numeric PID probe as proof of exit. `serve` accepts `delivery_budget_ms` (1–120000, default 10000): each automatic peer call uses at most the remaining network budget for that pass. A slow peer therefore delays the next local pass only by that budget rather than by every queued message's timeout; durable attempt order gives other peers their turn on later passes. Routes needing a longer deadline can use a larger budget or explicit `mail.flush`. It makes no model calls, and only one dispatcher runs per home (an exclusive lock on `<home>/serve.lock`); agents cannot run it.

Mail is the durable record of a pending wake. A first mate is due when its ship has mail newer than both its acknowledgement and its last successful wake, at least one message is not a low-urgency notice (routine notices wait for the next real wake), and the batching window (`batch_secs`) has passed since the newest actionable message or the oldest has waited `max_delay_secs`. Eligibility examines the whole backlog; each wake covers the oldest contiguous page of at most 200 messages. A routine-only page advances while actionable mail waits behind it, without covering or acknowledging the later page. Successful wake coverage advances to that page's last sequence; failed wakes do not advance wake coverage. The prompt still bounds message summaries and may omit bodies with an instruction to read `mail.inbox`; selected-page coverage does not prove every body was rendered or handled. Coverage never acknowledges mail: unread facts stay durable until the harness explicitly acknowledges them, and open requests survive retention. Large backlogs may take several wakes and remain subject to the hourly budget. A ship whose first mate is already awake is not woken again; an hourly wake budget (`max_wakes_per_hour`) and a backoff after a failed wake (`retry_backoff_secs`) apply. A wake runs the first mate through `agent.start`, with the wake's text (a summary of requests owed and owing, the new mail, and what to acknowledge) appended after the stable brief so the brief remains a cacheable prefix. A wake covers mail through its sequence number whether or not the first mate acknowledges it, so a forgetful agent is not woken repeatedly. `wake.list` shows each wake's coverage, job, outcome and the token usage its harness reported (Codex per-turn usage is summed; a cumulative result is taken as reported). Context follows the focus, so a first mate that starts fresh can keep working without carrying old conversations. Each message belongs to a focus: a task the ship owns (`task:<id>`, from the message's task or the request it answers), a request thread (`thread:<root id>`), or the captain's conversation (`captain`); `ship` holds the ship's long-lived knowledge. The wake presents its page grouped by focus: first the ship's bearings (open tasks, requests owed and owing, unacknowledged mail and the ship note, built from records with no model call), then each focus in play with its handoff note and its new mail. A wake whose oldest wake-worthy mail concerns a task the ship owns runs under that task when it has active `spawn` authority; otherwise under the duty task. `wake.list` records every focus a wake covered. A quiet ship whose open tasks nothing will start is mailed one bounded backlog notice by the dispatcher (`backlog_alarm_secs`, see [the backlog alarm](scheduling.md#backlog-alarm)), which wakes it through these same paths.

Notes hold judgement; the runtime already records facts. `note.put` replaces a focus's note (2 KB, or 4 KB for `ship`) and keeps the last five versions; a note of 200 bytes or more whose words average over twelve characters is refused as text squeezed by dropping spaces. A crew task's assignment is the focus `assignment:<task>` (16 KB): `note.get` for `task:<task>` returns it as `assignment`, so the crew read it with their note, while wakes load only handoff notes. `note.pin {ship, focus, key, value}` keeps up to eight one-line facts per focus (an empty value unpins); `note.get` returns them and every wake shows them for each focus in play, resumed or not; `note.get` and `note.list` read them, and the wake asks the first mate to update the note for each focus it worked on. `focus.digest` returns a focus's history on demand, curated and bounded: a task's events, jobs and mail, a thread's messages in order, or the captain's conversation. A ship's backlog is its open, unstarted tasks (the duty task excepted): `task.backlog {ship}` lists them next first, ranked tasks by rank and the rest oldest first, and `task.rank {id, rank}` (1 starts first; null clears) lets the owning ship or the operator reorder them; `privateer backlog [TASK RANK|clear]` does the same for the captain in a ship's folder. The bearings list work in hand before the backlog, and a blocked task leaves the work in hand with its blocker recorded rather than holding a place. `ship.bearings` returns the summary on its own, including `idle_tasks`: tasks the ship marks running with no live job on them or any task beneath them, no open request the ship sent about them and no pinned `waiting` fact (the duty task excepted). Agents read and write these only for their own ship. `history.prune` drops notes for finished tasks and threads whose latest note predates the cutoff, keeping captain and ship notes. A wake whose mail all belongs to one focus resumes that focus's native session when it is warm: the harness reported the session at start-up (decoded from its JSON events, mirroring `plugins/native_events.py`), its last turn ended within `cache_window_secs` (default 300, while the provider's prompt cache is likely warm; 0 disables resuming), and it has had fewer than `session_max_wakes` wakes (default 6). A resumed wake passes the session to the adapter's explicit `resume` option and sends only the wake text, without the brief, bearings or notes the session already holds. Otherwise the wake starts fresh, and a single-focus fresh wake becomes that focus's session; mail spanning several foci never resumes one focus's conversation, and a failed wake drops the focus's session. Sessions rotate after `session_max_wakes` instead of compacting. `wake.list` shows each wake's mode and session. The rotation limit counts wakes rather than tokens, because harnesses report usage differently (per turn or cumulative); see the [design](design/conversation-and-activation.md#context-and-cost).

### Dispatcher restarts

A resident `serve` start takes the home lock, atomically clears native sessions and records a new dispatcher generation before its first pass. Wakes retain their launch generation: an old wake may still finish successfully and cover its recorded mail, but cannot restore or delete the new generation's warmth. Legacy wakes without a generation are likewise fenced after the first resident start. Ordinary Store opens, ticks and `serve {"once":true}` are maintenance operations, not restart boundaries; they do not reset sessions. A one-shot pass still holds the same exclusive lock and cannot run beside a resident dispatcher.

Generated dispatcher units use `KillMode=process`, and on macOS dispatcher launchd agents (`~/Library/LaunchAgents/privateer-SHIP-<hash>.plist`, loaded into the login session's `gui/UID` domain) set `AbandonProcessGroup`: stopping/restarting the dispatcher leaves independent job supervisors and their payloads alive. Both restart a dispatcher only after a failure, record the current `PATH`, and are stopped by `service stop` (`launchctl bootout`), which then waits for the home lock to be released. Detached stop also signals only the recorded dispatcher, never its process group. On the next start, recorded job identities and outcomes, not parent-child relationships, determine whether a wake is still running. A missing supervisor with a live or uncertain payload remains blocking; it is not proof of payload death and must not trigger a duplicate wake. If the supervisor was lost, a successful payload result cannot in general be recovered: inspect/cancel/recover explicitly rather than fabricating success. Mail arriving meanwhile remains durable and is covered by the next eligible wake, after the adopted wake's sequence. Successful coverage suppresses replay; this is not a promise of exactly-once external effects if a harness crashes or explicitly acknowledges mail it has not handled.

`service stop` repairs a legacy dispatcher's unit stop policy and requires a successful daemon reload **before** stopping it. Direct `systemctl restart` of an old, unrefreshed unit is still unsafe: the future upgrade orchestrator must install/reload the safe policy first. Front doors deliberately retain `KillMode=control-group`, since stopping a door must stop its adapter. This does not implement fleet upgrading, draining, approvals, or deployment, and does not keep wakes alive through a host reboot or explicit job cancellation.

## Crew outcomes

Crew are the supervised jobs a ship's first mate starts for the ship's tasks. When a job whose task is owned by a ship hosted here first reaches `succeeded`, `failed`, `cancelled`, `timed_out` or `orphaned`, the runtime writes a notice from the reserved sender `crew` to that ship, in the same transaction that records the status, so a crash cannot separate the two. Its id, `crew-<job id>-<incarnation>`, makes it exactly one per incarnation: an orphan is reported when it is orphaned (it is no longer supervised, so its deadline is not enforced), and its later settlement is not reported again; `job.retry` is a new job with its own outcome. The notice carries the job's task, so it lands in the task's focus, and states the status, exit code, reason, duration, command, log path and the end of stderr and stdout, bounded so the whole message fits what a wake or hook shows (2,000 characters); the payload holds the same fields. Failures, timeouts and orphans are `high` urgency, success `normal`, and a job the ship cancelled itself `low`, which waits for the next real wake. A first mate's own wake jobs are excluded: `serve` records the wake, with its job id, before starting it. Each `serve` pass also reconciles unfinished jobs whose supervisor has gone, so their outcome is recorded without anyone asking for their status.

Crew run as their ship, so they cannot mail their own first mate. The supervisor sets `PRIVATEER_JOB` in each payload's environment; `crew.report` (`kind` `progress` or `decision`, a body, an optional payload and idempotency `id`) is accepted only from the agent a launching or running job works for, on a task its ship still owns, and never from a wake job. Progress is a `low` notice; a decision is a `high` request the first mate answers with `mail.send` kind `reply` to `crew`, which the crew reads with `crew.answer` (optionally waiting up to `wait_secs`). `crew` has no mailbox otherwise: nobody, the operator included, can send as it, mail it anything but a reply to its request, or name a ship after it.

## Errands

A first mate's own conversation is its ship's portfolio, and whatever it reads stays there; reviewing crew by pulling their logs and sources into a live first mate's thread filled its context within an hour. `errand.start {focus, brief}` runs that thinking elsewhere: a short headless session for one `task:` or `thread:` focus of the caller's ship, launched like a wake (in the ship's folder, with the ship's harness, model and charter, no workspace and no live pane). Its first prompt is the brief and the focus's records (handoff note, pins, task and crew assignment), not the first mate's thread, and it is told to end with its verdict as its final reply. When its job ends, the dispatcher reads that reply from the harness's event log (Pi `message_end`, Codex `agent_message`, Claude `result`) and mails it to the ship from `crew` on the focus's task (the duty task for a thread), bounded to 4,000 characters with the log path for the rest; an errand that ends without a reply is reported as failed, at high urgency. Its job's own crew outcome is not mailed. A successful errand keeps its session under the key `errand:<focus>`, and the next errand on that focus resumes it with only the new brief while it is warm (`cache_window_secs`, `session_max_wakes`); a failed one drops it. A stow holds new errands like other jobs. `errand.list` shows them, and the bearings list errands still running.

## Attended mode

While the captain talks to a ship's first mate in an interactive session, that session is the first mate. It holds the ship's presence lease (`ship.attend`, `ship.leave`, `ship.presence`), and `serve` skips headless wakes for an attended ship, leaving its mail to the live session; when the lease is released or lapses, headless wakes resume. `privateer start [HARNESS] [-- ARGS]` claims the lease in a write transaction before spawning the ship's harness, or the one named, in the ship folder under the agent role as the ship. A live lease rejects another start, and a failed spawn releases the claim. The runtime refreshes the lease with a heartbeat while the harness runs and releases it on exit. For Claude Code, `privateer init` installs hooks (`privateer hook claude EVENT`) that take the lease at session start and show the bearings and new mail, show newly arrived mail with each prompt, keep the first mate working at turn end when unseen mail has arrived (exit status 2 with the mail as the reason), and release the lease at session end; a hook-held lease lapses after 30 minutes without activity. Each message is presented to the session once, so a first mate that does not acknowledge is not prompted in a loop. Hooks never fail the harness: errors allow the event and go to `<home>/hooks.log`. Other harnesses read their inbox as `AGENTS.md` directs. Attended Pi-family first mates also load the captain's fleet commands (`plugins/attended/captain.ts`): `/stow [status|resume]`, `/yolo [on|off|status]` and `/ships`, the commands a front door offers; the attended Claude mod registers the same commands, and also reports attention and nudges idle tasks as described below. A slash command is typed by the person at the keyboard, never by the first mate's model, so these run the CLI as the captain, without the session's agent role; headless wakes and crew never load them. A live Pi first mate continues one thread, so its session would otherwise compact only when its context fills, often mid-task. The same mail adapter compacts it earlier, when that is cheap and safe: the session has been idle for `quiet_compact_secs` (default 600, past the prompt cache's life, so the next turn would pay for the whole context anyway; 0 turns it off), its context is at least `quiet_compact_percent` full (default 40), no draft is in the editor and this session holds the ship's presence lease. Pi keeps recent turns verbatim; the compaction instructions ask the summary to quote every unanswered captain question and unkept promise, and afterwards the ship's bearings and captain note are attached as a context message, built from records with no model call. It compacts at most once per quiet period, and a failure waits for new activity before trying again. Because a Pi turn ends as soon as the model replies without a tool call, a first mate can announce work and stop. Before a completed run settles, the adapter reads `idle_tasks`; if any exist, it adds one message listing them and asks Pi for one more step, so the first mate continues them or records why they wait (a blocked task or a pinned `waiting`). It nudges once per distinct set of idle tasks, never after an aborted or failed run, and only in the session holding the ship's lease. The same adapter reports the ship's attention: after each settled run its live context (`attention.report`, kind `turn`, from Pi's context usage) and after each compaction the tokens before it and the summary's size (kind `compaction`), from the session holding the lease. The bearings turn the last hour of reports into `attention`: how full the context is, how much was added (rises between runs, with a compaction resetting the baseline), compactions and unread crew reports. It reads high, with its reasons, after a compaction in the hour, at 75% full, when half a window was added in the hour, or with five unread crew reports; these thresholds are provisional. The brief asks a first mate to start no new task while it is high. There is no fixed limit on tasks; reports older than a day are pruned. See [Boarding and management](dashboard.md#boarding-and-management) for Herdr presence bindings and their refresh/expiry rules.

### Hosted first mates

With `first_mate.host = "herdr"` (set through `ship.put`; `init` keeps it), the dispatcher keeps the ship's first mate as a live interactive session in its own background Herdr space, so it shows in Herdr's agent list with its history and the captain can read or type to it. On every ordinary `serve` pass (including `{"once":true}`), even with no wake-worthy mail, it claims the presence lease for a `host:` holder, creates the space (labelled with the ship's name, without taking focus) and runs `privateer start --hosted` in it. That session adopts the lease rather than claiming a new one, binds it to its pane, and carries on the ship folder's latest conversation (`--continue`). Its attended mail adapter starts a turn when actionable mail arrives; after a native error it retries a minute later instead of waiting for the captain. While the hosted session lives, `serve` leaves the mail to it; when the session exits its lease is released, and an unadopted launch lapses after 60 seconds. Launch admission checks attendance, running wakes, tool-permission pauses, native harness compatibility, duty ownership/effective charter, cwd and the selected provider adapter/options. `start --hosted` rechecks these before adopting; unsupported custom adapter/config routes fail closed rather than being silently replaced by native defaults. Native HOME/auth configuration and the configured provider/model route are preserved. A per-ship `host_launches` row reserves the next retry atomically with the launch lease, before host I/O. Refused or unadopted launches back off from 60 seconds exponentially to at most an hour, surviving dispatcher restarts; errors are bounded to 2,000 characters. An adopted native process resets the consecutive launch count but keeps the reserved deadline, and an unsuccessful native exit also reserves at least a minute. Backoff ticks neither reattempt the host nor append repeated errors; reports expose `host_backoff_until_ms`. A later due pass can recover without new mail. If Herdr is unreachable (its socket is `HERDR_SOCKET_PATH`, or `herdr/herdr.sock` under the user's config directory), the headless wake runs as before when mail is due; the failed-attempt report carries `host_error`, and later fallback reports carry the durable host backoff deadline instead. Host retries do not consume or acknowledge mail, spend headless wake budgets, or construct model prompts. Pi, Pi-signed and Claude first mates can be hosted, since their attended adapters start turns on mail. A hosted Claude first mate needs Claude's folder trust already accepted for the ship folder itself (read from Claude's `.claude.json`, which Privateer never writes; trust on a folder above does not cover a folder with its own permission rules, which every ship folder has); otherwise the launch is refused with that instruction, because an untrusted interactive Claude stops at a dialog whose default exits. The same one-time `privateer start claude` in the ship folder also clears auto mode's first-run setup screen (a summary of what it will treat as sensitive, ending in "Looks good — save it") when the ship uses `"permission_mode": "auto"`; Privateer cannot see whether that screen was finished, and a hosted session left on it holds its lease without handling mail. It passes the ship's `permission_mode` and `effort`, and continues the folder's latest conversation only when Claude holds one there, since an interactive `--continue` with none exits. Hosted crew remain Pi-only. Hosted turns are not wakes: they are not batched, budgeted per hour or recorded with usage.

A hosted first mate can sleep to free memory between conversations. Once its mail adapter has reported the session idle for `first_mate.sleep_after_secs` (default 1800, past the prompt cache's life and quiet compaction, so a first mate the captain is talking to stays up; a ship recorded before the setting existed uses the default; 0 never sleeps) without a break (no turn, queued delivery, work offer or draft in the editor; a busy report, a new session or 30 seconds without a report starts the count again) and no scheduled work is ready, `start --hosted` stops the native harness: in one transaction it rechecks all of that, moves the ship's presence lease to a new `host:` holder, so the adapter delivers nothing more, and records the mailbox's latest sequence; then it sends the harness SIGTERM (SIGKILL after 10 seconds) and waits for that process itself to exit. The launcher execs the harness, so the wait proves the payload stopped. The pane stays, holding and refreshing the lease, restores the terminal and says the first mate is asleep. Because the ship stays attended by a hosted holder, `serve` opens no other space and starts no headless wake. Actionable mail that arrived after it slept, scheduled work becoming ready, or Enter in its pane (a line typed before it is first mailed to the ship as the captain, as in `privateer watch`) rechecks hosted admission and starts the harness again in the same pane on the same conversation (`--continue`), as the holder the lease now names. Low-urgency notices wait for the next wake. Herdr lists only panes in which it detects an agent, so while asleep the pane reports itself as the ship's agent under the label `privateer` (`idle`, with the message that it is asleep and that focus or Enter wakes it), with the ship as its display name. Herdr drops a report that names the agent it recorded as exited in that pane, until it detects a new agent process, so the harness's own name is never used. Each report is read back with `pane.get`; a pane Herdr does not list as the sleeping ship is warned about on the pane and audited once per sleep as `host.report_ignored`, with what was sent and read back. `herdr agent prompt` cannot reach a pane under this label, so Enter typed in the pane (`pane.send_input` text plus Enter), moving to the pane in Herdr, or mail wakes it. Moving to the pane also wakes it, unless the pane was already focused when it fell asleep or Herdr cannot report focus. The report is released before the harness starts, so Herdr's own detection takes over; a release Herdr does not confirm is audited the same way. If the lease lapses or is replaced while asleep, the pane exits and an ordinary launch follows. Audit records `host.slept` and `host.woke` (with the reason). A ship with bounded tool bundles starts fresh on every launch, so its first mate also wakes into a new conversation. The pane keeps the settings it started with; changing the first mate's route or `sleep_after_secs` takes effect at its next launch from the dispatcher.

A hosted pane keeps the release it started from, so after an upgrade it would otherwise run old code indefinitely (and its old release could not be pruned). `start --hosted` records its own process identity (PID and kernel start time, not a bare PID) and its release, and records each native harness it spawns. Bearings report the pane's live release, `commit`, with `current_commit` and `drift`, and `privateer upgrade status` lists every hosted pane in the home as `hosted_panes`. A pane is behind when its release differs from the one `current` selects, or when its binary was replaced on disk (Linux's ` (deleted)`). An unversioned build is never behind, since relaunching it would start the same binary again; with no selected release nothing is behind. Relaunch moves a pane onto the current release at a safe point, never mid-turn. `privateer host relaunch SHIP` (the operator, or the machine's owner; agents are refused) asks the pane to relaunch. It refuses while a fresh report says a turn is running, unless `--force` is given. The pane's supervisor then stops its harness, waits for that process to exit, releases the lease and ends. The command then launches a fresh pane on the current release, which resumes the conversation (`--continue`), and reports whether the old harness exited. Without a request, a behind pane catches up on its own once it has been idle for its sleep threshold, or 60 seconds when `sleep_after_secs` is 0. An asleep pane that is behind ends at once, and the dispatcher launches the current release for the next mail or pass. A planned exit clears the launch backoff its launch reserved, since it is not a failed launch. A request that no pane takes within ten minutes lapses, and the command withdraws its own request after 90 seconds.

The same dispatcher pass checks the exact pane bound to each hosted lease using the Herdr snapshot it already reads for sidebar repair. A continuously `blocked` pane starts a five-minute timer; after that, the captain receives one normal-urgency mailbox notice from `crew` on the first mate’s duty task, naming the ship and saying its live session is waiting for input in Herdr. The bounded timer and sent flag clear on a known `idle`, `working` or `done` status and are removed when the hosted lease ends. Missing or `unknown` status neither starts nor clears a timer. The alert leaves the live session untouched for the captain to answer.

A hosted ship's crew run live too. When its first mate starts crew (`agent.start` outside a wake) and Herdr answers, the harness is planned interactively, with the crew extension (`plugins/attended/crew.ts`), and the job is marked `hosted`. Its supervisor (`_job-supervise`) runs in a background space labelled `└ TASK` instead of detached. Custody is unchanged: the supervisor claims the job there, checks authority, and starts the harness in its own process group, now the pane's foreground group with the pane's terminal instead of log pipes. Timeouts, cancellation, admission and crew outcome mail work exactly as for headless crew, but the job's logs stay empty; the session's own history holds the transcript. The crew extension shuts the session down when its work settles, exiting with status 1 when the last turn failed, so the job ends as usual and its space closes. The captain can watch or type into a crew at any time; interrupting a run (Esc) keeps the crew open until its next settle. A space that never runs its supervisor leaves the job unsupervised, and reconciliation fails it after 30 seconds. Only Pi and Pi-signed crew are hosted this way. Crew on any other harness (Claude, Codex) run headless as usual, since an interactive Claude in a fresh workspace can stop at its folder-trust or auto-mode setup screen with nobody there, and a headless run's completion is confirmed from its event stream. When the ship is hosted and Herdr answers, `agent.start` then also opens a viewer space labelled `└ TASK` running `privateer watch --job ID` (reported as `viewer` in its result). The view follows the job's log, reports the crew to Herdr as working, done or blocked (titled `SHIP crew on TASK`), and closes 30 seconds after the job ends. A headless crew takes no input mid-run, so lines typed there go to the ship's first mate as a captain notice on the task. The view runs as the operator although a first mate started the crew: its command is fixed, reads only records and logs, and mails only what is typed in the captain's terminal. A refused viewer space never stops the crew.

Privateer tags the spaces it opens (`workspace.report_metadata`, source `privateer`, tokens `privateer` = `mate` or `crew` and `ship`) and keeps them together at the top of Herdr's sidebar: the bridge first, then each ship's first mate followed by its crew, ships in first-mate sidebar order (then ship name for ships without a first-mate space). Crew without a first-mate space follow all first mates. Arranging recovers missing first-mate tags from live hosted presence bindings, checking the socket incarnation and terminal identity; dispatchers also repair their own bound mates each pass. Fleet recovery reads existing homes without creating or migrating them. While hosting is enabled, host orchestration maintains one background bridge for the machine's per-user fleet registry; a shared durable claim and the direct dashboard's lifetime lease serialize independent homes. It tags only its verified launched bridge, never an arbitrary dashboard's space. Bare operator entry focuses that existing bridge only after revalidating its claim, socket/pane/terminal/session, hosting home and live lease; otherwise ordinary inline dashboard/onboarding fallback remains. Dashboard observation never creates/reorders/focuses spaces. See [Hosted machine bridge](dashboard.md#hosted-machine-bridge) for ownership, conservative recovery and the first-under-Local ordering limitation. The captain's other spaces stay below, in their own order. Arranging is presentation only; a refusal never affects a launch.

While a hosted first mate has errands running, its Herdr pane shows a caption such as `infra · reviewing dashboard-102 +1`: the oldest running focus and how many more there are. Only sanitized, bounded focus IDs are shown, never task titles, briefs or mail. The caption is sent with `pane.report_metadata` under its own source, `privateer-errands`, which sets only `display_agent` and is cleared when the last errand settles; the pane's other metadata, its lifecycle, session and focus are untouched. Starting and settling an errand and every dispatcher pass bring the caption up to date. Each ship's last sent caption is recorded before it is sent, so a fresh dispatcher does not send it again, and one Herdr did not confirm is sent again on the next pass. Herdr is never called inside a database transaction.

A caption is shown only on this home's own local ship, while its live hosted lease matches its launch record, its harness matches the bundled one, and its duty task is open and on an active charter. The pane must still be the one the lease was bound to (the same socket, pane, terminal, workspace and tab, and the recorded session if there is one), run no other agent, and be claimed by no other presence. Otherwise nothing is sent and the record is dropped without clearing a pane that may now belong to something else. This is display only: it grants no input, navigation or lifecycle authority, and a failed caption never fails an errand.

## Getting aboard

Git-backed crew work uses built-in [task workspaces](workspaces.md). Privateer
owns each task's durable Treehouse lease, plans its harness against the isolated
checkout, and pins subsequent jobs to that lease. Workspace release verifies
processes and preserved/landed work; it never follows from a process exit alone.
First-mate wake and interactive sessions retain their existing ship repository.

Bare `privateer` is the everyday entry point. See
[First run and everyday entry](dashboard.md#first-run-and-everyday-entry) for
installed dashboard entry, liaison handoff and onboarding conditions. When
the dashboard is unavailable, the legacy flow applies: Inside a ship folder (any folder at or below one holding `.privateer`), it makes sure the ship's dispatcher is running and then runs `privateer start`. Elsewhere it asks whether to make the current folder a ship, naming it after the folder and choosing the first installed harness, then does the same; without a terminal to ask in it prints help, and `--yes` skips the question. It refuses to make the user's home directory or `/` a ship. The dispatcher is installed as a systemd user service where a user manager is available (the unit records the current `PATH`, where harnesses usually live, and `PRIVATEER_RESOURCE_HOME`/`PRIVATEER_PLUGINS` when set) and otherwise started as a detached process logging to `<home>/serve.log`, rotated at 1 MiB. A dispatcher holding `serve.lock` counts as running however it was started, so nothing starts twice. `privateer service status|start|stop` manages it; stopping a detached dispatcher signals the recorded process only while it still holds the lock and is that home's `serve`. `PRIVATEER_SERVICE=systemd|detached|none` overrides the choice.

`privateer init --liaison` makes the captain's contact: a ship the captain
reaches from the dashboard, a terminal or a front door, which acts on their
behalf. Its charter holds the default actions of any captain-made ship
(everything but `deploy_production`), so the ships it creates inherit working
authority, and it can provision them itself: `ship.create`, `ship.actions` and
`project.add` need no trip to the command line. Production deployment stays
with the captain under explicit approval. Generated first-mate onboarding
instructions ask about work and preferences, propose peer ships and actions,
create them, add their repositories, and explain dashboard and direct access.
They store lasting preferences in the ship's `ship` note and onboarding
progress in its `captain` note. Ordinary init retains the preset and uses the
persisted ship identity unless a ship name is explicitly supplied with
`--ship`. Existing charters remain captain-owned: re-running init upgrades only
a liaison still holding the earlier contact-only preset (`inspect`, `spawn`,
`message`) at its first revision, never one the captain has edited.
Independently authored `AGENTS.md` files are preserved, while Privateer-managed
instructions are refreshed with the checklist when the preset is active.
A validated `agent.start` harness job runs under `spawn`
authority; ordinary `job.start` requires an implementation/test/
recovery/cleanup action and cannot request `spawn`, so a captain who narrows
a liaison to read/message/delegate still has it process mail headlessly.
The instruction checklist is not proof of a model-driven onboarding outcome.

### Replacing the installed executable

[Versioned releases](releases.md) keep each running binary paired with its own bundled plugins. In that layout, persisted command paths use `current/bin/privateer`, while internal supervisors retain the running image. `privateer upgrade status` reports the selected and running commits separately and reads recorded fleet outcomes; it does not perform an upgrade.

On Linux, a running dispatcher can outlive an atomic replacement of its installed binary. Job supervisors reexec the dispatcher's retained image through `/proc/self/exe`, so an upgrade does not mix versions of the internal supervisor protocol. Agent control argv, hooks, and newly recorded peer/service commands instead use the installed path: a `/proc/self/exe` alias must never be passed to another process as its control CLI. The resolver checks the running image identity before interpreting Linux's ` (deleted)` marker, preserves literal filenames with that suffix, and never searches `PATH` for a substitute.

The installed replacement must remain a regular file executable by the runtime's effective credentials. If it is missing or not executable, control-command creation fails with the path and restore/restart guidance. On Linux, replacing or removing the installed file leaves the retained image available for ordinary job supervision, but changing execute access on that retained image can still prevent a supervisor launch. Other Unix platforms use the OS-reported installed path for supervisors and validate it before job admission. A supervisor spawn failure marks the admitted job failed and removes its capacity reservation or queue entry.

Compatibility between different releases of the external CLI protocol is not verified. Restart dispatchers after installing an update to activate its runtime changes. Already-running dispatchers from before this fix still need a restart, and existing records or agent sessions containing stale CLI paths are not automatically rewritten.

## The fleet

Every ship made with `privateer init` or `ship.create` joins a per-user fleet registry (`PRIVATEER_FLEET`, or `$XDG_STATE_HOME/privateer/fleet.sqlite`, default `~/.local/state/privateer/fleet.sqlite`), and is linked both ways with every other active ship: each home gets a local-transport peer `fleet-<name>` and a directory entry behind it, so ships mail each other without manual setup. A name belongs to one active ship; a ship whose folder was deleted no longer holds it, and linking never recreates a deleted folder. `fleet.list` shows the registry and `fleet.link` relinks this home.

A ship manages the ships it created. Anything beyond that is a **standing grant** from the captain: `privateer grant add SHIP --actions ship.scope,ship.retire --ships A,B [--notify] [--expires-hours N] [--note TEXT]` (`grant.put`, operator only) lets one ship take the named actions on the named ships of this machine. The actions a grant can carry are `ship.retire`, `ship.scope`, `ship.actions`, `ship.consumes` and `project.add`. `grant pause|resume|revoke ID` take effect at once, an expired grant stops by itself, and a ship may list the grants it holds (`grant.list`). Each use is audited in the grantee's home as `grant.used`, and a grant with `notify` also mails the captain a notice. A grant never widens a ship's own charter; it only lets the ship act on others.

`ship.consumes {name, consumes}` records the ships a ship uses, such as an app and the server it relies on, and `ship.consumers {name}` lists the ships this home knows to consume one, so a server ship finds who to tell when a contract they rely on changes, without a hand-kept list. Like a scope it routes and grants nothing: a ship may set its own, otherwise only its creator or the operator, and only ships the ship knows can be named. It is written to every home on this machine at once and travels to linked machines with the next directory exchange; a `ship.put` that does not name `consumes`, such as a directory refresh, keeps it.

### Linked machines

`privateer machine add NAME SSH_TARGET --executable /remote/privateer [--remote-fleet PATH] [--as THIS_MACHINE]` (operator, `machine.add`) links this machine's fleet with another machine's, once, from the side that can connect. One call to the other machine's gateway (`privateer [--fleet PATH] gateway`, one JSON request per line over SSH, like `rpc`) exchanges both ship directories and records the link in both registries. Every home on either side then gets a single peer, `machine-NAME`, with a directory entry behind it for each of the other machine's ships; homes created later get them when they are linked. Ship names stay bare mail addresses and are unique across linked machines: a link whose fleets share a name is refused on both sides, and `init` and `ship.create` refuse a name a linked machine holds. `machine list`, `machine refresh [NAME]` (re-exchange directories now), `machine collect [NAME]` (collect now) and `machine remove NAME` (forget the link and its directory entries here only) complete it.

A link is one-way: the linking machine reaches the other's gateway, which never connects back. Mail to the other machine goes out through the usual outbox, and the gateway hands it to the recipient's home's `mail.deliver`, with the sender's identity carried as narrowing flags as for any peer; the gateway lets agents only deliver mail, and linking and collecting are the operator's. On the other machine the linking machine's peer has transport `collected`, so mail for its ships stays `pending` and is never attempted. Each pass, one of the linking machine's dispatchers (a lock `machine-NAME.lock` beside the registry, and only dispatchers of homes in that registry) calls `fleet.collect`, delivers each message locally by its id and acknowledges it with `fleet.collected`; a crash in between collects it again and redelivery stays idempotent, and a message the receiving home refuses is quarantined on the sending machine with the reason. A machine is contacted at most every 30 seconds, backing off to ten minutes while it is unreachable, and directories are re-exchanged every five minutes. Each side also states its stows on that exchange, in the request and the reply of both `fleet.link` and `fleet.collect`: the stows in force and the twenty most recently resumed, from this machine's own ledger, bounded so the frame stays small. Each side records the peer's answer in its machines row (`machine list` shows it) and ends any open request bound to a stow that machine reports as resumed, or reports as unknown to it (see [Stowing the fleet](#stowing-the-fleet)); the exchange is the only channel, and a peer too old to report its stows reads as reporting none. By default the captain reads mail on the linking machine, where the front door runs. Mail the other machine's ships write to the captain after the link is made is collected the same way and delivered into the captain's home there, the fleet's liaison or else its first ship, so the door, `/waiting` and `captain.waiting` show it with its sender; it also stays in the writing home's captain mailbox, and a `machine_collected` record keeps it from being offered twice. The door writes the captain's mail to a ship on the other machine in that same home, from where it goes out through the gateway, so requests and replies close on both machines; the door's ship list includes the other machine's ships with their `machine`. `mail.deliver` accepts the captain's mail only from the operator and only across a machine peer, and an agent can never write as the captain. Directory entries for ships retired on the other machine are not removed.

`privateer machine owner SHIP` (operator, `machine.owner`) names the ship that looks after this machine, and `machine owner --clear` clears it; `machine list` shows it. The owner gains no authority over other ships' work. Its own dispatcher checks the machine at most once a minute and mails it a runtime notice (from `crew`, on its duty task, with `payload.machine_alert`) when a host-level problem starts and again when it clears: free disk below the host floor, free disk falling fast enough to reach that floor within `disk_warn_horizon_secs` (default 24 hours) while still above it, the capacity queue's head waiting ten minutes or more, or a model route backing off for half an hour or more. Free space is sampled per filesystem at most once every five minutes, for seven days, by every admitted job and every owner check; when those readings at least half an hour apart describe a rate, `resource.status` reports the trend and the forecast, and the owner is warned before the floor rather than after ([resources](resources.md)). The owner may also stow the machine (see [Stowing the fleet](#stowing-the-fleet)).

Ships can make ships, so the captain can grow a fleet from the first one. `ship.create` (`privateer ship new NAME`) makes a new ship folder, by default beside the creating ship's folder, with the creator's harness unless another is named, starts its dispatcher and links it. When the child uses the same eligible native harness as its creator, it inherits the existing model/provider options and `first_mate.host`; a different harness gets its own defaults, without the creator's host. `ship.create {host:"herdr"}` explicitly selects hosting and `host:null` explicitly opts out. Hosting is validated before creating child state and applied before starting its dispatcher; it does not copy tool-bundle selection, plugin config, activation settings, or change charter delegation limits. Existing ships are not rewritten. An agent needs active `spawn` authority to create ships, and a new ship's charter can hold only actions the creating ship's own charter has; the operator may set any. Creation checks authority under the creator's write lock before publishing the child, serializing that decision with revocation. Cross-home bootstrap and publication are not a distributed transaction, and child charter defaults remain unchanged. `ship.actions {name, actions}` replaces a ship's charter actions; an agent may change only ships it created, only to actions its own active charter has, under its write lock. `ship.scope {name, scope}` changes what a ship is for everywhere the fleet reads it: the ship's own record, every other home's directory entry and its generated `AGENTS.md`. A scope routes work and grants nothing, so a ship may restate its own; otherwise only its creator or the operator may, and the ship is sent a notice. The homes are updated one after another rather than in one transaction, and running it again finishes an interrupted change. `project.add {url, name?, target?}` (`privateer project add URL [NAME] [--ship SHIP]`) clones a repository into a ship's `projects/`: an agent may add to itself, or, with `spawn`, to ships it created; the operator to any fleet ship. The clone is staged in `projects/` and published by rename after authority is checked again under the caller's write lock; agent clones run without terminal or SSH prompts, `ext::`/`fd::` transports are refused, and HTTP(S) credentials in the address are redacted from replies and the audit log. `ship.retire` revokes a ship's charter, stops its dispatcher, unlinks it and marks it retired, keeping its folder; an agent may retire only ships it created. The registry records who created each ship: the creating agent's ship, or the captain when the operator runs `ship new`, even in a ship's folder, whose harness, model and hosting the new ship then only borrows. `ship.retire` accepts optional `expected_home` to reject a name that now belongs to a different home; its final registry update also checks the originally selected home and active status after stopping the dispatcher.

`ship.create {machine: NAME}` (`privateer ship new NAME --machine NAME`) creates the ship on a linked machine this one reaches, over the same gateway link, as that machine's own `ship.create` would. Authority is decided on the requesting side before the machine is contacted, exactly as for a ship created here: the operator always may; an agent needs `spawn` in its active charter, may pass only actions it holds and otherwise gives the new ship its own. That check and a `ship.create.requested` audit entry commit in one short write transaction before the call, so a revoke committed first wins; no lock is held while the machine works, since the call can outlast other writers' wait and a remote creation cannot be rolled back. A revoke committed during the call does not stop that creation; the `ship.created` entry written afterwards notes it, and a failed call is recorded as `ship.create.failed` (a call that timed out here may still have created the ship there). The gateway accepts only `ship.create` for this, from a machine linked to it, and records the creator honestly: the captain when the operator asked, otherwise the requesting ship's name, which name uniqueness across linked machines keeps unambiguous (a name of a ship on the receiving machine is refused). The receiving machine applies its own defaults: the requester's harness, model and hosting are not lent, `harness` and `host` apply only when passed, and the folder goes beside the receiving fleet's captain home (its liaison, or else its first ship) unless `folder` names one there. The new ship joins only the receiving machine's registry; the requesting side then refreshes its directory so the ship is reachable at once, or at the next refresh if that fails. An unknown machine, a link made from the other side, or the machine's refusal is an error naming the machine. Managing that ship across machines (`ship.retire`, `ship.scope`, `ship.actions`) is not supported; it is managed on its own machine.

`ship.move {name, to}` (`privateer ship move NAME --to MACHINE`, or `--here` to bring one back) moves an idle ship between linked machines. The machine that made the link runs the move in either direction, and the other machine takes part through its gateway. The move stops the ship's dispatcher and refuses while a wake, job, errand, held workspace or live session is in flight, or while a project has uncommitted or unpushed work; the dispatcher then restarts and nothing changes. Otherwise the ship's machine stages a snapshot of its database (`VACUUM INTO`) and its folder, leaving out projects and runtime files. The other machine first checks it has the first mate's harness and plugin and can fetch every project, then receives the files in chunks, checks their digests and lays the folder out beside its captain's home. It rewrites what belonged to the old machine (the charter's repository path, peers, sessions, presence, and hosting when Herdr is absent), clones the projects one call each, then registers and links the ship and starts its dispatcher with the login shell's PATH. Only then does the old machine revoke its copy's charter, retire the registry entry, point its other ships at the machine the ship went to, and leave `moved.json` in the old home. Every command refuses to run there, and the folder is kept; a later move back sets that folder aside instead of overwriting it. Each step is idempotent per move, and the running machine records its progress (`moves` in the registry), so running the move again after an interruption finishes it, never undoing a ship that may already be active on the other side. A failure before then is undone on both machines. A ship's mail, notes, tasks and history travel with it; credentials, routes and harness logins are the receiving machine's own.


The captain's desk can sit on the machine the link reaches instead, such as an always-on server while the linking laptop sleeps: `privateer machine captain NAME` (`machine.captain`, operator only; `--here` brings it back) on the linking machine. Each pass then hands the captain mail its homes write after that moment to the other machine's captain home (`fleet.captain` over the gateway) and records what was taken or refused so nothing is sent twice, and stops collecting that machine's captain mail, which stays there for its door. Captain mail is not relayed between machines: a third machine reaches the desk by linking to the desk's machine itself and moving its own desk there too, after which it hands its captain mail only to the desk and a machine collecting from it gets none. The captain's answers come back as ordinary collected mail and close the requests where they were asked. Mail handed to the desk is placed as collected captain mail is: a reply goes to the home holding the request it answers, and a refusal is put before the captain. A ship that moves carries its captain mail, and what the captain already had there, taken by a link or shown by a door, is not offered again from its new machine.
After authorized creation, the child's dispatcher runs as an operator service.
The detached launch clears the creator's execution identity while retaining
configured fleet, resource, plugin and configuration paths. Its first-mate jobs
run as agents bound to the child ship.

## Stowing the fleet

Before the captain updates or restarts Privateer, `privateer stow` (or `/stow` at a front door) checkpoints the fleet. It records a stow in the host's resource ledger, which every home on the host shares, and sends each active fleet ship an ordinary captain request asking it to finish its step, commit work in its workspaces, cancel queued jobs it will not need, replace its handoff notes and pins, and reply with what it left in flight. While a stow is in force, job admission refuses every new job under the ledger's lock, in every home; a job started with `wait_for_capacity` keeps its place in the queue instead. First mates' wakes are exempt, because `serve` records a wake before starting its job, so ships can wake to stow, and running jobs finish on their own. `privateer stow status` reads, from records only, which ships have replied, their replies and their unfinished jobs; it reports ready once every ship has replied and nothing but queued jobs remains. `privateer stow resume` lifts the hold and sends each ship a notice to carry on. Stow, status and resume are operator commands (`stow.start`, `stow.status`, `stow.resume`). The machine's owner may stow it as well, as an agent, to clear it for the captain or for one large build: its requests come from the owner in its own words, so the replies reach the owner, the owner is not asked itself, and the owner may resume only a stow it started; the captain resumes either. A linked machine is stowed from here with `privateer stow [status|resume] --machine NAME` (or `/stow [status|resume] NAME` at a front door): the call travels over the machine link's gateway, the same SSH transport that collects its mail, and the remote gateway runs that stow under its own ledger, asking only its own ships. Only the operator may start one; an agent, the machine's owner included, is refused, and an unknown name is an error. Status names the machine it describes. The plain form still means this machine.

A stow is one machine's hold, so the request and the resume notice name that machine (the name it chose when it made a link, else the host's name) and never speak of "the fleet". A resume notice also names every linked machine still holding its own ships, and every linked machine whose hold this one cannot know: a link is one-way, so a machine that reaches this one is named as unknown rather than assumed resumed, and a machine that cannot be reached is named as unknown with the transport error. `stow.status` and `stow.resume` report the same `machines` list beside their own `this_machine`, so a machine-scoped claim can be checked in records before it is repeated to a ship. `privateer stow resume --all` (or `/stow resume all`) lifts every linked machine this one reaches first, then this one, so a notice written afterwards names no machine that is still stowed; it is the operator's alone, it does not require this machine to be stowed (the linked machine may be the only one that is), and a machine it could not reach stays in the notices as unknown rather than being claimed as resumed. It cannot be combined with `--machine NAME`.
A request may record the stow it waits on, in its payload as `depends_on`: `{"stow": id}` for a stow on this machine, `{"stow": id, "machine": NAME}` for one on a linked machine. It is explicit only: nothing is read from the body. A stow on this machine must exist and still be in force, so a request cannot be bound to a stow that has resumed or to one that never existed; a linked machine's stow is accepted even when this home has not heard of it yet, because its id reaches this home only through an exchange. A binding that names this machine by its own name is this machine's stow. Only a request or decision carries a binding. `stow.resume` ends every open request bound to the stow it lifts, in each home on this machine, as `withdrawn` on the sender's behalf with the reason `stow <id> on <machine> resumed at <time>`, through the same durable closure path as a sender's own withdrawal, so the recipient gets one low closing notice. It does this after the hold lifts: a request stored before the lift is open and ends, and one stored after is refused, because the stow is no longer in force. A home that cannot be opened is skipped and named in the output, and its requests stay open. Only the sender's own rows are ended: a received copy is closed by the sender's home, and that closing notice carries the end here. Only open requests are touched, so a repeat writes no second notice. A request already answered, or bound to no stow, is untouched. A request bound to a stow on another machine ends when the next exchange with that machine reports the stow resumed, or reports it neither in force nor among the recent resumes it carries, which is a typo or a stow that ended before this home heard of it; that second case ends with the reason `stow <id> not known on <machine>`, so a binding never sits forever. No notice reaches a sender on another machine: the closure is written in the home that holds the request, and the sender reads its own mail there.

## Front doors

A front door carries the captain's conversation to wherever the captain is: a chat service, a phone, voice. It is a long-running trusted adapter registered once for the whole fleet, not for one ship, and it owns no fleet state. Registering a door is an operator command, because a door speaks as the captain: `privateer door add NAME [--manifest PATH] [--config PATH] [--to SHIP]` records it in the fleet registry (a bundled door such as `telegram` needs no `--manifest`). Its manifest is a version 1 plugin manifest with `"kind": "front-door"`, and `"config_required": true` when it cannot run without private configuration, which must be a user-owned `0600` file. Harness planning refuses a front-door manifest and `door add` refuses a harness manifest.

`privateer door start NAME` runs the door's supervisor in the background the way the dispatcher runs, as a user service where systemd is available (`privateer-door-NAME-<hash>.service`), as a launchd agent on macOS, or detached; `door stop`, `door status` and `door list` manage it, `door remove` stops and unregisters it, and `door run NAME` is the supervisor in the foreground. One supervisor runs per door, holding `doors/NAME/lock` beside the fleet registry. It starts the adapter in its own process group without any `PRIVATEER_` environment, so the adapter is neither a ship nor an agent; it restarts an exiting adapter with backoff from one second to a minute, and when stopping closes the adapter's input, then signals its whole group before reaping it. On Linux a supervisor killed outright takes its adapter with it. The adapter's stderr goes to `doors/NAME/door.log` (rotated at 1 MiB) and `doors/NAME/state/` is its own state directory.

Protocol version 1 is JSON lines over the adapter's stdin and stdout. The runtime sends `hello` first (door name, config path, state directory, and the default recipient), then one `mail` event per message to the captain from any ship in the fleet, oldest first in each ship's home, each with an opaque `ref`. The adapter answers `delivered` with that ref once the captain has the message. Each door keeps its own durable cursor per home (`door_cursor`), separate from the captain's read cursor: a door acknowledging mail does not mark it read on the dashboard, and the dashboard reading it does not stop the door. A new door starts from what the captain has already acknowledged, so unread mail still arrives. Delivery is at least once: a restarted adapter is sent everything after its last `delivered` again, so an adapter dedupes by mail id. Acknowledging a ref the adapter was not sent ends the session.

The adapter asks with `request` lines (an `id`, `command` and `args`) and gets a `response` with the same id. `send` mails a ship as the captain, in that ship's own home, as a `request` (the default), `notice` or `reply` (with `correlation`); without `to` it goes to the door's `--to` ship, else the fleet's one liaison, else a one-ship fleet's ship. `ships` lists the fleet with scopes and the default recipient; `status` and `waiting` answer from records with no wake and no model call (what each ship is doing, and the requests and decisions still owed the captain). Every send is audited in the receiving home as `door.send`. See the [Telegram door](../plugins/telegram/README.md) for the first adapter.

## Away mode

The captain says they are away with `/afk [until TIME] [words]` at a front door, in a first mate's Pi session, or `privateer afk` anywhere; the period is recorded fleet-wide in the fleet registry, and the liaison is told as an ordinary captain message carrying the words, which it acts on within its charter (a decision they answer can be recorded with `captain.relay`, citing that message; production approvals are never relayed). Every ship's bearings say the captain is away. While away, a front door stops carrying the captain's mail: it stays unacknowledged in each ship's home and the door's cursor does not move past it, except for a ship's `"urgency":"high"` mail, at most three an hour, which the door marks as a breakthrough (crew outcomes never break through); the brief reserves high urgency for production or data at risk, security, unexpected spend and deadlines within hours. `/status`, `/waiting`, `/ships` and `/held` leave the captain away. The captain's first ordinary message, `/back` or `privateer back`, ends the period: every door's cursor moves past the held mail, which is summarized rather than replayed; the captain gets a digest built from records (time away, messages and ships, requests waiting, emergencies sent, urgent mail held over the limit); and the liaison receives a captain request listing the held mail and asking for a plain-words summary, needs first, before the captain's own message. `/held` lists the latest period's held mail.

## Plugins and local configuration

Optional executable plugins use JSON lines over stdio. They receive a minimal task context and return a validated command specification; they cannot widen the charter. Harness choice, model choice, provider routing, and private gateway policy live outside the core.

Examples can demonstrate a generic native harness or a gateway-constrained Pi route. A particular account's endpoint, provider alias, allowed models, and credentials belong in private configuration, not an example checked into Git. An unavailable required route is an error, never permission to bypass it. New provider adapters do not require changes to task/event/job storage.

## Peer transport

`peer.put` stores a transport address: name, `ssh` or `local`, absolute executable/home paths, timeout, and response limit. A machine peer (`gateway: true`, optionally with the remote `fleet` registry) reaches another machine's gateway instead of one home, and a `collected` peer has no transport: its mail waits for the other machine to collect it. `peer.call` sends one correlated RPC request and returns the remote envelope. Each remote command enforces that remote home's workflow rules. Native SSH supplies host verification and authentication.

SSH runs a remote shell even when invoked through a local argv array. Privateer validates endpoint tokens and POSIX-quotes every remote command argument. Stdin carries JSON; task contents never become shell commands. Request size, output size, diagnostics, and total call duration are bounded. A local transport exercises the identical RPC protocol without SSH credentials.

This milestone does not implement distributed consensus or cryptographic cross-host charter inheritance. Explicitly configured remote homes remain responsible for their own charters. A peer's address is not a superior role or authority credential. Cross-host authorization and custody protocols need further qualification before replacing a fleet. [Linked machines](#linked-machines) implement the first steps of the [cross-machine fleet proposal](design/cross-machine-fleet.md).

## Delivery and deployment

Passing-head checks bind delivery evidence to the current artifact. Production approval binds a separate decision to an exact artifact and environment and records an approver other than the task owner. That approval supplies authority for the single deployment without requiring broader standing deployment rights: the production `delivery.check` that allows it consumes it. Active task/charter reads and exact approval matching and consumption share a write transaction, so a concurrent revocation cannot leave the check using stale authority. These are workflow guards running under one OS identity.

## Operators and agents

Harnesses launched by `agent.start`, and any job an agent starts, run with `PRIVATEER_ROLE=agent` and `PRIVATEER_ACTOR` set to the task owner. Under that role, operator commands (`init`, `charter.put`, `charter.revoke`, `approval.grant`, `approval.consume`, `peer.put`, `resource.recover`) are refused, `actor`/`from` arguments must name the agent itself, and jobs can be started only for the agent's own tasks. `peer.call` passes the role to the remote home as `--role agent --actor NAME`, flags that can only narrow a caller, never widen it. The same caller checks apply to human CLI commands: agents cannot run bare `privateer`, the dashboard, `start` or `service`, or directly initialize a home; `project add` applies the `project.add` limits. Agents require an existing home; an explicit `--home` does not grant operator authority. Mail shortcuts use the agent's own address. `ship new|retire` retain the delegated creation, action and retirement limits described under [The fleet](#the-fleet), including bounded internal child initialization. This stops a confused or overeager agent from widening its charter or approving its own deployment. It is not a security boundary: an agent that deliberately clears its environment or edits the state database is outside it. Enforced separation needs a separate OS account or broker. Hard isolation from production credentials requires a separately enforced broker or account boundary.

The first milestone has no live forge merge/deployment adapter and no automatic fleet migration. A passing runtime pilot establishes behavior of the machinery; native model-driven execution is a separate qualification step.
