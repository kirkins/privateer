# Architecture

Privateer's flat structure distributes routine decisions while preserving explicit responsibility. A navigator is a conversational role, not the scheduler's exclusive control plane. A department may contact another department directly. Tasks retain an owner, a charter, status, and bounded delegation depth. A handoff requires the current owner's request and the recipient's acceptance.

## Runtime boundary

The Rust runtime handles durable state, process supervision, resource admission, and transport. SQLite stores charter/task state, facts, pending issues, approvals, and audits. A job runs under a recorded task and an admitted resource reservation. A detached supervisor manages its payload process group and records completion after the invoking CLI exits.

Schema upgrades, including activation's wake/session columns, check and change the schema under an immediate write transaction. Concurrent opens serialize those checks and retain existing wake history.

Multiple homes on one host share a configured resource ledger, and admission decisions are made under its lock against the same readings, so independent departments cannot each assume the machine is free.

Heavy jobs, and any job that passes an `estimate` (`cpus`, `memory_bytes`), are admitted from live readings rather than a fixed slot count: the load average, CPU count and available memory, plus the estimates of jobs admitted within the last `ramp_secs` (default 60), whose use does not show in those readings yet. A job is admitted while load plus recent estimates stays below `max_load_per_cpu` (default 1.0) per CPU, and while available memory minus recent estimates and its own stays above `min_available_memory_bytes` (default 1 GiB). A job's own estimate counts only while another estimated job holds a reservation: one running alone needs just that floor, so a small machine whose person is using most of its memory still runs its builds one at a time instead of queueing them forever. Heavy jobs without an estimate count as every CPU and 2 GiB (`heavy_estimate`), so two big builds cannot start together, while a later one is admitted once the first turns out to be light. `max_heavy_jobs` adds an optional host-wide slot cap and a charter's `max_heavy_jobs` an optional per-charter share. `resource.configure` changes these host-wide settings for every home, and is open to agents so they can tune the machine to their person's wishes, from using all of it to leaving room for the person's own work; `resource.status` shows the settings beside the live readings. Light jobs without an estimate are not subject to admission.

A job started with `wait_for_capacity: true` joins a host-wide, first-come-first-served queue in the ledger instead of being refused. Its detached supervisor waits there, re-checking cancellation and authority about once a second, and starts the payload once the job reaches the head of the queue and fits; `max_wait_secs` (default 3600) bounds the wait. Requests subject to admission cannot bypass a non-empty queue, and entries whose supervisor has gone are dropped. Nothing runs while a job is queued, so cancelling it, or losing its supervisor, simply ends it.

Admission governs work started through `job.start`. A harness started by `agent.start` is light by default, since it mostly waits on its model; its brief asks it to run builds and test suites that load the machine as heavy jobs with `wait_for_capacity`, so those are spaced out and queued. Work a harness runs directly in its own shell is outside admission. Process identity and surviving payloads matter more than a supervisor's liveness; uncertain ownership is preserved for explicit recovery. A job whose supervisor and recorded process group are both provably gone settles automatically: to its leader's recorded result when descendants outlived the leader, otherwise to `failed`. `resource.recover` explicitly releases a reservation no job can settle, such as one left by a crash between the ledger and home commits. It never releases a live supervisor or process group, and a reservation with no recorded payload identity requires `force: true`.

Events are facts. Pending notifications are a projection: repeated facts concerning the same task and issue update one pending item. An acknowledgment names the sequence actually observed, so a later fact cannot be silently discarded. Messages name a recipient and a task rather than broadcasting to the whole fleet.

History is kept until an operator prunes it. `history.prune` (`older_than_days` or `before_ms`, optionally `dry_run`) removes event facts older than the cutoff that no longer back a pending notification, audit rows older than the cutoff, and finished jobs whose reservations are released, together with their log directories. Pending notifications, including unread messages, and live or still-reserved jobs are kept. Pruned event and job ids may be reused afterwards. Nothing is deleted automatically; run it by hand or from cron.

## Ships and mailboxes

A ship is an identity with its own mailbox, first mate and crew; a home hosts one or more ships, and the directory (`ship.put`, `ship.list`, `ship.show`) records each ship's plain-language scope, location and the request kinds it accepts. `captain` is the reserved address of the person. Directory administration through `ship.put` is an operator command.

`mail.send` writes typed, durable messages: a `request` or a `decision` (addressed to the captain) stays open until its single `reply` from the recipient, and the runtime tracks it rather than any agent's memory; a `notice` states a fact. Message ids are idempotency keys, a request can carry a reply deadline after which it reads as overdue, and typed request kinds are checked against what the recipient accepts. `mail.inbox` returns unacknowledged mail, `mail.ack` acknowledges through a sequence actually present in that mailbox and never moves back, and `mail.requests` lists incoming or outgoing requests by state. Agents send and read mail only as their own ship; only the operator speaks as, or reads mail for, the captain. `history.prune` removes acknowledged mail past its cutoff but never unread mail or a request still owed its reply. A ship can live behind a peer (`location: {"peer": name}`): mail to it is recorded first as an outgoing copy, then delivered through `peer.call` to the other home's `mail.deliver`, which accepts it only from a ship it knows to live behind a peer and only for a ship it hosts. A failed attempt leaves the copy pending, counted in `status`, until `mail.flush` delivers it; redelivery is idempotent. Each home keeps its own copy of a request, and the reply closes both. Task ids and captain mailbox storage stay local to their home; see the [dashboard](dashboard.md) for the captain's fleet view. The older `message.send`/`message.inbox` commands remain for now. See the [conversation and activation design](design/conversation-and-activation.md) for where mailboxes lead.

`mail.send` accepts at most 64 KiB of serialized JSON arguments. New outgoing mail must also fit that bound after normalization into the receiving home's envelope, including generated ids, defaults, timestamps and reply deadlines. Rejection rolls back the outgoing record and leaves a correlated request open. Transport correlation ids are separate from the durable message id, which is preserved across delivery and replies.

Outgoing delivery keeps sequence order within each peer and selects the peer attempted least recently, so one unavailable destination cannot hide other peers behind its backlog. A new remote send makes at most one network attempt for that peer, which may deliver an older queued message; the returned record shows whether the new message remains pending. Failures preserve the mail and record a durable retry delay, starting at one second and doubling to at most 60 seconds; automatic sends and dispatcher passes honor that delay across restarts. An agent cannot deliver another sender's mail or bypass it in the peer's queue. Explicit `mail.flush` bypasses the delay, uses configured peer timeouts, and attempts a failed peer only once per invocation. Its `limit` bounds network attempts; each invocation examines at most `limit + 50` records, including local classifications. Immediate sends examine at most 51 records under their one-attempt budget. Large invalid backlogs may require several passes. The flush result reports `delivered`, `attempted`, active `pending` mail and total `quarantined` mail visible to the caller.

An older binary could accept outgoing arguments that fit 64 KiB but whose normalized receiving envelope exceeds it. When such a record reaches an eligible queue head, delivery records `delivery: "quarantined"`, a bounded `delivery_error`, and a `mail.quarantined` audit in one transaction. This classification uses the local envelope bytes, never an error string from a peer. It sends nothing, consumes no network attempt, and changes no peer retry state. The original message id, sender, body, payload and request state remain unchanged; the quarantined row stops blocking the active FIFO and is excluded from `history.prune`. Transport errors and remote refusals remain pending with normal backoff. `status.undelivered_mail` includes pending and quarantined mail; `status.quarantined_mail` reports the quarantined subset.

Inspect outgoing delivery with `mail.outbox {"delivery":"quarantined","limit":40}`. The optional `delivery` filter accepts `pending`, `quarantined` or `delivered`; omitting it lists all three states for cross-home outgoing copies, excluding local-only mail. It returns headers, request state, correlation, attempts and errors without loading bodies or payloads; follow `next_after_seq` with `after_seq` until it is null. The default page is 40 records, capped at 100. Operators may filter by `from`; agents see only their own outgoing mail even when they omit that filter. Error display is capped at 1,024 characters without changing the stored diagnostic. `mail.show {"id":"..."}` reads the full original record and delivery metadata; quarantined records remain readable after restart or `history.prune`.

Quarantine recovers queue progress and visibility; it does not rewrite conversations. Replaying the original id returns the unchanged quarantined record, and changed content under that id is refused. A corrected notice or request needs a new id and may refer to the retained original; an original open request stays open. A legacy oversized reply may already have closed its sender-local request while the remote request remains open. A second reply to that locally answered request is still refused: coordinate explicitly in a new thread, retaining the original reply and correlation for investigation. No automatic request closure, reopening, in-place repair or retry of an unchanged oversized envelope is implied.

## Waking first mates

A ship hosted here can have a first-mate profile (`ship.put` with `first_mate`): the harness plugin manifest and options to launch, a duty task owned by the ship whose charter its first mate works under, and activation settings. `privateer serve` is the dispatcher, meant to run as a background service; `serve` with `{"once": true}` performs a single pass. Each pass reconciles unsupervised jobs, records finished wakes, and wakes due first mates before attempting outgoing delivery. `serve` accepts `delivery_budget_ms` (1–120000, default 10000): each automatic peer call uses at most the remaining network budget for that pass. A slow peer therefore delays the next local pass only by that budget rather than by every queued message's timeout; durable attempt order gives other peers their turn on later passes. Routes needing a longer deadline can use a larger budget or explicit `mail.flush`. It makes no model calls, and only one dispatcher runs per home (an exclusive lock on `<home>/serve.lock`); agents cannot run it.

Mail is the durable record of a pending wake. A first mate is due when its ship has mail newer than both its acknowledgement and its last successful wake, at least one message is not a low-urgency notice (routine notices wait for the next real wake), and the batching window (`batch_secs`) has passed since the newest actionable message or the oldest has waited `max_delay_secs`. Eligibility examines the whole backlog; each wake covers the oldest contiguous page of at most 200 messages. A routine-only page advances while actionable mail waits behind it, without covering or acknowledging the later page. Successful wake coverage advances to that page's last sequence; failed wakes do not advance wake coverage. The prompt still bounds message summaries and may omit bodies with an instruction to read `mail.inbox`; selected-page coverage does not prove every body was rendered or handled. Coverage never acknowledges mail: unread facts stay durable until the harness explicitly acknowledges them, and open requests survive retention. Large backlogs may take several wakes and remain subject to the hourly budget. A ship whose first mate is already awake is not woken again; an hourly wake budget (`max_wakes_per_hour`) and a backoff after a failed wake (`retry_backoff_secs`) apply. A wake runs the first mate through `agent.start`, with the wake's text (a summary of requests owed and owing, the new mail, and what to acknowledge) appended after the stable brief so the brief remains a cacheable prefix. A wake covers mail through its sequence number whether or not the first mate acknowledges it, so a forgetful agent is not woken repeatedly. `wake.list` shows each wake's coverage, job, outcome and the token usage its harness reported (Codex per-turn usage is summed; a cumulative result is taken as reported). Context follows the focus, so a first mate that starts fresh can keep working without carrying old conversations. Each message belongs to a focus: a task the ship owns (`task:<id>`, from the message's task or the request it answers), a request thread (`thread:<root id>`), or the captain's conversation (`captain`); `ship` holds the ship's long-lived knowledge. The wake presents its page grouped by focus: first the ship's bearings (open tasks, requests owed and owing, unacknowledged mail and the ship note, built from records with no model call), then each focus in play with its handoff note and its new mail. A wake whose oldest wake-worthy mail concerns a task the ship owns runs under that task when it has active `spawn` authority; otherwise under the duty task. `wake.list` records every focus a wake covered.

Notes hold judgement; the runtime already records facts. `note.put` replaces a focus's note (2 KB, or 4 KB for `ship`) and keeps the last five versions; `note.get` and `note.list` read them, and the wake asks the first mate to update the note for each focus it worked on. `focus.digest` returns a focus's history on demand, curated and bounded: a task's events, jobs and mail, a thread's messages in order, or the captain's conversation. `ship.bearings` returns the summary on its own. Agents read and write these only for their own ship. `history.prune` drops notes for finished tasks and threads whose latest note predates the cutoff, keeping captain and ship notes. A wake whose mail all belongs to one focus resumes that focus's native session when it is warm: the harness reported the session at start-up (decoded from its JSON events, mirroring `plugins/native_events.py`), its last turn ended within `cache_window_secs` (default 300, while the provider's prompt cache is likely warm; 0 disables resuming), and it has had fewer than `session_max_wakes` wakes (default 6). A resumed wake passes the session to the adapter's explicit `resume` option and sends only the wake text, without the brief, bearings or notes the session already holds. Otherwise the wake starts fresh, and a single-focus fresh wake becomes that focus's session; mail spanning several foci never resumes one focus's conversation, and a failed wake drops the focus's session. Sessions rotate after `session_max_wakes` instead of compacting. `wake.list` shows each wake's mode and session. The rotation limit counts wakes rather than tokens, because harnesses report usage differently (per turn or cumulative); see the [design](design/conversation-and-activation.md#context-and-cost).

### Dispatcher restarts

A resident `serve` start takes the home lock, atomically clears native sessions and records a new dispatcher generation before its first pass. Wakes retain their launch generation: an old wake may still finish successfully and cover its recorded mail, but cannot restore or delete the new generation's warmth. Legacy wakes without a generation are likewise fenced after the first resident start. Ordinary Store opens, ticks and `serve {"once":true}` are maintenance operations, not restart boundaries; they do not reset sessions. A one-shot pass still holds the same exclusive lock and cannot run beside a resident dispatcher.

Generated dispatcher units use `KillMode=process`: stopping/restarting the dispatcher leaves independent job supervisors and their payloads alive. Detached stop also signals only the recorded dispatcher, never its process group. On the next start, recorded job identities and outcomes, not parent-child relationships, determine whether a wake is still running. A missing supervisor with a live or uncertain payload remains blocking; it is not proof of payload death and must not trigger a duplicate wake. If the supervisor was lost, a successful payload result cannot in general be recovered: inspect/cancel/recover explicitly rather than fabricating success. Mail arriving meanwhile remains durable and is covered by the next eligible wake, after the adopted wake's sequence. Successful coverage suppresses replay; this is not a promise of exactly-once external effects if a harness crashes or explicitly acknowledges mail it has not handled.

`service stop` repairs a legacy dispatcher's unit stop policy and requires a successful daemon reload **before** stopping it. Direct `systemctl restart` of an old, unrefreshed unit is still unsafe: the future upgrade orchestrator must install/reload the safe policy first. Front doors deliberately retain `KillMode=control-group`, since stopping a door must stop its adapter. This does not implement fleet upgrading, draining, approvals, or deployment, and does not keep wakes alive through a host reboot or explicit job cancellation.

## Crew outcomes

Crew are the supervised jobs a ship's first mate starts for the ship's tasks. When a job whose task is owned by a ship hosted here first reaches `succeeded`, `failed`, `cancelled`, `timed_out` or `orphaned`, the runtime writes a notice from the reserved sender `crew` to that ship, in the same transaction that records the status, so a crash cannot separate the two. Its id, `crew-<job id>-<incarnation>`, makes it exactly one per incarnation: an orphan is reported when it is orphaned (it is no longer supervised, so its deadline is not enforced), and its later settlement is not reported again; `job.retry` is a new job with its own outcome. The notice carries the job's task, so it lands in the task's focus, and states the status, exit code, reason, duration, command, log path and the end of stderr and stdout, bounded so the whole message fits what a wake or hook shows (2,000 characters); the payload holds the same fields. Failures, timeouts and orphans are `high` urgency, success `normal`, and a job the ship cancelled itself `low`, which waits for the next real wake. A first mate's own wake jobs are excluded: `serve` records the wake, with its job id, before starting it. Each `serve` pass also reconciles unfinished jobs whose supervisor has gone, so their outcome is recorded without anyone asking for their status.

Crew run as their ship, so they cannot mail their own first mate. The supervisor sets `PRIVATEER_JOB` in each payload's environment; `crew.report` (`kind` `progress` or `decision`, a body, an optional payload and idempotency `id`) is accepted only from the agent a launching or running job works for, on a task its ship still owns, and never from a wake job. Progress is a `low` notice; a decision is a `high` request the first mate answers with `mail.send` kind `reply` to `crew`, which the crew reads with `crew.answer` (optionally waiting up to `wait_secs`). `crew` has no mailbox otherwise: nobody, the operator included, can send as it, mail it anything but a reply to its request, or name a ship after it.

## Attended mode

While the captain talks to a ship's first mate in an interactive session, that session is the first mate. It holds the ship's presence lease (`ship.attend`, `ship.leave`, `ship.presence`), and `serve` skips headless wakes for an attended ship, leaving its mail to the live session; when the lease is released or lapses, headless wakes resume. `privateer start [HARNESS] [-- ARGS]` claims the lease in a write transaction before spawning the ship's harness, or the one named, in the ship folder under the agent role as the ship. A live lease rejects another start, and a failed spawn releases the claim. The runtime refreshes the lease with a heartbeat while the harness runs and releases it on exit. For Claude Code, `privateer init` installs hooks (`privateer hook claude EVENT`) that take the lease at session start and show the bearings and new mail, show newly arrived mail with each prompt, keep the first mate working at turn end when unseen mail has arrived (exit status 2 with the mail as the reason), and release the lease at session end; a hook-held lease lapses after 30 minutes without activity. Each message is presented to the session once, so a first mate that does not acknowledge is not prompted in a loop. Hooks never fail the harness: errors allow the event and go to `<home>/hooks.log`. Other harnesses read their inbox as `AGENTS.md` directs. See [Boarding and management](dashboard.md#boarding-and-management) for Herdr presence bindings and their refresh/expiry rules.

### Hosted first mates

With `first_mate.host = "herdr"` (set through `ship.put`; `init` keeps it), the dispatcher keeps the ship's first mate as a live interactive session in its own background Herdr space, so it shows in Herdr's agent list with its history and the captain can read or type to it. When `serve` starts, and again whenever mail would wake a ship with no session aboard, it claims the presence lease for a `host:` holder, creates the space (labelled with the ship's name, without taking focus) and runs `privateer start --hosted` in it. That session adopts the lease rather than claiming a new one, binds it to its pane, and carries on the ship folder's latest conversation (`--continue`). Its attended mail adapter starts a turn when actionable mail arrives; after a native error it retries a minute later instead of waiting for the captain. While the hosted session lives, `serve` leaves the mail to it; when the session exits its lease is released, and an unadopted launch lapses after 60 seconds. If Herdr is unreachable (its socket is `HERDR_SOCKET_PATH`, or `herdr/herdr.sock` under the user's config directory), the headless wake runs as before and its report carries `host_error`. Only Pi and Pi-signed first mates can be hosted today, since their adapter starts turns on mail. Hosted turns are not wakes: they are not batched, budgeted per hour or recorded with usage.

A hosted ship's crew run live too. When its first mate starts crew (`agent.start` outside a wake) and Herdr answers, the harness is planned interactively, with the crew extension (`plugins/attended/crew.ts`), and the job is marked `hosted`. Its supervisor (`_job-supervise`) runs in a background space labelled `└ TASK` instead of detached. Custody is unchanged: the supervisor claims the job there, checks authority, and starts the harness in its own process group, now the pane's foreground group with the pane's terminal instead of log pipes. Timeouts, cancellation, admission and crew outcome mail work exactly as for headless crew, but the job's logs stay empty; the session's own history holds the transcript. The crew extension shuts the session down when its work settles, exiting with status 1 when the last turn failed, so the job ends as usual and its space closes. The captain can watch or type into a crew at any time; interrupting a run (Esc) keeps the crew open until its next settle. A space that never runs its supervisor leaves the job unsupervised, and reconciliation fails it after 30 seconds.

Privateer tags the spaces it opens (`workspace.report_metadata`, source `privateer`, tokens `privateer` = `mate` or `crew` and `ship`) and keeps them together at the top of Herdr's sidebar: the bridge first, then each ship's first mate followed by its crew, ships in first-mate sidebar order (then ship name for ships without a first-mate space). Crew without a first-mate space follow all first mates. Arranging recovers missing first-mate tags from live hosted presence bindings, checking the socket incarnation and terminal identity; dispatchers also repair their own bound mates each pass. Fleet recovery reads existing homes without creating or migrating them. The dashboard tags its own space as the bridge when it starts inside Herdr. The captain's other spaces stay below, in their own order. Arranging is presentation only; a refusal never affects a launch.

## Getting aboard

Git-backed crew work uses built-in [task workspaces](workspaces.md). Privateer
owns each task's durable Treehouse lease, plans its harness against the isolated
checkout, and pins subsequent jobs to that lease. Workspace release verifies
processes and preserved/landed work; it never follows from a process exit alone.
First-mate wake and interactive sessions retain their existing ship repository.

Bare `privateer` is the everyday entry point. See
[First run and everyday entry](dashboard.md#first-run-and-everyday-entry) for
installed dashboard entry, liaison handoff and onboarding conditions. When
the dashboard is unavailable, the legacy flow applies: Inside a ship folder (any folder at or below one holding `.privateer`), it makes sure the ship's dispatcher is running and then runs `privateer start`. Elsewhere it asks whether to make the current folder a ship, naming it after the folder and choosing the first installed harness, then does the same; without a terminal to ask in it prints help, and `--yes` skips the question. It refuses to make the user's home directory or `/` a ship. The dispatcher is installed as a systemd user service where a user manager is available (the unit records the current `PATH`, where harnesses usually live, and `PRIVATEER_RESOURCE_HOME`/`PRIVATEER_PLUGINS` when set) and otherwise started as a detached process logging to `<home>/serve.log`, rotated at 1 MiB. A dispatcher holding `serve.lock` counts as running however it was started, so nothing starts twice. `privateer service status|start|stop` manages it; stopping a detached dispatcher signals the recorded process only while it still holds the lock and is that home's `serve`. `PRIVATEER_SERVICE=systemd|detached|none` overrides the choice.

`privateer init --liaison` makes the captain's contact: a ship the captain
reaches from the dashboard, a terminal or a front door, which acts on their
behalf. Its charter holds the default actions of any captain-made ship
(everything but `deploy_production`), so the ships it creates inherit working
authority, and it can provision them itself: `ship.create`, `ship.actions` and
`project.add` need no trip to the command line. Production deployment stays
with the captain under explicit approval. Generated first-mate onboarding
instructions ask about work and preferences, propose peer ships and actions,
create them, add their repositories, and explain dashboard and direct access.
They store lasting preferences in the ship's `ship` note and onboarding
progress in its `captain` note. Ordinary init retains the preset and uses the
persisted ship identity unless a ship name is explicitly supplied with
`--ship`. Existing charters remain captain-owned: re-running init upgrades only
a liaison still holding the earlier contact-only preset (`inspect`, `spawn`,
`message`) at its first revision, never one the captain has edited.
Independently authored `AGENTS.md` files are preserved, while Privateer-managed
instructions are refreshed with the checklist when the preset is active.
A validated `agent.start` harness job runs under `spawn`
authority; ordinary `job.start` requires an implementation/test/
recovery/cleanup action and cannot request `spawn`, so a captain who narrows
a liaison to read/message/delegate still has it process mail headlessly.
The instruction checklist is not proof of a model-driven onboarding outcome.

### Replacing the installed executable

[Versioned releases](releases.md) keep each running binary paired with its own bundled plugins. In that layout, persisted command paths use `current/bin/privateer`, while internal supervisors retain the running image. `privateer upgrade status` reports the selected and running commits separately and reads recorded fleet outcomes; it does not perform an upgrade.

On Linux, a running dispatcher can outlive an atomic replacement of its installed binary. Job supervisors reexec the dispatcher's retained image through `/proc/self/exe`, so an upgrade does not mix versions of the internal supervisor protocol. Agent control argv, hooks, and newly recorded peer/service commands instead use the installed path: a `/proc/self/exe` alias must never be passed to another process as its control CLI. The resolver checks the running image identity before interpreting Linux's ` (deleted)` marker, preserves literal filenames with that suffix, and never searches `PATH` for a substitute.

The installed replacement must remain a regular file executable by the runtime's effective credentials. If it is missing or not executable, control-command creation fails with the path and restore/restart guidance. On Linux, replacing or removing the installed file leaves the retained image available for ordinary job supervision, but changing execute access on that retained image can still prevent a supervisor launch. Other Unix platforms use the OS-reported installed path for supervisors and validate it before job admission. A supervisor spawn failure marks the admitted job failed and removes its capacity reservation or queue entry.

Compatibility between different releases of the external CLI protocol is not verified. Restart dispatchers after installing an update to activate its runtime changes. Already-running dispatchers from before this fix still need a restart, and existing records or agent sessions containing stale CLI paths are not automatically rewritten.

## The fleet

Every ship made with `privateer init` or `ship.create` joins a per-user fleet registry (`PRIVATEER_FLEET`, or `$XDG_STATE_HOME/privateer/fleet.sqlite`, default `~/.local/state/privateer/fleet.sqlite`), and is linked both ways with every other active ship: each home gets a local-transport peer `fleet-<name>` and a directory entry behind it, so ships mail each other without manual setup. A name belongs to one active ship; a ship whose folder was deleted no longer holds it, and linking never recreates a deleted folder. `fleet.list` shows the registry and `fleet.link` relinks this home.

Ships can make ships, so the captain can grow a fleet from the first one. `ship.create` (`privateer ship new NAME`) makes a new ship folder, by default beside the creating ship's folder, with the creator's harness unless another is named, starts its dispatcher and links it. An agent needs active `spawn` authority to create ships, and a new ship's charter can hold only actions the creating ship's own charter has; the operator may set any. Creation checks authority under the creator's write lock before publishing the child, serializing that decision with revocation. Cross-home bootstrap and publication are not a distributed transaction, and child charter defaults remain unchanged. `ship.actions {name, actions}` replaces a ship's charter actions; an agent may change only ships it created, only to actions its own active charter has, under its write lock. `project.add {url, name?, target?}` (`privateer project add URL [NAME] [--ship SHIP]`) clones a repository into a ship's `projects/`: an agent may add to itself, or, with `spawn`, to ships it created; the operator to any fleet ship. The clone is staged in `projects/` and published by rename after authority is checked again under the caller's write lock; agent clones run without terminal or SSH prompts, `ext::`/`fd::` transports are refused, and HTTP(S) credentials in the address are redacted from replies and the audit log. `ship.retire` revokes a ship's charter, stops its dispatcher, unlinks it and marks it retired, keeping its folder; an agent may retire only ships it created. The registry records who created each ship. `ship.retire` accepts optional `expected_home` to reject a name that now belongs to a different home; its final registry update also checks the originally selected home and active status after stopping the dispatcher.

After authorized creation, the child's dispatcher runs as an operator service.
The detached launch clears the creator's execution identity while retaining
configured fleet, resource, plugin and configuration paths. Its first-mate jobs
run as agents bound to the child ship.

## Front doors

A front door carries the captain's conversation to wherever the captain is: a chat service, a phone, voice. It is a long-running trusted adapter registered once for the whole fleet, not for one ship, and it owns no fleet state. Registering a door is an operator command, because a door speaks as the captain: `privateer door add NAME [--manifest PATH] [--config PATH] [--to SHIP]` records it in the fleet registry (a bundled door such as `telegram` needs no `--manifest`). Its manifest is a version 1 plugin manifest with `"kind": "front-door"`, and `"config_required": true` when it cannot run without private configuration, which must be a user-owned `0600` file. Harness planning refuses a front-door manifest and `door add` refuses a harness manifest.

`privateer door start NAME` runs the door's supervisor in the background the way the dispatcher runs, as a user service where systemd is available (`privateer-door-NAME-<hash>.service`) or detached; `door stop`, `door status` and `door list` manage it, `door remove` stops and unregisters it, and `door run NAME` is the supervisor in the foreground. One supervisor runs per door, holding `doors/NAME/lock` beside the fleet registry. It starts the adapter in its own process group without any `PRIVATEER_` environment, so the adapter is neither a ship nor an agent; it restarts an exiting adapter with backoff from one second to a minute, and when stopping closes the adapter's input, then signals its whole group before reaping it. On Linux a supervisor killed outright takes its adapter with it. The adapter's stderr goes to `doors/NAME/door.log` (rotated at 1 MiB) and `doors/NAME/state/` is its own state directory.

Protocol version 1 is JSON lines over the adapter's stdin and stdout. The runtime sends `hello` first (door name, config path, state directory, and the default recipient), then one `mail` event per message to the captain from any ship in the fleet, oldest first in each ship's home, each with an opaque `ref`. The adapter answers `delivered` with that ref once the captain has the message. Each door keeps its own durable cursor per home (`door_cursor`), separate from the captain's read cursor: a door acknowledging mail does not mark it read on the dashboard, and the dashboard reading it does not stop the door. A new door starts from what the captain has already acknowledged, so unread mail still arrives. Delivery is at least once: a restarted adapter is sent everything after its last `delivered` again, so an adapter dedupes by mail id. Acknowledging a ref the adapter was not sent ends the session.

The adapter asks with `request` lines (an `id`, `command` and `args`) and gets a `response` with the same id. `send` mails a ship as the captain, in that ship's own home, as a `request` (the default), `notice` or `reply` (with `correlation`); without `to` it goes to the door's `--to` ship, else the fleet's one liaison, else a one-ship fleet's ship. `ships` lists the fleet with scopes and the default recipient; `status` and `waiting` answer from records with no wake and no model call (what each ship is doing, and the requests and decisions still owed the captain). Every send is audited in the receiving home as `door.send`. See the [Telegram door](../plugins/telegram/README.md) for the first adapter.

## Plugins and local configuration

Optional executable plugins use JSON lines over stdio. They receive a minimal task context and return a validated command specification; they cannot widen the charter. Harness choice, model choice, provider routing, and private gateway policy live outside the core.

Examples can demonstrate a generic native harness or a gateway-constrained Pi route. A particular account's endpoint, provider alias, allowed models, and credentials belong in private configuration, not an example checked into Git. An unavailable required route is an error, never permission to bypass it. New provider adapters do not require changes to task/event/job storage.

## Peer transport

`peer.put` stores a transport address: name, `ssh` or `local`, absolute executable/home paths, timeout, and response limit. `peer.call` sends one correlated RPC request and returns the remote envelope. Each remote command enforces that remote home's workflow rules. Native SSH supplies host verification and authentication.

SSH runs a remote shell even when invoked through a local argv array. Privateer validates endpoint tokens and POSIX-quotes every remote command argument. Stdin carries JSON; task contents never become shell commands. Request size, output size, diagnostics, and total call duration are bounded. A local transport exercises the identical RPC protocol without SSH credentials.

This milestone does not implement distributed consensus or cryptographic cross-host charter inheritance. Explicitly configured remote homes remain responsible for their own charters. A peer's address is not a superior role or authority credential. Cross-host authorization and custody protocols need further qualification before replacing a fleet.

## Delivery and deployment

Passing-head checks bind delivery evidence to the current artifact. Production approval binds a separate decision to an exact artifact and environment and records an approver other than the task owner. That approval supplies authority for the single deployment without requiring broader standing deployment rights: the production `delivery.check` that allows it consumes it. Active task/charter reads and exact approval matching and consumption share a write transaction, so a concurrent revocation cannot leave the check using stale authority. These are workflow guards running under one OS identity.

## Operators and agents

Harnesses launched by `agent.start`, and any job an agent starts, run with `PRIVATEER_ROLE=agent` and `PRIVATEER_ACTOR` set to the task owner. Under that role, operator commands (`init`, `charter.put`, `charter.revoke`, `approval.grant`, `approval.consume`, `peer.put`, `resource.recover`) are refused, `actor`/`from` arguments must name the agent itself, and jobs can be started only for the agent's own tasks. `peer.call` passes the role to the remote home as `--role agent --actor NAME`, flags that can only narrow a caller, never widen it. The same caller checks apply to human CLI commands: agents cannot run bare `privateer`, the dashboard, `start` or `service`, or directly initialize a home; `project add` applies the `project.add` limits. Agents require an existing home; an explicit `--home` does not grant operator authority. Mail shortcuts use the agent's own address. `ship new|retire` retain the delegated creation, action and retirement limits described under [The fleet](#the-fleet), including bounded internal child initialization. This stops a confused or overeager agent from widening its charter or approving its own deployment. It is not a security boundary: an agent that deliberately clears its environment or edits the state database is outside it. Enforced separation needs a separate OS account or broker. Hard isolation from production credentials requires a separately enforced broker or account boundary.

The first milestone has no live forge merge/deployment adapter and no automatic fleet migration. A passing runtime pilot establishes behavior of the machinery; native model-driven execution is a separate qualification step.
