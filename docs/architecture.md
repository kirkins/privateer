# Architecture

Privateer's flat structure distributes routine decisions while preserving explicit responsibility. A navigator is a conversational role, not the scheduler's exclusive control plane. A department may contact another department directly. Tasks retain an owner, a charter, status, and bounded delegation depth. A handoff requires the current owner's request and the recipient's acceptance.

## Runtime boundary

The Rust runtime handles durable state, process supervision, resource admission, and transport. SQLite stores charter/task state, facts, pending issues, approvals, and audits. A job runs under a recorded task and an admitted resource reservation. A detached supervisor manages its payload process group and records completion after the invoking CLI exits.

Multiple homes on one host share a configured resource ledger, and admission decisions are made under its lock against the same readings, so independent departments cannot each assume the machine is free.

Heavy jobs, and any job that passes an `estimate` (`cpus`, `memory_bytes`), are admitted from live readings rather than a fixed slot count: the load average, CPU count and available memory, plus the estimates of jobs admitted within the last `ramp_secs` (default 60), whose use does not show in those readings yet. A job is admitted while load plus recent estimates stays below `max_load_per_cpu` (default 1.0) per CPU, and while available memory minus recent estimates and its own stays above `min_available_memory_bytes` (default 1 GiB). Heavy jobs without an estimate count as every CPU and 2 GiB (`heavy_estimate`), so two big builds cannot start together, while a later one is admitted once the first turns out to be light. `max_heavy_jobs` adds an optional host-wide slot cap and a charter's `max_heavy_jobs` an optional per-charter share. `resource.configure` changes these host-wide settings for every home, and is open to agents so they can tune the machine to their person's wishes, from using all of it to leaving room for the person's own work; `resource.status` shows the settings beside the live readings. Light jobs without an estimate are not subject to admission.

A job started with `wait_for_capacity: true` joins a host-wide, first-come-first-served queue in the ledger instead of being refused. Its detached supervisor waits there, re-checking cancellation and authority about once a second, and starts the payload once the job reaches the head of the queue and fits; `max_wait_secs` (default 3600) bounds the wait. Requests subject to admission cannot bypass a non-empty queue, and entries whose supervisor has gone are dropped. Nothing runs while a job is queued, so cancelling it, or losing its supervisor, simply ends it.

Admission governs work started through `job.start`. A harness started by `agent.start` is light by default, since it mostly waits on its model; its brief asks it to run builds and test suites that load the machine as heavy jobs with `wait_for_capacity`, so those are spaced out and queued. Work a harness runs directly in its own shell is outside admission. Process identity and surviving payloads matter more than a supervisor's liveness; uncertain ownership is preserved for explicit recovery. A job whose supervisor and recorded process group are both provably gone settles automatically: to its leader's recorded result when descendants outlived the leader, otherwise to `failed`. `resource.recover` explicitly releases a reservation no job can settle, such as one left by a crash between the ledger and home commits. It never releases a live supervisor or process group, and a reservation with no recorded payload identity requires `force: true`.

Events are facts. Pending notifications are a projection: repeated facts concerning the same task and issue update one pending item. An acknowledgment names the sequence actually observed, so a later fact cannot be silently discarded. Messages name a recipient and a task rather than broadcasting to the whole fleet.

History is kept until an operator prunes it. `history.prune` (`older_than_days` or `before_ms`, optionally `dry_run`) removes event facts older than the cutoff that no longer back a pending notification, audit rows older than the cutoff, and finished jobs whose reservations are released, together with their log directories. Pending notifications, including unread messages, and live or still-reserved jobs are kept. Pruned event and job ids may be reused afterwards. Nothing is deleted automatically; run it by hand or from cron.

## Ships and mailboxes

A ship is an identity with its own mailbox, first mate and crew; a home hosts one or more ships, and the directory (`ship.put`, `ship.list`, `ship.show`) records each ship's plain-language scope, location and the request kinds it accepts. `captain` is the reserved address of the person. Adding ships is an operator command.

`mail.send` writes typed, durable messages: a `request` or a `decision` (addressed to the captain) stays open until its single `reply` from the recipient, and the runtime tracks it rather than any agent's memory; a `notice` states a fact. Message ids are idempotency keys, a request can carry a reply deadline after which it reads as overdue, and typed request kinds are checked against what the recipient accepts. `mail.inbox` returns unacknowledged mail, `mail.ack` acknowledges through a sequence actually present in that mailbox and never moves back, and `mail.requests` lists incoming or outgoing requests by state. Agents send and read mail only as their own ship; only the operator speaks as, or reads mail for, the captain. `history.prune` removes acknowledged mail past its cutoff but never unread mail or a request still owed its reply. A ship can live behind a peer (`location: {"peer": name}`): mail to it is recorded first as an outgoing copy, then delivered through `peer.call` to the other home's `mail.deliver`, which accepts it only from a ship it knows to live behind a peer and only for a ship it hosts. A failed attempt leaves the copy pending, counted in `status`, until `mail.flush` delivers it; redelivery is idempotent. Each home keeps its own copy of a request, and the reply closes both. Task ids and captain mailbox storage stay local to their home; see the [dashboard](dashboard.md) for the captain's fleet view. The older `message.send`/`message.inbox` commands remain for now. See the [conversation and activation design](design/conversation-and-activation.md) for where mailboxes lead.

## Waking first mates

A ship hosted here can have a first-mate profile (`ship.put` with `first_mate`): the harness plugin manifest and options to launch, a duty task owned by the ship whose charter its first mate works under, and activation settings. `privateer serve` is the dispatcher, meant to run as a background service; `serve` with `{"once": true}` performs a single pass. Each pass delivers pending outgoing mail, records the outcome of finished wakes, and wakes the first mates that are due. It makes no model calls, and only one dispatcher runs per home (an exclusive lock on `<home>/serve.lock`); agents cannot run it.

Mail is the durable record of a pending wake. A first mate is due when its ship has mail newer than both its acknowledgement and its last successful wake, at least one message is not a low-urgency notice (routine notices wait for the next real wake), and the batching window (`batch_secs`) has passed since the newest message or the oldest has waited `max_delay_secs`. A ship whose first mate is already awake is not woken again; an hourly wake budget (`max_wakes_per_hour`) and a backoff after a failed wake (`retry_backoff_secs`) apply. A wake runs the first mate through `agent.start` under the duty task, with the wake's text (a summary of requests owed and owing, the new mail, and what to acknowledge) appended after the stable brief so the brief remains a cacheable prefix. A wake covers mail through its sequence number whether or not the first mate acknowledges it, so a forgetful agent is not woken repeatedly. `wake.list` shows each wake's coverage, job, outcome and the token usage its harness reported (Codex per-turn usage is summed; a cumulative result is taken as reported). Context follows the focus, so a first mate that starts fresh can keep working without carrying old conversations. Each message belongs to a focus: a task the ship owns (`task:<id>`, from the message's task or the request it answers), a request thread (`thread:<root id>`), or the captain's conversation (`captain`); `ship` holds the ship's long-lived knowledge. A wake covers all of a ship's pending mail, which keeps acknowledgement simple, but presents it grouped by focus: first the ship's bearings (open tasks, requests owed and owing, unacknowledged mail and the ship note, built from records with no model call), then each focus in play with its handoff note and its new mail. A wake whose oldest mail concerns a task the ship owns runs under that task when its charter allows a first mate; otherwise under the duty task. `wake.list` records every focus a wake covered.

Notes hold judgement; the runtime already records facts. `note.put` replaces a focus's note (2 KB, or 4 KB for `ship`) and keeps the last five versions; `note.get` and `note.list` read them, and the wake asks the first mate to update the note for each focus it worked on. `focus.digest` returns a focus's history on demand, curated and bounded: a task's events, jobs and mail, a thread's messages in order, or the captain's conversation. `ship.bearings` returns the summary on its own. Agents read and write these only for their own ship. `history.prune` drops notes for finished tasks and threads whose latest note predates the cutoff, keeping captain and ship notes. A wake whose mail all belongs to one focus resumes that focus's native session when it is warm: the harness reported the session at start-up (decoded from its JSON events, mirroring `plugins/native_events.py`), its last turn ended within `cache_window_secs` (default 300, while the provider's prompt cache is likely warm; 0 disables resuming), and it has had fewer than `session_max_wakes` wakes (default 6). A resumed wake passes the session to the adapter's explicit `resume` option and sends only the wake text, without the brief, bearings or notes the session already holds. Otherwise the wake starts fresh, and a single-focus fresh wake becomes that focus's session; mail spanning several foci never resumes one focus's conversation, and a failed wake drops the focus's session. Sessions rotate after `session_max_wakes` instead of compacting. `wake.list` shows each wake's mode and session. The rotation limit counts wakes rather than tokens, because harnesses report usage differently (per turn or cumulative); see the [design](design/conversation-and-activation.md#context-and-cost).

## Crew outcomes

Crew are the supervised jobs a ship's first mate starts for the ship's tasks. When a job whose task is owned by a ship hosted here first reaches `succeeded`, `failed`, `cancelled`, `timed_out` or `orphaned`, the runtime writes a notice from the reserved sender `crew` to that ship, in the same transaction that records the status, so a crash cannot separate the two. Its id, `crew-<job id>-<incarnation>`, makes it exactly one per incarnation: an orphan is reported when it is orphaned (it is no longer supervised, so its deadline is not enforced), and its later settlement is not reported again; `job.retry` is a new job with its own outcome. The notice carries the job's task, so it lands in the task's focus, and states the status, exit code, reason, duration, command, log path and the end of stderr and stdout, bounded so the whole message fits what a wake or hook shows (2,000 characters); the payload holds the same fields. Failures, timeouts and orphans are `high` urgency, success `normal`, and a job the ship cancelled itself `low`, which waits for the next real wake. A first mate's own wake jobs are excluded: `serve` records the wake, with its job id, before starting it. Each `serve` pass also reconciles unfinished jobs whose supervisor has gone, so their outcome is recorded without anyone asking for their status.

Crew run as their ship, so they cannot mail their own first mate. The supervisor sets `PRIVATEER_JOB` in each payload's environment; `crew.report` (`kind` `progress` or `decision`, a body, an optional payload and idempotency `id`) is accepted only from the agent a launching or running job works for, on a task its ship still owns, and never from a wake job. Progress is a `low` notice; a decision is a `high` request the first mate answers with `mail.send` kind `reply` to `crew`, which the crew reads with `crew.answer` (optionally waiting up to `wait_secs`). `crew` has no mailbox otherwise: nobody, the operator included, can send as it, mail it anything but a reply to its request, or name a ship after it.

## Attended mode

While the captain talks to a ship's first mate in an interactive session, that session is the first mate. It holds the ship's presence lease (`ship.attend`, `ship.leave`, `ship.presence`), and `serve` skips headless wakes for an attended ship, leaving its mail to the live session; when the lease is released or lapses, headless wakes resume. `privateer start [HARNESS] [-- ARGS]` launches the ship's harness, or the one named, in the ship folder under the agent role as the ship, holding the lease with a heartbeat for as long as the harness runs and releasing it on exit. For Claude Code, `privateer init` installs hooks (`privateer hook claude EVENT`) that take the lease at session start and show the bearings and new mail, show newly arrived mail with each prompt, keep the first mate working at turn end when unseen mail has arrived (exit status 2 with the mail as the reason), and release the lease at session end; a hook-held lease lapses after 30 minutes without activity. Each message is presented to the session once, so a first mate that does not acknowledge is not prompted in a loop. Hooks never fail the harness: errors allow the event and go to `<home>/hooks.log`. Other harnesses read their inbox as `AGENTS.md` directs. Inside Herdr, attended
leases also record a binding captured from the explicit inherited socket and
caller pane, with socket incarnation and exact terminal/location identities. A
replacement holder captures a new binding; heartbeat refreshes preserve the
existing one. Bindings support dashboard navigation, not input injection.

## Getting aboard

Bare `privateer` is the everyday entry point. Inside Herdr (`HERDR_ENV=1`), if an
executable `privateer-dashboard` is installed beside the runtime or on PATH, it
opens the dashboard. With no current ship this happens before initialization,
so onboarding can choose a dedicated folder. With a current ship its dispatcher
is ensured first. `privateer start` remains the direct first-mate path. When
the dashboard is unavailable or outside Herdr, the existing flow applies: Inside a ship folder (any folder at or below one holding `.privateer`), it makes sure the ship's dispatcher is running and then runs `privateer start`. Elsewhere it asks whether to make the current folder a ship, naming it after the folder and choosing the first installed harness, then does the same; without a terminal to ask in it prints help, and `--yes` skips the question. It refuses to make the user's home directory or `/` a ship. The dispatcher is installed as a systemd user service where a user manager is available (the unit records the current `PATH`, where harnesses usually live, and `PRIVATEER_RESOURCE_HOME`/`PRIVATEER_PLUGINS` when set) and otherwise started as a detached process logging to `<home>/serve.log`, rotated at 1 MiB. A dispatcher holding `serve.lock` counts as running however it was started, so nothing starts twice. `privateer service status|start|stop` manages it; stopping a detached dispatcher signals the recorded process only while it still holds the lock and is that home's `serve`. `PRIVATEER_SERVICE=systemd|detached|none` overrides the choice.

`privateer init --liaison` supplies an optional contact charter: `inspect`,
`message` and `spawn`, with no implementation action, plus generated first-mate
onboarding instructions. It preserves later captain edits and persists the
preset across ordinary init. Agent-created ships still inherit at most the
creator's actions. A validated `agent.start` harness job now runs under `spawn`
authority; ordinary `job.start` continues to require an implementation/test/
recovery/cleanup action and cannot request `spawn`. This lets a read/message/
delegate liaison process mail headlessly without granting implementation rights.
The instruction checklist is not proof of a model-driven onboarding outcome.

## The fleet

Every ship made with `privateer init` or `ship.create` joins a per-user fleet registry (`PRIVATEER_FLEET`, or `$XDG_STATE_HOME/privateer/fleet.sqlite`, default `~/.local/state/privateer/fleet.sqlite`), and is linked both ways with every other active ship: each home gets a local-transport peer `fleet-<name>` and a directory entry behind it, so ships mail each other without manual setup. A name belongs to one active ship; a ship whose folder was deleted no longer holds it, and linking never recreates a deleted folder. `fleet.list` shows the registry and `fleet.link` relinks this home.

Ships can make ships, so the captain can grow a fleet from the first one. `ship.create` (`privateer ship new NAME`) makes a new ship folder, by default beside the creating ship's folder, with the creator's harness unless another is named, starts its dispatcher and links it. An agent may create ships, but a new ship's charter can hold only actions the creating ship's own charter has; the operator may set any. `ship.retire` revokes a ship's charter, stops its dispatcher, unlinks it and marks it retired, keeping its folder; an agent may retire only ships it created. The registry records who created each ship.

## Plugins and local configuration

Optional executable plugins use JSON lines over stdio. They receive a minimal task context and return a validated command specification; they cannot widen the charter. Harness choice, model choice, provider routing, and private gateway policy live outside the core.

Examples can demonstrate a generic native harness or a gateway-constrained Pi route. A particular account's endpoint, provider alias, allowed models, and credentials belong in private configuration, not an example checked into Git. An unavailable required route is an error, never permission to bypass it. New provider adapters do not require changes to task/event/job storage.

## Peer transport

`peer.put` stores a transport address: name, `ssh` or `local`, absolute executable/home paths, timeout, and response limit. `peer.call` sends one correlated RPC request and returns the remote envelope. Each remote command enforces that remote home's workflow rules. Native SSH supplies host verification and authentication.

SSH runs a remote shell even when invoked through a local argv array. Privateer validates endpoint tokens and POSIX-quotes every remote command argument. Stdin carries JSON; task contents never become shell commands. Request size, output size, diagnostics, and total call duration are bounded. A local transport exercises the identical RPC protocol without SSH credentials.

This milestone does not implement distributed consensus or cryptographic cross-host charter inheritance. Explicitly configured remote homes remain responsible for their own charters. A peer's address is not a superior role or authority credential. Cross-host authorization and custody protocols need further qualification before replacing a fleet.

## Delivery and deployment

Passing-head checks bind delivery evidence to the current artifact. Production approval binds a separate decision to an exact artifact and environment and records an approver other than the task owner. That approval supplies authority for the single deployment without requiring broader standing deployment rights: the production `delivery.check` that allows it consumes it. These are workflow guards running under one OS identity.

## Operators and agents

Harnesses launched by `agent.start`, and any job an agent starts, run with `PRIVATEER_ROLE=agent` and `PRIVATEER_ACTOR` set to the task owner. Under that role, operator commands (`init`, `charter.put`, `charter.revoke`, `approval.grant`, `approval.consume`, `peer.put`, `resource.recover`) are refused, `actor`/`from` arguments must name the agent itself, and jobs can be started only for the agent's own tasks. `peer.call` passes the role to the remote home as `--role agent --actor NAME`, flags that can only narrow a caller, never widen it. This stops a confused or overeager agent from widening its charter or approving its own deployment. It is not a security boundary: an agent that deliberately clears its environment or edits the state database is outside it. Enforced separation needs a separate OS account or broker. Hard isolation from production credentials requires a separately enforced broker or account boundary.

The first milestone has no live forge merge/deployment adapter and no automatic fleet migration. A passing runtime pilot establishes behavior of the machinery; native model-driven execution is a separate qualification step.
