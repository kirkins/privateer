# Versioned releases and upgrade status

This is the release-identity foundation for [issue #76](https://github.com/kirkins/privateer/issues/76). `privateer upgrade status`, `fetch`, `adopt`, and on one machine `upgrade COMMIT --local`, `upgrade rollback` and `upgrade prune` (below) are available; linked machines can be upgraded together with `upgrade COMMIT` (below); agents can request the same round with a one-use, exact-commit-and-machine-set captain approval, and Telegram can preview and confirm an operator round (below; [the design](design/upgrade-execute.md#as-built-in-pr-5)). Do not use an ad hoc symlink switch as a safe fleet upgrade: `upgrade COMMIT --local` switches and restarts what runs it, and rolls back when a dispatcher does not come back.

## Layout

The installation data directory is `$XDG_DATA_HOME/privateer`, defaulting to `~/.local/share/privateer`:

```text
privateer/
  releases/
    <full-lowercase-git-object-id>/
      bin/privateer
      bin/privateer-dashboard
      bin/privateer-mcp-broker
      share/privateer/plugins/
  current -> releases/<full-lowercase-git-object-id>
```

Both SHA-1 and SHA-256 full Git object IDs are accepted; branch names, abbreviations, and paths are not release identities. `releases::Release` defines the layout and the stable `current/bin/{privateer,privateer-dashboard}` entry points. A future installer must publish complete immutable releases (all three binaries, the dashboard built with its feature, and their bundled plugins), then switch `current` atomically. `privateer-mcp-broker` is never run from a release: `privateer mcp-broker install` copies it to the one unversioned path `$XDG_DATA_HOME/privateer/mcp-broker/bin/privateer-mcp-broker`, so upgrades leave its path and hash alone (see [the MCP broker](mcp-broker.md)). To switch it by hand, make a new link beside it and rename it over `current` in one rename(2): with GNU coreutils, `ln -sfn releases/<id> current.new && mv -T current.new current`; on macOS, `ln -sfh releases/<id> current.new && mv -h current.new current`. Plain `mv current.new current` follows the old link on macOS and moves the new link *into* the old release directory, leaving `current` unchanged, and `ln -shf releases/<id> current` is not atomic (there is a brief moment with no `current`). `python3 -c 'import os; os.replace("current.new", "current")'` is an atomic rename on either system. The `-n`/`-h` on the first `ln` keeps a `current.new` left by a failed attempt from swallowing the new link. Stable launchers such as `~/.local/bin/privateer` and service ExecStart paths should address `current/bin/privateer`, not a commit directory; `upgrade adopt` (below) makes them do so once per machine.

The OS-reported **real executable path**, not the launcher symlink or source build path, identifies the running release. A release binary loads plugins **only** from its own `share/privateer/plugins`. It neither follows `current` for adapters nor falls back to the build checkout, ancestor directories, or `PRIVATEER_PLUGINS`. Missing release plugins are an error. Thus moving `current` cannot change the Python code under an old dispatcher.

Agent control argv, generated instructions, and newly persisted peer/service commands go through `current/bin/privateer`. New dashboard launches from a release similarly use `current/bin/privateer-dashboard`, without falling back to an unrelated PATH binary. On Linux, internal job supervisors still reexec the running image through `/proc/self/exe`; their protocol must match their dispatcher. Keep the old release's files while its processes run; `upgrade prune` (below) never removes a release a live process runs or names.

Legacy `cargo install` and source/target builds remain supported: outside a recognized release layout, existing plugin lookup (explicit `PRIVATEER_PLUGINS`, `share/privateer/plugins` beside the binary's own `bin`, then the build checkout whose `Cargo.toml` names the `privateer` package and nothing above it) and executable replacement behavior remain unchanged. They are reported as an unversioned running binary, not assigned a guessed Git commit. A source checkout changing after compilation is not evidence of a binary's commit.

CI builds this layout with `scripts/release-layout.sh` on every push to main as a downloadable artifact: `privateer-macos-arm64-<commit>` (macOS on Apple silicon), `privateer-linux-x86_64-<commit>` and `privateer-linux-aarch64-<commit>` (Linux, built on Ubuntu 24.04 and checked to need glibc 2.39 or older, so they run on Ubuntu 24.04 and newer). Each holds one tarball of one `<commit>/` directory as above, plus `<commit>/SHA256SUMS` covering every other file in it. A release holds plain files and directories only, no links. The bundled plugins need `python3` on the machine.

## Fetching a release

```sh
privateer upgrade fetch <commit> [--build] [--source CHECKOUT] [--repo OWNER/NAME]
```

Operator only. It prepares `releases/<commit>` in the installation the running binary belongs to and switches nothing: `current`, launchers, service units and running processes are untouched. A complete release is staged under `staging/<id>/`, checked, and only then renamed into `releases/`, so `releases/<commit>` is either complete or absent.

- **From CI.** When `uname -sm` names a platform CI builds (and, on Linux, `getconf GNU_LIBC_VERSION` reports glibc 2.39 or newer), `gh api` finds the push run on main of `.github/workflows/ci.yml` in the repository (default `kirkins/privateer`; never a pull request's, a fork's or another workflow's run) whose release job for this platform succeeded, and its unexpired artifact. While that job is still queued or running the fetch is refused ("CI is still building"), never built from source instead; only a commit with no such run, or whose release job failed, was cancelled or was skipped, falls back to a build. The download's sha256 must equal the digest GitHub reports. The zip is unpacked with `python3 -I -m zipfile`, its tarball's names are checked to lie under `<commit>/` before `tar` extracts it, and the result must hold every binary, plugin manifests and a `SHA256SUMS` matching every file exactly.
- **From source.** With `--build`, or when CI has nothing for this platform or commit, and only with `--source CHECKOUT`: the commit must be on the checkout's `origin/main` (fetched first). It is exported with `git archive`, leaving the checkout's working tree, index and branch alone, built with `cargo build --release --locked --features dashboard` into `<data>/build/target`, and laid out by the same script CI runs. Builds share that target directory, so one source build runs at a time: the build and its layout hold `<data>/build/lock`, and a second fetch that needs a build meanwhile is refused, naming the holder. Without `--source` such a machine is refused, with the reason.
- **The checkout is the operator's choice.** A source build trusts the checkout's own `origin`: it is what `origin/main` means, and what is built. `--repo` names where CI artifacts come from and does not change the checkout's remote; when `--repo` is given, the checkout's origin URL must name that repository (`OWNER/NAME` as its last two path segments, `.git` aside) or the build is refused. Without `--repo`, nothing checks the origin, so build only from a checkout you trust. A wrong digest, a bad tarball or a failed check never falls back to a build.
- **Smoke check.** Before publishing, the staged `bin/privateer` must report itself as `<commit>` in `upgrade status`, initialise and read a throwaway home, and the dashboard and broker binaries must run, so a wrong-platform build fails here.
- **Releases never change.** An existing `releases/<commit>` is reused only when it is a real directory (a link to one is refused) whose `SHA256SUMS` still checks out exactly: every listed file matches and nothing else is present, `__pycache__` included. Otherwise the command fails naming the directory and overwrites nothing. The bundled plugins never write bytecode into a release: every plugin script that imports another sets `sys.dont_write_bytecode` before doing so, adapters run as `python3 -B -E -s`, and the smoke check runs with `PYTHONDONTWRITEBYTECODE=1`.

The build runs in the foreground and does not yet take the machine's heavy slot. `PRIVATEER_GH`, `PRIVATEER_CARGO` and `PRIVATEER_GLIBC` replace `gh`, `cargo` and getconf's report in tests.

## Adopting a machine

```sh
privateer upgrade adopt [--dry-run] [--commit COMMIT] [--allow-different-build]
```

Operator only, once per machine. A machine installed with `cargo install` (or by copying binaries into `~/.local/bin`) runs an unversioned binary, and every recorded path names it: unit `ExecStart` lines, `peer.executable`, `AGENTS.md`, permission rules. Adoption keeps those paths valid by making them resolve through `current/bin/<name>`, without rewriting the records:

- **The release.** The running binary's own release when it runs from `releases/<commit>`; otherwise `--commit COMMIT`, whose `releases/<commit>` must already exist and pass the same check as `upgrade fetch` (`SHA256SUMS` exact). A missing release is refused with "run `privateer upgrade fetch COMMIT` first": adopt builds and downloads nothing. Choose the commit of the build installed now: new wakes and jobs run the adopted release at once (below). Every proven installed `privateer` that is a real file is compared with the release's `bin/privateer`, and the report lists each under `installed` with `same_build`. Adopt cannot order two builds (an unversioned binary's `upgrade status` reports no commit, and the state schema has a single version), so when any installed `privateer` is not byte for byte the release's, adopt refuses unless `--allow-different-build` says the release is the build new wakes should run (it must not be older than the installed one). A CI artifact and a local `cargo install` of the same commit differ in their bytes, so adopting one over the other needs the flag too. `--dry-run` never refuses for this: it still lists the whole plan and adds `"would_refuse": "different build"` with the `refusal` a real run would print.
- **`current`.** Created pointing at `releases/<commit>` (a relative link made as `current.new` and renamed over `current`) when there is none. When it already selects that release it is left alone; when it selects another, adoption is refused: switching is not adoption's.
- **Launchers.** `privateer`, `privateer-dashboard` and `privateer-mcp-broker` in `~/.cargo/bin`, `~/.local/bin`, and the running executable's directory when it is not a release, become links to the absolute `<data>/current/bin/<name>`, each made as `<name>.new` and renamed over the file. A launcher already linked there is left; a link anywhere else is reported and left, and so is a proven launcher whose directory (or the file itself) this user cannot write, such as one in `/usr/local/bin`: link it by hand. A real file is replaced only when it is proven to be that Privateer binary: it is the running image itself (same device and inode), or it is a native executable (ELF or Mach-O, so a script or wrapper is never run or replaced) that, run with a throwaway HOME, XDG directories, fleet registry and ledger and no service manager, answers as itself: `privateer upgrade status` printing release status whose `running_executable` is that very file, the dashboard's `--help` banner, or the broker's `--version`. Anything else is reported with the reason and left; a binary too old to have `upgrade status` is among them (replace it by hand, or `cargo install` a newer one first). `CARGO_HOME` is not followed. The MCP broker's installed copy under `<data>/mcp-broker/` is never a launcher: its path and hash stay as they are ([the MCP broker](mcp-broker.md)).
- **Units.** Every dispatcher and door unit in the systemd user unit directory, and every dispatcher and door agent in `~/Library/LaunchAgents`, that Privateer generated (recognised by its `privateer-` name and its description, or an agent by its exact `--home HOME serve` or `door run NAME` arguments) and that does not run `<data>/current/bin/privateer` has its program rewritten to it, its arguments and environment kept; a dispatcher's also gets the safe stop policy `service stop` applies (`KillMode=process`; an agent abandoning its process group). Only a unit whose program is a `privateer` launcher this adoption moves or already moved (the same path, or the same device and inode) or lies inside this installation is rewritten; one running another `privateer` (a development build, a canary, another installation's) or something else is reported and left with the reason, and so is an `ExecStart` whose program is neither quoted nor an absolute path (a `-`, `@`, `+` or `!` prefix, single quotes, escapes or specifiers). Each is written beside the file and renamed over it. On Linux this is followed by one `systemctl --user daemon-reload`. On macOS launchd has no reload that does not restart, so `launchctl` is not called: a changed agent is read at its next bootstrap, and until then launchd restarts it through the old path, which is now a launcher into `current`. Nothing is started, stopped or restarted, but that does not mean nothing changes at once. A running dispatcher starts each new wake and job through the path it was started from (`executable::installed()`): on Linux that is the replaced launcher's path (the kernel reports the old file as deleted, and the suffix is dropped), on macOS the path it was invoked by, and either now leads to `current`. So new wakes and jobs run the adopted release immediately, while the dispatcher and doors themselves keep the old image until their next restart. On Linux a hosted pane whose image was replaced counts as drifted and relaunches at its next idle point; on macOS panes report no drift from adoption.

The report is one JSON object listing each action (`current`, `launcher`, `unit`, `reload`) with its `state`: `done`, `would` (under `--dry-run`, which changes nothing and lists the same plan; it does run the sandboxed identity checks), `already`, or `left` with a `reason`. A failure stops at that action, marked `failed`, with the rest `not_done`; the command prints the report and exits non-zero, each file is either the old one or the new one, and nothing is recorded in the history. A rerun picks up what is left. When it finds the work done but no adoption in the history (the earlier `daemon-reload` or history write failed), it plans one `daemon-reload` for the systemd units already pointing at `current` and records the adoption. A second run after a recorded adoption is a no-op that says so (`noop: true`). Adoptions of one installation are serialised by `<data>/upgrade.lock`. An adoption that changed anything is recorded in the upgrade history with `kind: "adopt"`.

Once `current` is set, `upgrade status` lists in `launcher_unversioned` each native executable that is a real file at a launcher path again (a later `cargo install`). Running `upgrade adopt` again does not fix this: the new `cargo install` is a different build from `current`, so adopt refuses it, and linking the launcher back to `current` would usually move it onto an older build. The way forward is `upgrade fetch` of the newer commit and `upgrade COMMIT --local` (below), which reports these launchers in its plan but does not refuse them.

## Switching to a release

```sh
privateer upgrade COMMIT --local [--dry-run]
privateer upgrade rollback [--local] [--dry-run]
```

Operator only (an agent is refused). `--local` selects the existing single-machine path described here. Without it, use the linked-machine round below. Nothing is fetched or built: `releases/COMMIT` must exist and pass the same check as `upgrade fetch` (else "run `privateer upgrade fetch COMMIT` first"), and the machine must be adopted: `current` exists, and every dispatcher and door unit or agent that adopt would repoint already runs `current/bin/privateer` (or a launcher linked to it); else "run `privateer upgrade adopt` first". A unit pinned to another `privateer` (a development build, another installation's) is left out of the round and listed under `left`, as is a service that is not running, or a detached one that runs no release of this installation or is not the process its pid file records (a dispatcher started by hand while the pid file names a process that has exited): restart those by hand. A dispatcher agent that does not abandon its process group (`<key>AbandonProcessGroup</key><true/>`, or `<false/>`, which the round rewrites) is refused before anything moves, since stopping it would end its wakes. `--dry-run` prints that plan (`dispatchers`, `doors`, `stop_policy`, `left`, `launcher_unversioned`) and changes nothing.

The round runs **detached**: the command starts `privateer upgrade _round ID` in its own session and waits for it, so restarting the dispatcher that the command may be running under cannot end the round. Each step is recorded as it happens in `<data>/upgrade/ID.json` (written beside itself and renamed over; the newest 20 rounds are kept, with their logs), and the command prints that state when the round ends. Rounds, adoptions and prunes of one installation are serialised by `<data>/upgrade.lock`, so a second round is refused while one runs. In order:

1. **Stop policy.** A dispatcher unit without `KillMode=process`, or an agent whose `AbandonProcessGroup` is false, gets it (written beside the file and renamed over). Then, whenever any unit is about to be restarted, one `systemctl --user daemon-reload`, changed or not: systemd stops a unit as it last read it, so a file edited by hand without a reload is read before its restart.
2. **Switch.** `current.new` is made as a link to `releases/COMMIT` and renamed over `current`; the previous target is recorded (`from`).
3. **Dispatchers.** Each running dispatcher in the fleet registry is restarted through what keeps it: `systemctl --user restart UNIT` (systemd stops only the main process, `KillMode=process`); on macOS `launchctl bootout` of its agent, a wait for its lock to be released, then `enable` and `bootstrap` (which reads a changed agent); a detached one is sent SIGTERM only while it still holds its lock and is the process `service start` recorded, and started again from `current` once it lets go. Running wakes and jobs are never stopped: their supervisors run in their own sessions, outside the dispatcher's unit or process group, and the new dispatcher adopts them.
4. **Health.** Each restarted dispatcher must hold its lock again under a new dispatcher generation within 60 seconds, report in that generation's record of its own image that it runs `releases/COMMIT`, and finish one dispatcher pass on it (`serve` records the first). A generation that lets go of its lock before that, or is replaced by another (a unit restarting a release that keeps crashing), fails at once. A dispatcher from before that record existed only has to come back. If any fails, `current` is switched back, every dispatcher is restarted again and checked against the previous release, and the round ends `rolled_back` (or `failed` if the previous release did not come back either). Doors are not restarted then.
5. **Doors**, only after every dispatcher passed: each running front door is restarted the same way and must hold its lock again. A door that does not is reported; the round ends `switched_with_failures` and exits non-zero, with `current` and the dispatchers on the new release.
6. **Hosted panes** are neither asked nor touched; their leases stay. A pane behind `current` catches up on its own at its next safe point (a sleeping pane at once, an idle one after its idle threshold, a busy one once its turn ends), as it does after any switch. The summary says which: `pane relaunch pending at its next safe point`, `pane busy: catching up when its turn ends`, or `pane on the current release`.
7. **Summary and history.** One line per ship (`infra: dispatcher restarted (systemd) on 0123456789ab; pane relaunch pending …`) and per door (`door:NAME: door restarted …`), what was left and why, and each MCP broker instance whose installed copy differs from the release's `privateer-mcp-broker`, as a captain action (`privateer mcp-broker stop --name N`, then `install`, when its windows are idle); the broker is never touched. The upgrade history gains `kind: "upgrade"` with `outcome` (`switched`, `switched_with_failures`, `rolled_back` or `failed`), the per-ship outcomes and `from_commit`; an automatic rollback adds a second record, `kind: "rollback"`, whose `rollback_of` names the upgrade it undid. A round that did not end `switched` exits non-zero.

Once `current` has moved, no step ends the round on its own: a step whose state cannot be saved is logged and the round goes on, the fleet registry is opened before the switch, hosted panes and MCP brokers that cannot be read are reported as such, and if the round still cannot finish (its history cannot be written, say) it goes back exactly as for a failed health check, restarting the doors it had restarted too, and records what it can.

A round **killed** midway (out of memory, the machine going down) leaves its state without an `outcome`; `upgrade status` shows it with `interrupted: true` and a `note`. If it had switched, `current` selects the new release and its dispatchers may be partly restarted: `privateer upgrade COMMIT --local` with the same commit resumes it, restarting every dispatcher and door the interrupted round planned (running or stopped by now) and checking them, with the release it came from as the rollback target; the old round is closed as `interrupted` with `resumed_by`. `privateer upgrade FROM --local` goes back instead. A round killed while rolling back is not resumed: `current` is already back, and its dispatchers are restarted by hand.

`upgrade rollback` switches to the release the newest successful (`switched` or `switched_with_failures`) upgrade onto the current release came from, through the same round (its record is `kind: "rollback"` with `rollback_of` naming that upgrade). A rollback's own record is never followed, so a second rollback steps further back rather than returning to the release just left.

On **Linux** with systemd the restart is `systemctl --user restart`; on **macOS** it is `launchctl bootout` then `bootstrap` of the agent, which SIGTERMs the dispatcher alone (its agent abandons its process group, and job supervisors run in their own sessions, as `service stop` relies on); this path is exercised here only through a fake `launchctl`. Without a service manager (`PRIVATEER_SERVICE=detached`), the recorded process is restarted on either system. A restarted dispatcher or door gets the environment of the command that ran the upgrade, as `service start` gives it.

## Upgrading linked machines

**All linked machines must run the same Privateer build for delegated sends**
(including MCP/ChatGPT sends). Upgrade senders, receiving gateways, and collectors
as one fleet, and verify their running builds before resuming delegated traffic.
An older collector permanently refuses unknown delegated message kinds, for
example `unknown message kind delegated.send.v1`. The sender's message is then
lost and must be resent after the builds match; upgrading does not recover it.
A queued send is not proof of delivery. Avoid delegated sends during a partial
upgrade or mixed-build rollback; do not downgrade to an unprovenanced send.

```sh
privateer upgrade COMMIT [--dry-run]
```

Operator only, from the captain's desk machine. Install this gateway-capable build by hand once on each machine, and adopt each installation first. The desk probes all direct outgoing machine links, prepares and verifies **all** participating releases, and only then applies one machine at a time (linked machines in name order, desk last). A preparation failure switches nothing anywhere. A machine already selecting the target must verify it, then is reported `already_current` without prepare/apply, so a retry can finish a partial round. If every machine is already current, the round ends `already_current`. Retrying after a machine's local apply ended `switched_with_failures` also skips it because it already selects the target: **its failed doors need a manual restart**, not another linked upgrade. A gateway too old for `upgrade.probe` is explicitly skipped and reported; a successful round containing such skips ends `switched_with_skips`, not `switched`. Connection failures are not skipped. Reverse-only links are refused because the desk cannot call them.

Each machine fetches with its own `gh` when available; otherwise the desk can push the GitHub-digest-checked artifact in bounded chunks. When a source build is necessary, configure `PRIVATEER_UPGRADE_SOURCE` in that machine's gateway environment to an absolute trusted checkout; a caller cannot supply a remote filesystem path. Source builds do not yet take the machine's heavy slot. `--dry-run` lists the target order without preparing or changing anything.

The coordinator is detached and records per-machine probes, preparations, local apply round ids/results and summary strings under `<data>/upgrade-linked/ID.json` (20 rounds retained); `upgrade status` includes its newest state as `linked_round`. On any failed or unknown apply the round stops, **leaving already switched machines in place**. The failing machine uses the single-machine rollback policy above. There is no distributed rollback: inspect the reported machine round before recovering with its local upgrade/rollback command, especially after a lost connection or interrupted coordinator. See [As built in PR 4](design/upgrade-execute.md#as-built-in-pr-4) for the gateway protocol, chunk bounds and recovery limitations.

If the coordinator died with a lost apply reply or an unreachable recorded machine, inspect every machine marked `applying` first. Once satisfied that starting another linked round is safe, run:

```sh
privateer upgrade interrupt-linked ID --inspected
```

This operator-only command marks the coordinator interrupted and preserves its machine records; it does not cancel or reconcile remote applies. It refuses while the coordinator lock or recorded pid is live/uncheckable, and during its first 30 seconds of startup. A reused live pid is conservatively refused too. Retry `upgrade COMMIT` only after inspecting/recovering the actual remote rounds; the flag is an acknowledgment of that inspection, not proof that an unreachable machine stopped.

## Agent requests and Telegram

An agent first calls `upgrade.plan` with `{"commit":"<full lowercase SHA>"}` from a ship home on the captain's desk machine. It returns the ordered `machines` and an opaque `environment` binding this installation and the complete named link destinations. A plan changes nothing and makes no network calls. Use that exact environment and commit when asking the captain for a `production_approval` through the normal mail/`approval.grant` flow.

Only after the captain grants it, call:

```text
upgrade.start {"commit":"<full lowercase SHA>","task_id":"<owned task>","approval_id":"<captain grant id>"}
```

The runtime derives the environment again, checks the existing approval's exact artifact, environment, active charter hash and captain approver, and consumes it once in the same write transaction as the request's durable custody. An `upgrade:` grant defaults to a 24-hour expiry; the captain may supply `expires_ms` to `approval.grant`. An expired or legacy non-expiring approval is not accepted for an upgrade. Standing grants, publish or merge rights are never deployment authority. The consume transaction copies the deadline into the queued request. Dispatch after that deadline fails without preparing anything, replies in the operation thread and notifies the captain; the approval stays consumed. Any retry, even after a start failure or queue expiry, needs a fresh approval.

The call only records approved intent and returns immediately, not after the switch. It returns `id` (the queued linked round), `dispatch: "pending"` and `request_thread` (the runtime-owned operation request). A running operator dispatcher, or an operator `serve` maintenance pass, must claim and start it. The dispatcher rechecks the installation and machine bindings, replaces recorded machines/routes with its own fresh plan (missing route hashes fail closed), and supplies its own environment: none of the agent's artifact, source-build, PATH or service overrides reach the worker. A claim is never automatically retried after a crash; inspect unavailable custody and obtain a new approval. On completion the agent receives one reply in that thread, with the outcome and per-machine lines. The captain receives a notice only for `rolled_back`, `switched_with_failures`, `switched_with_skips` or `failed`. A dispatcher restart recovers unsent terminal outcomes idempotently from the absolute round-state path recorded at dispatch (even if its own data directory differs); it never replays applies to recover mail. The linked state and request audit name `requested_by` and `production_approval`. Errors handling one request are logged and recorded without blocking later requests. The dispatcher refuses stale queued intent if the local selected release has changed since admission, except when it already equals the target (`already_current` is still a no-op). This conservatively prevents a queued target from undoing an intervening local switch; it does not order opaque commit ids or prohibit an intentionally approved older commit when selection has not changed.

The dispatcher starts the same operator coordinator as `upgrade COMMIT`. It reparents and leaves the dispatcher's session. On scoped Linux installations it also requests a sibling transient scope with `systemd-run --user --scope --collect`, then checks that it left both the dispatcher's and the requesting wake's recorded cgroup subtrees before working. Scope selection uses the operator dispatcher's service environment, not the agent's `PRIVATEER_SERVICE`. There is no unsafe fallback if the user manager is unavailable. A wake can therefore start the operation asynchronously and finish independently of its dispatcher's restart. macOS/unscoped installations use the detached session; `PRIVATEER_SERVICE=none` fixtures never contact a real manager.

In Telegram, `/upgrade <full lowercase SHA>` shows the dry-run target order and a **Confirm upgrade** button. Confirmation expires after five minutes, is single use, is lost if the door restarts, and refuses a changed plan. It is the captain's operator command and needs no additional production approval. Set `allowed_user_ids` to include the captain: both the command and confirmation require a listed sender, even in private chats. Bad outcomes arrive by mail. The dashboard has no upgrade action yet: its live attention-action loop has no installation/round confirmation view; use the CLI or Telegram rather than treating a per-ship attention answer as deployment confirmation.

## Pruning releases

```sh
privateer upgrade prune [--keep N] [--dry-run]
```

Operator only. Removes old releases from this installation's `releases/`, keeping the newest N (default 3, by when each was published), the one `current` selects, the one `upgrade rollback` would return to, the release the command itself runs, and every release a live process of this user runs, works in, or names in its arguments. The executable and working directory are the kernel's resolved paths (`/proc/PID/exe` and `/proc/PID/cwd` on Linux, `proc_pidpath` and `proc_pidinfo` on macOS), so a process started through `current` still protects the release it runs after `current` moved, and a plugin adapter run from its release's directory with relative arguments protects that release. Arguments are read as invoked (`/proc/PID/cmdline`, or `ps` on macOS) and only count when they name a path under `releases/`. Only real directories directly inside `releases/` named by a full commit are candidates; anything else there (a link, a file, a staging leftover) is left. Each is renamed aside within `releases/` and then removed, so a half-removed release is never seen under its name, and the in-use check is repeated just before each removal. `--dry-run` lists `would_remove` and changes nothing; the report lists what was kept and why.

## Bundled ship manifests

A first-mate profile stores `"manifest": "bundled:pi"` (or another bundled harness id) rather than a checkout/release path. Profile validation, activation, native-session decoding, plugin command planning, attended harness selection, and child-ship inheritance understand these references. Resolution uses the *running runtime's* plugins. Private configs, model/provider options, and charter provider-plugin pins are not rewritten.

Opening a ship home transactionally and idempotently migrates recognizable old `first_mate.manifest` paths:

- A standard `plugins/<known-harness>/manifest.json` in the build checkout or a recognizable checkout (`.git`, `Cargo.toml`, and `plugins/native.py`), when its JSON matches the shipped bundled manifest.
- A matching bundled manifest in the versioned release layout, including an absent manifest under a deleted release.

Custom paths stay absolute and unchanged, even when their manifest declares a familiar id or has the same JSON as a bundled adapter. Modified manifests are not silently converted. An already-deleted **unidentifiable checkout** cannot safely be distinguished from a missing custom plugin: its path is preserved, not guessed. Such records need an explicit operator profile update to `bundled:<id>`. A new ship using the ordinary bundled manifests records a durable reference before its checkout can disappear. This migration changes no provider route or private config.

## Status and history

```sh
privateer upgrade status
privateer upgrade.status --json '{}'
```

Both forms emit JSON, work outside a ship folder, and may be read by agents. `upgrade.status` is also available over RPC. Status is read-only: it does not create a fleet registry, run Git, change `current`, or start/stop anything.

Fields include:

- `current_commit`: release selected by `current`, or null if no release is selected.
- `running_commit`: this process's release, or null for an unversioned executable. It can differ from `current_commit`.
- `current`, `running_executable`: paths that make that distinction inspectable.
- `launcher_unversioned`: once `current` is set, the native executables that are real files at launcher paths (see adopting, above).
- `history`: newest 100 upgrade outcomes from the fleet registry (`history_limit: 100`). Existing registries without an upgrades table report an empty history.
- `keep_releases`: `upgrade prune`'s default, 3; not a claim that pruning ran.
- `round`: the newest `upgrade COMMIT --local` or `upgrade rollback` round's state (its steps, `outcome` once it ended, `summary`), with `in_progress` true while it still runs, and `interrupted: true` with a `note` saying how to go on when it stopped without an outcome.
- `hosted_panes`: each live hosted first mate in this home (listed for the operator when a ship home is at hand). Each reports the release its process runs (`commit`, null for an unversioned build), its `executable`, the `current_commit`, and `drift`: true when the pane runs a different release than `current`, or its binary was replaced on disk. Drift is reported, not repaired, here: hosted panes relaunch at their next idle point or through `privateer host relaunch SHIP`, as the [architecture notes](architecture.md#hosted-first-mates) describe.

A dangling, invalid, or foreign `current` target is reported as an error, not repaired. The fleet registry gains an additive `upgrades` table, independent of per-ship home schemas. `UpgradeRecord` holds an id, exact from/to commits, actor, start/completion timestamps, and each ship's outcome. The persistence API is idempotent for identical records and refuses a conflicting record with the same id. There is deliberately no command to fabricate history: only adopt, upgrade and rollback rounds record their results here. Status does not imply that the live fleet has restarted or that an upgrade has been approved.

The isolated release tests use copied test binaries, disposable registries/homes, and a real dispatcher and adapter subprocess. They switch only fixture symlinks, never the installed Privateer binary or a live fleet.
